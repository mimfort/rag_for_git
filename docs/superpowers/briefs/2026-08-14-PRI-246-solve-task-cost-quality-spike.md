## Task
- **Проблема:** 28 из 55 брифов в `docs/superpowers/briefs/` несут детерминированный блок «## Токены (этап solve-task)» (пишет `plugin/hooks/brief_cost.py`), но эти данные ни разу не агрегировались — решения об оптимизации solve-task (prepare_task_context, разгрузка SKILL.md, правки грунтовки) принимаются без baseline.
- **Что сделать:** (1) разовый скрипт под `eval/` парсит блоки токенов из 28 брифов (fresh-in/output/cache-write/cache-read, main vs sidechain, разброс по задачам); (2) сопоставить пути `## Relevant code` каждого брифа с файлами, реально изменёнными в PR той же задачи (связь уже в графе `:Task`); (3) посчитать precision/recall ретрива, отдельно — что систематически теряется (тесты/конфиги/миграции); (4) короткий отчёт: цена этапа, структура расхода, попадание ретрива, вывод по трём смежным задачам.
- **Критерии приёмки** (из description, блок «## Критерии приёмки» — `criteria` в сторе пуст):
  1. Числа по фактической цене этапа и структуре расхода (главный цикл vs sidechain).
  2. Измеренные precision/recall ретрива на выборке брифов.
  3. Явный вывод — какие из PRI-247/PRI-249/prepare_task_context оправданы данными, какие закрыть без реализации.
  4. Код анализа помечен одноразовым (eval-харнес), в продакшн-путь reviewer не попадает.
- Продакшн-код не трогает; спайк предшествует и может отменить/переупорядочить три смежные задачи.

## Constraints / open questions
- **Округление необратимо:** `human_tokens` пишет 1 значащую цифру после точки (K/M) — точный `total`/по-бакетные суммы, посчитанные обратным парсингом markdown, будут иметь погрешность в пределах округления; это ограничивает точность вывода «цена этапа» до диапазона, не до точного числа. Альтернатива — если нужна точность, парсить исходные JSONL-транскрипты сессий (`aggregate_usage`/`find_window_start` в `brief_cost.py:112-155`), но это требует доступа к транскриптам, которых у скрипта, скорее всего, нет (только 28 markdown-брифов упомянуты в задаче).
- **Не все 55 брифов сопоставимы:** блок токенов есть только в 28 — часть до PRI-208 (сайдчейна ещё не было), часть без `.review.yml`-флага. Отчёт должен явно разделить «нет данных» от «нулевая стоимость».
- **Task-ключ из имени файла:** задача говорит «ключ задачи есть в имени файла брифа» (паттерн `YYYY-MM-DD-<KEY>-slug.md` или без ключа, см. `2026-06-27-solve-task-brief-token-cost.md`/`2026-06-28-improve-solve-task-skill.md` в листинге — без явного PRI-ключа); скрипту нужен fail-soft regex-экстрактор ключа, пропускающий брифы без ключа, а не падающий на них.
- **TOUCHES может быть пуст:** `link_pr`/`link_prs_batch` — `touched=[]` для пар из `index_batch` (батчевая линковка без TOUCHES, «код подтягивается лениво через get_pr_diff»); часть задач в графе может не иметь touched-символов вовсе, даже если PR слинкован — тогда recall/precision для этой задачи не считаются, а не считаются нулём.
- **`get_task_context` фильтрует linked по project, но не сам taskʼ prs** — для сопоставления PR по ключу из имени файла брифа лучше идти напрямую `get_task_context(key)`, а не через `search_tasks`.
- **eval/ уже пакет с `__init__.py`** — уточнить при реализации, кладётся ли одноразовый скрипт как модуль пакета `eval` или как top-level scratch-файл вне пакета (не конфликтует ли с существующими импортами `eval/run_eval.py`).
