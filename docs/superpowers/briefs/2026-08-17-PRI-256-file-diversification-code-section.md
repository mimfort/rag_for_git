https://ru.yougile.com/team/686c049c8af8/#PRI-256

## Task
ID-310 (алиас PRI-256), родитель ID-307. Секция `code` брифа solve-task режет по релевантности
чанков, а не по разнообразию файлов; бюджет секции по сути файловый (путь `path:line — почему`,
не тела символов). Требуется: (1) потолок чанков на файл при отборе кандидатов code, (2) отдельный
более широкий файловый бюджет для code, независимый от чанкового потолка общего поиска,
(3) строка на файл в бриф без лишнего дублирования. Критерии: медиана числа файлов в code выросла
относительно baseline; дельта bulk core-recall от этого рычага измерена отдельно; объём секции
code в символах не растёт непропорционально числу файлов.

## Constraints / open questions
- **Premise тикета устарел.** Описание задачи ссылается на `search_base`/`retriever.py:198-212`
  как место cliff-отсечки секции `code`. После PRI-255 (смержен) секция `code` идёт через
  параллельный путь `reviewer/retrieval/multiquery.py::search_multi`, где реранкера и cliff-отсечки
  нет вовсе (единственный ранкер — RRF); `search_base`/`retriever.py:198-212` по-прежнему
  используется, но для `/ask`, грунтовки и графового пути ревью PR, не для секции `code`
  solve-task. Рычаг PRI-256 нужно ставить в `search_multi`, а не в `search_base`.
- **Baseline «5-6 файлов» из тикета не сходится с офлайн-отчётом.** `eval/replay_report.md`
  фиксирует «предсказано файлов (медиана): 2 → 4» именно для перехода
  однозапросный-`search_base` → `search_multi` (PRI-255), т.е. текущий baseline ПОСЛЕ PRI-255 —
  медиана 4 файла, а не 5-6. Цифра «5-6» в тикете, видимо, из более старого/иного замера (или
  оценки на глаз) и не подтверждается найденным отчётом — реализатору стоит использовать «медиана 4»
  как фактический текущий baseline для критерия приёмки №1, либо явно указать источник «5-6», если
  найдётся другой отчёт.
- **Взаимодействие файлового бюджета с внешним символьным потолком (критерий №3).**
  `ContextPack.as_context()` режет итоговый текст тупым `text[:max_chars]`, `max_chars =
  settings.max_tool_result_chars` (дефолт 8000 символов), это применяется ПОСЛЕ `MAX_BLOCK_CHARS=
  2000`-обрезки каждого блока. Уже сейчас 15 блоков × ≤2000 символов теоретически дают до 30000, но
  реально долетает ~4 блока до среза в 8000. Значит: (а) простое расширение `ceiling` без per-file
  потолка не даёт роста разнообразия файлов, потому что 8000-предел режет раньше; (б) наоборот,
  агрессивный per-file потолок (например 1-2 чанка/файл) при сохранении текущего `ceiling=15` и
  `MAX_BLOCK_CHARS=2000` МОЖЕТ дать пропорциональный рост файлов без роста итогового объёма, если
  подобрать числа так, чтобы суммарный текст оставался в районе прежних ~8000 символов. Нужно
  явно спроектировать, что режется первым — блок или общий текст — и соотнести это с критерием
  «рост числа файлов не даёт кратного роста токенов брифа» до реализации.
- **`RRF_K=60`** продублирован в трёх местах (`multiquery.py`, SQL `index/store.py::hybrid_search`,
  `tasks/store.py::search`) — известный долг, не предмет этой задачи, но при добавлении нового
  файлового бюджета НЕ трогать эту константу и не плодить четвёртую копию.
- **Соседний нереализованный рычаг ID-312** («Разворот кластеров subsystems в файлы-кандидаты»)
  тоже расширяет состав файлов секции `code`/входа брифа, но с другой стороны (через subsystems, а
  не через multiquery-хиты). Порядок реализации не зафиксирован — если ID-312 будет делаться
  параллельно/после, стоит свериться, не задвоится ли файловый бюджет или per-file потолок между
  двумя источниками.
- **Формат «строка на файл» (критерий №3, требование 3 из description) не рендерится сервером.**
  `_search_codebase_multi` возвращает сырой `ContextPack.as_context()` — блоки чанков с
  построчной нумерацией per node, а не построчный `path:line — почему` per файл; такой формат
  сегодня получается только в финальном тексте брифа, который собирает LLM-скилл solve-task
  (по образцу секции `## Relevant code` самого этого брифа). Открытый вопрос для реализации:
  требование 3 — про сжатие payload'а тула (например, headers-only/один диапазон на файл в самом
  `search_multi`, аналог PRI-138 для search_base) или про инструкцию скиллу лучше схлопывать
  дубликаты при сборке брифа — из кода это не следует однозначно, нужно решить в брейншторме.
- **Замер офлайн-эффекта.** `eval/replay_report.md` (раздел «Приёмка PRI-255») и
  `eval/solve_task_metrics/{recall,briefs,subquery_stats,replay,replay_report}.py` — готовая
  инфраструктура: `bulk N=4` (доверительный интервал узкий, уже отмечено в отчёте PRI-255),
  `core-recall`/`bulk core-recall`/`precision`/«предсказано файлов» — те же метрики нужно снять
  до/после PRI-256 в новом разделе того же отчёта, переиспользуя пайплайн, а не копируя его.
