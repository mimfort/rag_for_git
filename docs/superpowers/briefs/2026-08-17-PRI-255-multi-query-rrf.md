# Brief — PRI-255 Multi-query по сущностям и структуре задачи с RRF-слиянием
https://ru.yougile.com/team/686c049c8af8/#PRI-255

## Task

ID-309/PRI-255: секция `code` брифа solve-task эмбеддит задачу одним запросом
(заголовок + первые 8 строк описания) — многотемный текст усредняется в вектор,
не близкий ни к одной теме, технические идентификаторы тонут, хвостовые пункты
«Что сделать» не ищутся вовсе. Сделать: (1) детерминированно извлечь подзапросы
из пунктов «Что сделать»/«Критерии приёмки» + технических идентификаторов текста
(snake_case, CamelCase, пути `/`, `.py`, имена таблиц); (2) число подзапросов
производно от размера задачи (2-3 мелкая, 10-15 развёртка, предохранитель ~20);
(3) слить выдачи RRF — файл нескольких подзапросов поднимается наверх, файл
одного всё равно попадает; (4) извлечение — чистый модуль без сети/БД.
Критерии: распределение числа подзапросов по размеру задачи (не константа);
положительная дельта bulk core-recall в replay-отчёте; хвостовой пункт находит
свои файлы на задаче-развёртке; рост Voyage-эмбеддингов не ограничение, рост
LLM-токенов недопустим.

  expand→dedupe→rerank→cliff; здесь уже есть паттерн RRF-подобного слияния

  через-константу паттерн, но НЕ обязательно должен жить в этом классе (задача
  локализована в task_context.py — см. родителя ID-307, п.6).

## Constraints / open questions

- **Жёсткая локализация (инвариант родителя ID-307 п.6/п.7):** править только
  `_TaskContextDeps.code`/`task_context.py`; `Retriever.search_base` — общий
  для `ask` и review-PR — не менять, либо менять строго за флагом, включённым
  только для solve-task. Это определяет архитектуру: multi-query, скорее всего,
  N раз зовёт существующий `search_codebase`/`search_base` с разными query и
  сливает РЕЗУЛЬТАТЫ (пути/тексты), а не патчит гибрид-SQL.
- **Voyage free tier 3 RPM / 10K TPM.** Критерий 4 явно разрешает рост числа
  эмбеддингов ("не ограничение"), но реальный лимит никуда не делся: N
  подзапросов = N `embed_query` вызовов (query, не document — LRU-кэш есть,
  512 записей, но кэш per-process и по точному тексту, разные подзапросы не
  разделяют кэш). Предохранитель ~20 подзапросов — это и защита от TPM/RPM
  троттлинга внутри одного вызова `prepare_task_context`, не только от
  вырожденного текста. Открытый вопрос: нужен ли троттлинг/пауза между
  подзапросами, или retry/backoff в `_retry.py` уже достаточен на пачке из ~20
  последовательных `embed_query`.
- **`eval` вне индекса** (`paths.ignore`) — харнесс правится только через
  Read/Glob/Bash, `search_codebase`/`callers` по нему не работают.
- **Расход LLM-токенов не должен вырасти** (критерий 4) — извлечение
  подзапросов детерминированное (без LLM), это должно остаться так;
  единственный риск роста — если секция `code` в бриф отдаёт БОЛЬШЕ текста
  из-за большего числа найденных путей (это уже частично скоуп ID-310).
- **Открытый вопрос — куда встраивать RRF-слияние технически:** на уровне
  `_TaskContextDeps.code` (зовёт `search_codebase` N раз, парсит
  `as_context`-текст regex'ом как в `extract_context_paths`, теряя объекты
  `Retrieved`/скор) — простой, но с потерей информации о score/строках; либо
  завести session-less вариант, возвращающий структурированные `Retrieved`
  до рендера (не ломая `search_codebase` для остальных вызывающих) — чище, но
  шире по площади изменений. Требует решения на брейншторме.
- **Открытый вопрос — эмбеддинг подзапроса «Что сделать» пункт vs весь query:**
  считать ли RRF по `hybrid_search` (BM25+ANN одного подзапроса) или дополнительно
  графом (`search_base` уже включает graph-expansion) — двойное расширение
  графа на N подзапросах может взорвать число кандидатов до реранка.
- **Открытый вопрос — какая baseline-цифра авторитетна для критерия 2
  («положительная дельта bulk core-recall в replay»):** родитель ID-307
  цитирует snapshot-линию PRI-249 (bulk 0.373, N=4), но актуальный
  `eval/replay_report.md` (raw-ретрив линия, тот же харнесс, что будет мерить
  PRI-255) даёт bulk 0.127/0.091 на корпусе 55 — `replay.py` docstring прямо
  предупреждает: **snapshot и replay линии несравнимы напрямую**. Дельта для
  критерия приёмки PRI-255 должна мериться `replay baseline vs replay
  multiquery` на одном и том же снимке — не против цифры 0.373 из тикета.
- **Число подзапросов зависит от размера задачи, а не от корпуса задач.**
  Тестовый корпус (`docs/superpowers/briefs/`, 56 брифов) даёт входные тексты
  для юнит-теста распределения (критерий приёмки 1), но сам НЕ хранит
  «эталонное» число подзапросов на задачу — придётся придумать эвристику с
  нуля (пункты списка + технические идентификаторы, с дедупом и capping).
