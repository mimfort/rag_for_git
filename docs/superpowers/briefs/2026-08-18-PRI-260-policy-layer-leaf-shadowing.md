# Brief — PRI-260 Слияние слоёв политики: затенение по листу вместо верхнего ключа + видимость дрейфа рабочего дерева
https://ru.yougile.com/team/686c049c8af8/#PRI-260
## Task
Два дефекта резолва `.review.yml`, найденные на приёмке PRI-259: (1) `merge` в `reviewer/config/layers.py:355-360` затирает верхний ключ целиком (не рекурсивно по mapping), из-за чего частичный домашний слой `context_limits` стирает коммиченные подсекции, о которых сам не высказывался; (2) `CommittedLayerFetcher` (`reviewer/config/committed.py`) читает `.review.yml` только из коммиченного git-блоба (`git show <ref>:...`), правки в рабочем дереве клона невидимы в `config show`, а метка `committed: local` (committed.py:23-24, 83) читается как «локальный файл», хотя означает «через git из локального клона». Нужно: рекурсивное слияние mapping-значений с точным путём в `shadowed`, предупреждение о дрейфе рабочего дерева vs коммиченного `.review.yml` в `config show`, переименование метки способа чтения, и тесты, включая регресс ровно на конфигурацию PRI-259 (коммиченный пин `code_section` + домашний слой без этой подсекции).

- Приоритет источников менять запрещено (criterion 4): порядок `home:review.yml → .review.yml (коммиченный) → home:repos/<repo>.yml` (`layers.py:446-449`) остаётся, дрейф рабочего дерева — только предупреждение, не новый источник данных для эффективной policy.
- Открытый вопрос для брейнсторминга: какие top-level ключи считаются «подсекциями» для рекурсивного слияния (mapping → рекурсия) vs «атомарными» (список/скаляр → замена целиком, как сейчас). Задача явно называет `context_limits.code_section` как пример; в схеме есть минимум ещё три mapping-подобных ключа — `categories` (`dict[str, bool]`), `task_board` (mapping с secrets-фильтрацией выше по стеку), `summary_cluster_depth_overrides` (`dict[str, int]`) — нужно решить единый критерий (вероятно: «рекурсия для любого `Mapping`, замена для `list`/скаляра» — так буквально сформулировано в п.1 «Что сделать», но тогда `categories`/`task_board`/`summary_cluster_depth_overrides` тоже начнут мержиться по ключам, что меняет их сегодняшнее поведение целиком-замены и требует отдельного regression-покрытия).
- `_simulated_repo_layer` (`layers.py:1015-1032`) — дублирует `merge` вручную для `migrate_repo_config`; при рекурсивном мерже эту копию нужно либо тоже сделать рекурсивной, либо вынести общую функцию мержа, чтобы `migrate` и `resolve_policy_data` не разошлись.
- `CommittedLayerFetcher.source` — публичный атрибут, но `_clone_root` приватный; проверка дрейфа рабочего дерева в `config show` (задача 3) либо переиспользует уже прочитанный `_clone_root` через новый публичный метод/атрибут фетчера, либо CLI повторно вызывает `validate_clone` — решить, где живёт код сравнения (в `committed.py` рядом с `CommittedLayerFetcher`, или отдельной функцией, которую зовёт только `cli.py`), учитывая, что MCP (`reviewer/mcp/service.py:1646-1696`) тоже создаёт `CommittedLayerFetcher`, но criterion 3 требует предупреждение только в `config show`.
- Метка `committed: local` переименовывается (задача 4), но `COMMITTED_UNREAD_WARNING_PREFIX`/тексты existing warnings в `layers.py` её не используют напрямую — переименование ограничено `committed.py` (`SOURCE_LOCAL`) и рендером в `cli.py:167`; проверить grep на `SOURCE_LOCAL`/`"local"` во всех потребителях (`cli.py`, `mcp/service.py`, тесты) перед переименованием, чтобы не оставить рассинхрон строкового литерала.
