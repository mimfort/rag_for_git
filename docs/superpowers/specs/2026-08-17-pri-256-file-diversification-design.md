# PRI-256 — Файловая диверсификация и файловый бюджет секции code

Бриф: `docs/superpowers/briefs/2026-08-17-PRI-256-file-diversification-code-section.md`

## Проблема

Секция `code` контекста задачи (`prepare_task_context`) отдаёт медиану 4 различных файла, тогда как
медиана ядра реального диффа — ≥8. Причина не в ранжировании, а в арифметике бюджета.

После PRI-255 секция идёт через `reviewer/retrieval/multiquery.py::search_multi`. Там единственная
отсечка — чанковая: `_dedupe_overlapping(items)[:lim.ceiling]` (`multiquery.py:157`), `ceiling=15`.
Дальше каждый блок обрезается до `MAX_BLOCK_CHARS = 2000` (`multiquery.py:29`), а весь итоговый
текст — до `max_chars = settings.max_tool_result_chars = 8000`
(`reviewer/retrieval/retriever.py:112`, `reviewer/config/settings.py:55`,
проброшено в `Retriever(max_context_chars=...)` в `reviewer/app.py:101`).

8000 ÷ 2000 = **4 блока**. Остальные 11 из 15 отобранных чанков отбрасываются срезом строки и до
сборщика брифа не доезжают. Пер-файлового потолка нет вовсе: несколько чанков одного файла
занимают слоты, которые и так почти все съедены символьным срезом.

Потолок чанков на файл сам по себе эту стену не сдвигает — нужен собственный бюджет секции.

**Устаревший premise тикета.** Описание PRI-256 указывает на cliff-отсечку в
`search_base` (`reviewer/retrieval/retriever.py:198-212`). Это место после мержа PRI-255 секцию
`code` не обслуживает: `search_base` остался путём `/ask`, грунтовки и ревью PR, а в `search_multi`
реранкера и cliff нет вовсе (финальный ранкер — RRF). Рычаг ставится в `search_multi`. Комментарий
`multiquery.py:34` («Файловые квоты и диверсификация — не здесь, это ID-310») — намеренно
оставленная PRI-255 точка расширения.

## Решение

### Отдельный бюджет секции

Новый frozen dataclass в `reviewer/policy/context_limits.py`:

```python
@dataclass(frozen=True)
class CodeSectionLimits:
    max_files: int = 12          # различных файлов в секции
    max_chunks_per_file: int = 1 # чанков на один файл
    chars_per_file: int = 1300   # доля символов на файл
```

Подключается полем `ContextLimits.code_section` и парсится в `ContextLimits.from_review_yaml` по
образцу существующих блоков — заданные ключи поверх дефолтов, env-слоя нет:

```yaml
context_limits:
  code_section:
    max_files: 12
    max_chunks_per_file: 1
    chars_per_file: 1300
```

Бюджет **отдельный от `CodebaseLimits`** намеренно: `CodebaseLimits` обслуживает публичный
`search_codebase`, `/ask` и грунтовку, где единица бюджета — чанк и потолок связан с квотой
реранкера. Единица бюджета секции `code` — файл. Смешение двух шкал в одном dataclass сделало бы
невозможной формулировку «независимый от чанкового потолка общего поиска» из тикета.

Символьный потолок секции — **производный**, не отдельный ключ:

```
section_max_chars = max_files × chars_per_file    # 12 × 1300 = 15600
```

Он передаётся в `ContextPack.max_chars` явно, вместо `retriever.max_context_chars`. Так объём
секции растёт строго линейно по числу файлов, и критерий приёмки №3 («рост числа файлов не даёт
кратного роста токенов») выполняется по построению, а не проверяется постфактум. Третьего
независимого регулятора нет — нечему рассинхронизироваться.

### Диверсификация по файлам

Новая чистая функция в `multiquery.py`:

```python
def diversify_by_file(items: list, *, max_files: int, max_chunks_per_file: int) -> list:
```

Идёт по входному порядку, ведёт счётчик на `item.path`, пропускает чанк сверх
`max_chunks_per_file` для этого пути и останавливается, набрав `max_files` различных путей.
Порядок выживших стабилен относительно входа.

Место вызова в `search_multi` — строго между дедупом и рендером:

```
runs → rrf_merge → +graph-only хвост → фильтр тестов → _dedupe_overlapping
     → diversify_by_file → cap_block(chars_per_file) → ContextPack(max_chars=section_max_chars)
```

Порядок обязателен. `_dedupe_overlapping` оставляет самый широкий чанк из вложенных
(`retriever.py:44-67`); при обратном порядке потолок «1 чанк на файл» мог бы удержать вложенный
метод и выбросить охватывающий класс, то есть ухудшить выдачу, а не улучшить.

Приоритет «сначала hybrid, потом graph-only» сохраняется — он уже закодирован порядком списка на
входе (`multiquery.py:153`), а `diversify_by_file` порядок не меняет. Внутри файла удерживается
первый по RRF-рангу чанк.

Существующая отсечка `[:lim.ceiling]` из строки 157 убирается: `max_files` × `max_chunks_per_file`
делает её недостижимой, и два потолка на одной выдаче — ровно тот случай «что именно срезало», от
которого спека отказывается выше. Второе использование `lim.ceiling` — как числа сидов
graph-expansion (`multiquery.py:153`) — остаётся: там это не бюджет выдачи, а глубина расширения.

### Область действия

Лимиты применяются ко всему, что идёт через `_search_codebase_multi`
(`reviewer/mcp/service.py:1797`) — это секции `code` и `test_exemplars` payload'а
`prepare_task_context`. Тул получает новый параметр `section_limits`; резолв политики остаётся
единственным (`self._resolve_context_limits`), параллельной ветки чтения `.review.yml` не заводится.

`MAX_BLOCK_CHARS = 2000` как модульная константа удаляется — её роль занимает
`chars_per_file` из политики. `cap_block` сохраняет сигнатуру с явным аргументом.

### Что не меняется

- `Retriever.search_base`, `Retriever.retrieve`, публичный MCP-тул `search_codebase` — ни поведение,
  ни лимиты. Контракт публичных тулов не меняется: `prepare_task_context` по-прежнему отдаёт
  секции строкой.
- `RRF_K = 60` и его три независимых объявления (`multiquery.py`, SQL в `index/store.py`,
  `tasks/store.py`) — известный долг, вне скоупа; четвёртой копии не появляется.
- `build_subqueries` / `MAX_SUBQUERIES` — источник кандидатов не трогается.
- `ContextPack.as_context` — механика среза не меняется, меняется только передаваемый ей бюджет.

## Замер приёмки

Критерии 1 и 2 требуют цифр, снятых отдельно по этому рычагу. Прогон — существующим пайплайном
`eval/solve_task_metrics/replay.py` на том же `indexed_sha`, новым разделом «Приёмка PRI-256» в
`eval/replay_report.md`. Снимаются: медиана числа различных файлов секции `code`, медиана
core-recall, bulk core-recall, precision.

**Baseline — 4 файла**, из раздела «Приёмка PRI-255» того же отчёта. Цифра «5-6», названная в
описании тикета, ни одним найденным отчётом не подтверждается и, судя по всему, предшествует
замеру PRI-255; источником истины берётся зафиксированный замер на текущем коде. Расхождение
называется в разделе отчёта явно, чтобы приёмка не сверялась с двумя разными линейками.

Ожидаемое падение precision (PRI-255 дал 0.875 → 0.5 при росте 2 → 4 файла) — цена, заложенная
родительской задачей ID-307: бриф оптимизируется по recall ядра, лишний файл в секции стоит одной
строки, пропущенный — потерянного контекста.

## Тесты

`tests/retrieval/test_multiquery.py` (фейковые `Store`/`Embedder`, без сети, по образцу
`test_blocks_are_capped_before_render:193`):
- `diversify_by_file` удерживает не более `max_chunks_per_file` чанков одного пути;
- не более `max_files` различных путей;
- порядок выживших стабилен, hybrid раньше graph-only;
- диверсификация идёт после дедупа: вложенный метод не вытесняет охватывающий класс;
- итоговый `as_context` не содержит `[...truncated]` при полном наборе файлов —
  производный бюджет обязан вмещать то, что отобрано;
- вырожденные значения (`max_files=0`, один файл на всю выдачу) не роняют сборку.

`tests/policy/test_context_limits.py` — `from_review_yaml` читает `context_limits.code_section`,
отсутствующие ключи дают дефолты, пустой блок эквивалентен отсутствию.

Guard: `search_base` и публичный `search_codebase` не изменили поведения — существующие тесты
`tests/retrieval/test_search_base.py` должны пройти без правок.
