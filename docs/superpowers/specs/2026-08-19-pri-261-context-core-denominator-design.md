# PRI-261 — Знаменатель контекста для метрики брифа: контекстное ядро из графа

Дата: 2026-08-19. Задача: PRI-261 (стор ID-315). Бриф:
`docs/superpowers/briefs/2026-08-19-PRI-261-context-core-denominator.md`.

## Проблема

Знаменатель `core-recall` — только файлы, изменённые настоящими PR-мержами задачи. Файл,
который надо ПРОЧИТАТЬ, но не менять (контракт, соседний адаптер, образец для нового кода),
в знаменатель не входит: recall его не штрафует, precision — штрафует. Отсюда систематически
заниженная precision (в приёмке PRI-259 её пришлось объявить смещённым индикатором) и полное
отсутствие обратной связи у половины бюджета секции `code`.

## Спайк: контекстное ядро выводимо, но только из diff-скоупных сидов

Замер на 8 задачах (`dev`, `indexed_sha 308b86b`, всего core-файлов в репо — 152), медиана
числа НОВЫХ core-файлов (сверх изменённых задачей):

| сиды | обход | медиана |
|---|---|---|
| все символы изменённых файлов | ненаправленный 1 хоп | 60 |
| все символы изменённых файлов | направленный `CALLS`, 1 хоп | 57 (37 % репозитория) |
| **только затронутые диффом символы** | **направленный `CALLS`, 1 хоп** | **14.5** |
| только затронутые диффом символы | направленный `CALLS`, 2 хопа | 31 |
| только затронутые диффом символы | входящие `CALLS`, 1 хоп | 3 |

Вывод, который определяет всю задачу: **решает сидирование, а не глубина обхода.** Сидирование
всеми символами изменённого файла (150–300 символов на задачу) даёт 57 файлов — тот самый
«мусорный» исход, при котором задача закрывается отрицательным результатом. Сидирование только
затронутыми диффом символами даёт 14.5 на том же графе и той же глубине — вчетверо меньше.
Прецедент PRI-257 воспроизвёлся буквально: нулевой/мусорный результат оказался механикой, а не
свойством сигнала, и проверять механику до вердикта обязательно.

Для масштаба: медиана сегодняшнего знаменателя `core-recall` — 5–9 файлов; контекстное ядро в
14.5 утраивает его, но не размывает до размеров репозитория.

`IMPLEMENTS` на всех восьми задачах дал 0. Это не дефект: рёбер `IMPLEMENTS` в графе 141 против
19 166 `CALLS`, направление `наследник → база` корректно, а все восемь задач выборки —
метрико-эвальные, без наследования в затронутых символах. Ребро остаётся в обходе: оно ничего
не стоит и покрывает ровно тот случай, ради которого задача заведена (соседний адаптер досок).

## Решение

### 1. Расположение кода: чистое ядро отдельно от ввода-вывода

`reviewer/metrics/brief_quality/` документирован как чистый — без ввода-вывода, git и БД, — и
именно эта чистота есть гарантия того, что офлайн и онлайн меряют одной линейкой (критерий 7).
Обход графа — ввод-вывод. Поэтому вывод ядра разделяется так же, как `ground_truth.py` уже
разделён над git через инъекцию `GitRunner`:

- **Чистая часть** — новый `reviewer/metrics/brief_quality/context_core.py`: принимает
  множество сид-символов и ИНЪЕКТИРУЕМЫЙ callable обхода, возвращает множество путей
  контекстного ядра (политика хопов, фильтр `is_core_production_path`, вычитание уже
  изменённого ядра). Тестируется без Neo4j.
- **Грязная часть** — в `eval/solve_task_metrics/`: Cypher-запрос к Neo4j, поиск чанков в
  Postgres, разбор hunk-диапазонов git. Инъектируется внутрь чистой части.

`eval/solve_task_metrics/context_core.py` — ре-экспорт; существующий guard-тест на вторую копию
остаётся зелёным.

### 2. Вывод сидов

По задаче: настоящие PR-мержи (существующий `ground_truth.collect`) → `git diff --unified=0`
между `sha^1` и `sha`, hunk-диапазоны ПРАВОЙ стороны, только по core-путям → чанки `base:dev`,
чей `[start_line, end_line]` пересекается с диапазоном → их `path#symbol_fqn` как сид-символы.
Затем один хоп: исходящие `CALLS` ∪ исходящие `IMPLEMENTS`. Результат минус изменённое ядро =
контекстное ядро.

### 3. Форма метрики: аддитивно, старые числа не двигаются

`evaluate_task` получает необязательный параметр `context_core: set | None = None`. Без него
поведение тождественно сегодняшнему — это и есть механизм, которым онлайн-путь и числа приёмок
PRI-255…259 остаются нетронутыми (критерий 3).

Новые поля `TaskQuality`: `context_core`, `hit_context`, `context_recall`, `union_precision`.
`context_recall` равен `None` при пустом контекстном знаменателе, со своим статусом
`empty_context_denominator` по образцу `empty_core_denominator`: неопределённость не есть ноль
(критерий 4). `precision` сохраняет текущий смысл; `union_precision` считается по
объединённому знаменателю `изменённое ядро ∪ контекстное ядро` — файл, который надо было
прочитать, перестаёт считаться шумом, а старое число остаётся рядом для сравнимости с прошлыми
приёмками. `aggregate` получает соответствующие медианы и собственный счётчик
`no_context_measurement`.

Потребители аддитивных полей: `eval/solve_task_metrics/{replay,snapshot,report,replay_report,
history,forecast}.py` — строки отчётов расширяются колонками, старые строки истории читаются
по-прежнему.

### 4. Замер и вопрос глубины

Прогон корпуса на 20×975 даёт базовую точку `context-recall`, затем три точки глубины
20×780 / 20×975 / 20×1300 на одном `indexed_sha`.

Отчёт называет ПЕРВЫМ доказательство уровня кода, а не результат замера. В
`reviewer/retrieval/multiquery.py:274-292` набор путей фиксирует `diversify_by_file`, читающий
только `max_files` и `max_chunks_per_file`; `chars_per_file` применяется ПОСЛЕ, в `cap_block`,
к тексту уже отобранных блоков. Заголовок блока `// node_id (path:start-end)` — первая строка
блока, обрезка его не удаляет, поэтому `extract_context_paths` возвращает ТОЖДЕСТВЕННОЕ
множество путей на всех трёх точках **по построению**. Три совпавших числа — подтверждение
доказательства, а не открытие.

Отсюда ответ на критерий 5: новая метрика глубину не различает, и НИКАКАЯ метрика, считающая
пути, различать её не может — смена знаменателя эту слепоту не лечит. Следствие для пункта 6 задачи (судьба пола глубины): пол `chars_per_file >= 975` остаётся инженерным решением, но
теперь он задокументирован как **принципиально неизмеримый данным классом метрики**, а не
просто неизмеренный. Дефолты `CodeSectionLimits` не меняются: различимой дельты нет и быть не
может.

### 5. Онлайн-запись: офлайн-only, выбор назван явно

Критерий 6 требует явного выбора — он сделан в пользу офлайн-only. Расчётное ядро живёт в
`reviewer/metrics/brief_quality/` (критерий 7), но зовёт его только эвал-харнесс. Ни миграции,
ни новых колонок в `brief_quality`. Основания: онлайн-точка «до» — `bulk_n_measured = 4`,
слишком тонкая, чтобы новая колонка успела набрать данные к приёмке; а обход графа добавил бы
Neo4j-round-trip к каждому `publish_review` ради числа, которого пока некому читать. Старые
строки читаются по-прежнему, потому что схема не трогается вовсе.

## Оговорки, которые обязаны попасть в отчёт

1. **`typing.Protocol` рёбер не даёт** — структурная типизация не выражается рёбрами ни при
   каком бэкенде (тот же факт, что делает `family` отдельным от `implementations`). Контракт
   вроде `TaskBoardProvider` в контекстное ядро через `IMPLEMENTS` не попадёт никогда.
2. **Импорт — не ребро.** Формулировка задачи говорит «вызывает или импортирует»; граф знает
   только вызовы. Файл, из которого символ импортирован, но не вызван, в ядро не войдёт.
3. **Обход идёт по СЕГОДНЯШНЕМУ графу** (`indexed_sha 308b86b`), а не по состоянию репозитория
   на момент каждой исторической задачи. Для задачи, чей код позже отрефакторили, сид-символ
   может не существовать. Это ретроспективная оговорка метрики, а не дефект.

## Критерии приёмки

1. Контекстное ядро выводится детерминированно из графа на заданном `indexed_sha` и
   воспроизводится на исторических задачах корпуса.
2. Спайк зафиксировал числом размер ядра (таблица выше) и подтверждён ручной сверкой на 5–10
   задачах корпуса.
3. `context-recall` считается РЯДОМ с `core-recall`; числа приёмок PRI-255…259 не требуют
   пересчёта.
4. Пустой контекстный знаменатель даёт статус `empty_context_denominator` и `None`, не ноль.
5. Замер прогнан на трёх точках глубины на одном `indexed_sha`; отчёт отвечает числом и
   доказательством уровня кода на вопрос «различает ли метрика глубину».
6. Онлайн-запись `brief_quality` не меняется; выбор «офлайн-only» назван явно в спеке и отчёте.
7. Расчётное ядро одно на офлайн и онлайн; `eval/solve_task_metrics/` — ре-экспорт; guard-тест
   зелёный.

## Вне скоупа

Менять секции брифа кроме измерения; менять дефолты `CodeSectionLimits`; пере-гонять снятые
рычаги (co-change, разворот кластеров `subsystems`); метрика по СОДЕРЖИМОМУ блока — она и
только она ответила бы на вопрос глубины, и это отдельная задача.
