# PRI-235 — коммиченный `.review.yml` из локального клона в `config show` и MCP

Бриф: `docs/superpowers/briefs/2026-08-11-PRI-235-local-committed-policy-layer.md`

## Проблема

Коммиченный слой политики читается тремя разными способами. `reviewer index` берёт его локально
(`file_at_ref` → `git show <ref>:.review.yml`), а `config show` и MCP `_resolve_policy` идут за тем
же файлом в API хостинга (`vcs.get_file_at_ref`) — при том, что клон обычно лежит рядом. Следствия:
лишний сетевой вызов в диагностике, зависимость от токена/сети там, где она не нужна, и полная
недостижимость коммиченного слоя для репозитория без рабочего remote.

## Решение

### 1. Один фетчер с локальным приоритетом

`reviewer/config/committed.py::CommittedLayerFetcher` — вызываемый объект с сигнатурой
`resolve_policy_data`-фетчера (`(ref) -> str | None`), который:

- при валидном клоне читает `file_at_ref(root, ".review.yml", ref)` и ставит `source = "local"`;
- иначе (клона нет / он не подходит / локальное чтение сорвалось) делегирует VCS-фетчеру и ставит
  `source = "vcs"`;
- при отсутствии обоих источников поднимает `CommittedLayerUnavailable`, который `resolve_policy_data`
  уже обрабатывает fail-soft-механизмом `skipped` (PRI-234).

VCS-фетчер инъектируется **лениво** (`Callable[[], fetcher]`): при живом клоне VCS-провайдер не
создаётся вовсе — иначе экономия сетевого вызова обнулилась бы созданием клиента.

### 2. Валидация клона

`validate_clone(path, repo)` → корень клона или `None`:

- путь существует и является git-репозиторием (`repo_root`); используется именно корень, поэтому
  указание подкаталога допустимо;
- если у клона есть распознаваемый remote — его `owner/name` обязан совпасть с целевым repo
  (защита от устаревшего пути в БД, указывающего на чужой клон);
- **remote отсутствует или не распознан → клон принимается**: именно этот случай задача и лечит.

Отдельно валидируется ref: `rev_parse(root, ref)` обязан пройти ДО чтения. Без этой проверки
неразличимы «файла нет на ref» (легитимный `None` от `file_at_ref`) и «ref не выкачан в клоне» —
второе обязано уводить в VCS-фолбэк, а не молча обнулять слой.

### 3. Откуда MCP знает путь к клону

Новая таблица `repo_clone(repo PK, path, updated_at)` — прямой аналог `repo_vcs` (PRI-133):
`reviewer index` уже выполняется из клона и рядом пишет `set_repo_vcs`; там же пишется и
`set_repo_clone(repo_id, <абсолютный корень>)`. MCP-сервис читает её в `_resolve_policy`
(fail-soft: нет таблицы / Postgres недоступен → `None` → прежнее поведение через VCS).

Путь из БД никогда не доверяется на слово: MCP-сервер может работать не на той машине, где
индексировали, поэтому каждый путь проходит `validate_clone` перед использованием.

### 4. Порядок кандидатов в `config show`

`--path` (явный) → `repo_clone` из стора → текущий рабочий каталог. Каждый кандидат проходит
`validate_clone`, первый валидный побеждает. Автодетект по cwd безопасен ровно потому, что чужой
клон отсекается сверкой remote.

### 5. Отчёт

`build_config_report` получает поле `committed_source`: `"local"`, `"vcs"` или `null` (слой не
читался — например, резолв упал раньше). Печатается строкой `committed: <источник>`; в JSON — тем же
ключом. Путь к клону в отчёт **не** попадает: диагностике достаточно способа чтения, а путь — лишняя
информация о машине.

## Границы

- Кэш/инвалидация локального чтения не вводятся: `git show` дешёвый, а состояние клона меняется вне
  процесса.
- `reviewer index` не трогается по существу (он уже локальный) — только пишет `repo_clone`.
- `strict_committed` остаётся как есть: PRI-235 меняет источник слоя, а не строгость его отсутствия.

## Тесты

1. `validate_clone`: принимает клон без remote; отвергает клон с чужим remote; принимает подкаталог.
2. `CommittedLayerFetcher`: при валидном клоне VCS не вызывается вовсе (ленивая фабрика не
   дёргается), `source == "local"`; при невалидном — `source == "vcs"`; при нерезолвимом ref —
   фолбэк на VCS; без обоих источников — `CommittedLayerUnavailable`.
3. `store`: `set_repo_clone`/`get_repo_clone` round-trip (integration, как у `repo_vcs`).
4. `config show`: с доступным клоном не делает ни одного VCS-вызова и печатает `committed: local`;
   без клона — прежний путь и `committed: vcs`.
5. MCP `_resolve_policy`: при валидном пути из стора VCS-фабрика не вызывается; при пустом сторе
   поведение прежнее.
