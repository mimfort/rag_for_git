# PRI-146 — спека solution brief + жёсткий relevance-фильтр в solve-task

**Задача:** ID-146 / PRI-146 (оценка S). Зафиксировать формат и объём «solution brief», а
также жёсткий relevance-фильтр в `plugin/skills/solve-task/SKILL.md` (шаги 3–4), чтобы хендофф в
`brainstorming` был компактным и не терял деталей.

**Критерий приёмки (с доски):** brief компактен и структурирован; нерелевантное отсеивается с
указанием числа dropped; контекст для brainstorming не переполняется.

## Контекст и мотивация

Текущий шаг 4 («Distill the solution brief») задаёт лишь список секций, без объёма, без колпаков и
без конкретики relevance-фильтра. Brief может раздуться (10 похожих задач + все их PR) либо потерять
детали — качество хендоффа страдает в обе стороны.

Два сигнала релевантности, доступных скилу, **асимметричны** (проверено по коду):

- `search_tasks` возвращает per-result `score` — это **RRF**, `SUM(1.0/(60+rank))` по спискам
  BM25 и ANN (`reviewer/tasks/store.py:182-189`). Значения ранговые, ограничены ≈[0.016, 0.033]
  (top в обоих списках ≈ 0.03, в одном ≈ 0.02) и **несопоставимы между запросами**. Абсолютный
  порог (например 0.5) бессмыслен.
- `search_codebase` (после PR #23 / PRI-138) возвращает дедуплицированные, line-numbered, test-free
  сниппеты с заголовком `path#fqn (path:start-end)`, **без числового score** в выдаче — только
  порядок выдачи.

Вывод: фильтр строится на **ранге + бинарном суждении о прямой релевантности**, а score/rank
используется лишь как порядок рассмотрения и тай-брейк на границе колпака — не как числовой гейт.

## Объём изменений

- `plugin/skills/solve-task/SKILL.md` — шаги 3–4 (+ связующие строки). Шаг 0 (Preflight) и
  include-маркеры (`<!-- include: _common/tool-usage.md -->`, `_common/branch-selection.md`) **не
  трогаем** — guard-тесты `test_preflight_guardrail.py` / `test_assembled_prompts.py` остаются
  зелёными.
- `tests/skills/` — новый тонкий guard-тест на маркеры спеки.

Markdown-guidance; поведенческого кода нет.

## Дизайн

### Шаг 4 — relevance-фильтр

1. **Порядок по рангу** выдачи `search_tasks` (rank/score) и `search_codebase` (rank). Абсолютных
   порогов по score нет (RRF, k=60 — ранговый, несопоставим между запросами).
2. **Колпаки-потолки:** ≤3 related tasks · ≤5 файлов/символов. Это потолки, а не квоты — брать
   меньше, если хватает. Граф (`related_symbols`/`callers`/`definition`) разворачиваем только для
   немногих центральных символов.
3. **Keep/drop = бинарное правило «directly informs implementation» + колпак.** Score/rank задаёт
   только порядок рассмотрения и тай-брейк на границе колпака, не числовой гейт.
4. **Правило «directly informs» с примерами:**
   - ✅ INCLUDE: символ/файл, который будешь править или брать за образец; задача, чей PR показывает
     конкретный паттерн для повторения; ограничение, сужающее подход.
   - ❌ EXCLUDE: задача из той же области, но с другим механизмом; файл из выдачи, который не
     трогаешь и не копируешь; фон, по которому не будешь действовать.
5. **Dropped-count** хвостом на секциях Related work и Relevant code: `(отсеяно N: краткая
   причина)`.
6. **Ленивый `get_pr_diff` гейтится фильтром:** diff тянем только для задач, переживших top-3 +
   правило релевантности (экономия внешних вызовов).

### Шаг 4 — скелет-шаблон и бюджеты

В шаг 4 добавляем компактный fenced-скелет с подписями «что идёт в секцию» и бюджетами:

```
# Brief — <KEY> <title>
## Task — key/title/requirements/criteria (или формулировка юзера в board-less). До ~6 строк.
## Related work — ≤3 задач, 1 строка каждая: «KEY — что переиспользовать/за чем следовать». (отсеяно N: …)
## Relevant code — ≤5 файлов/символов, 1 строка: «path:line — зачем» (+ blast radius из графа). (отсеяно N: …)
## Constraints / open questions — терсные буллеты: лимиты, неизвестное, пробелы контекста.
```

Бюджет: один элемент = одна строка. Цитаты `path:line` берём напрямую из line-numbered сниппетов
шага 3 — без повторного Read (согласовано с контрактом PR #23 / PRI-138).

### Шаг 3 — связующие строки

- Одна фраза: сигналы для фильтра шага 4 — ранг/score `search_tasks` и ранг `search_codebase`;
  абсолютный score порогом не является.
- Явная привязка гейтинга ленивого PR-diff (п. 6) к прохождению фильтра.

### Guard-тест (`tests/skills/`)

Тонкий тест ассертит, что спека на месте в `solve-task/SKILL.md`: колпак Related work (≤3), маркер
`отсеяно`/dropped, наличие скелета brief. Цель — чтобы будущая правка не удалила спеку молча. В духе
существующих guard-тестов репозитория (PRI-141, PRI-142).

## Верификация

- Визуальная вычитка SKILL.md; include-маркеры целы.
- Worked-проверка скелета на брифе PRI-146, собранном в сессии (он почти конформен; единственное
