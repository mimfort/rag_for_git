# configure-review подсказывает context_limits под конкретный репозиторий

- **Задача:** свободная формулировка (board-less) — «научить `reviewer_configure-review`
  рекомендовать per-repo значения блока `context_limits` вместо голых дефолтов»
- **Дата:** 2026-07-01
- **Статус:** дизайн утверждён на brainstorming, готов к плану
- **Бриф:** `docs/superpowers/briefs/2026-07-01-configure-review-suggest-context-limits.md`
- **Связь:** PRI-202 (движок адаптивных лимитов — сделан), PRI-168 (сам скилл configure-review),
  PRI-166 (эвристика cluster depth — шаблон, к которому пристраивается классификация профиля)

## Проблема

PRI-202 сделал блок `context_limits` в `.review.yml` конфигурируемым (search_codebase /
search_tasks / graph), но скилл `reviewer_configure-review` его не трогает: тюнит только
`summary_cluster_depth`/overrides/`summary_topk_threshold`/`paths.ignore`. Репозиторий получает
голые дефолт-константы из кода, даже если он монорепа (где `ceiling=15` клипает широкие таски) или
крошечная утилита (где `candidate_pool=30` зря жжёт Voyage). Ручки есть — но никто не подсказывает,
какие значения поставить.

## Цель

Скилл классифицирует репозиторий в **профиль** по измеримым git-сигналам и предлагает **полный
документированный блок `context_limits`** — как черновик, который пользователь правит в диалоге
(поток скилла: draft → правки → merge-запись). Числа объяснимы и согласованны, а не 10 независимых
догадок.

## Ключевые решения (утверждены на brainstorming)

1. **Все ручки в блоке присутствуют** (search_codebase ×6, search_tasks ×2, graph ×2) — но
   производятся не независимыми формулами, а **профилями-пресетами**: профиль = готовый бандл всех
   значений. Объяснимо и согласованно.
2. **Форма — профили-пресеты**, не поформульный расчёт каждой ручки и не гибрид. Пресет —
   когерентный бандл; отдельные «формулы» для score-shape ручек были бы выдумкой (нет сигнала).
3. **`search_tasks.{floor,ceiling}` — из размера доски проекта**, ортогонально профилю репо.
   Размер берётся **best-effort из нашего графа задач** новым read-only тулом `count_tasks(project)`
   (COUNT по `:Task`, без похода на доску); **вопрос пользователю — только фолбэк**, когда reviewer
   MCP не подключён / тула нет (старый деплой) / граф пуст (корпус не синкали). Так скилл не
   заставляет оценивать то, что система может знать, но и не ломается на git-only-сетапе.
4. **Скилл всегда пишет полный документированный блок** выбранного профиля (даже для `standard`,
   где значения == дефолты). Конфиг самодокументируемый, в стиле корневого `.review.yml` этого репо.
5. **Честность по силе сигнала.** Масштаб-driven ручки (`ceiling`/`candidate_pool`/`callers_topk`)
   двигаются уверенно; score-shape (`ratio`/`abs_floor`/`ann_distance_max`) почти дефолт, с лёгким
   направленным нуджем и комментарием «directional, weak — подстрой, понаблюдав cliff-заметки»;
   `graph.hops` всегда 1 (рост до 2 взрывает стоимость).
6. **`context_limits` НЕ требует реиндекса/пересборки сводок** — читается live server-side
   (`_resolve_context_limits`) на ревью/solve-task. Скилл это явно сообщает (в отличие от
   `cluster_depth`/`ignore`, которые требуют rebuild).

## Классификатор профиля (только git-сигналы)

Ось — **масштаб + структура** (churn НЕ используется: он правит cluster depth, не ширину ретрива).
Сигналы уже считаются существующими шагами 2–3 скилла (`git ls-tree`, скан по префиксам):

- `N` = число трекаемых `.py` файлов;
- `pkgs` = число крупных top-level пакетов (крупный ≈ > 50 `.py`; моно-сигнал: несколько
  независимых корней вида `services/*`, `packages/*`).

| Профиль | Условие | Смысл |
|---|---|---|
| **tiny-util** | `N < 80` и один пакет | узкий контекст, экономия Voyage |
| **standard** (дефолт) | `80 ≤ N ≤ 800` | == дефолт-константы кода |
| **large / monorepo** | `N > 800` **или** `pkgs ≥ 3` крупных | шире рельса, чтобы не клипать большие таски |

Границы эвристические; скилл показывает `N`/`pkgs` и обоснование, пользователь правит.

## Бандлы значений (полный блок на профиль)

```
                    floor ceiling ratio abs_floor pool  ann   | graph.hops callers_topk
tiny-util             3     8     0.60   0.35     20   0.65   |    1          20
standard (=деф.)      4    15     0.50   0.30     30   0.65   |    1          25
large / monorepo      4    25     0.45   0.30     40   0.60   |    1          30
```

- **Масштаб-driven (сильный сигнал):** `ceiling`, `candidate_pool`, `callers_topk`.
- **Score-shape (слабый сигнал):** `ratio`/`abs_floor`/`ann_distance_max` — почти дефолт; нудж
  направленный (tiny строже, large шире контекст / экономнее Voyage), помечается комментарием.
- **`graph.hops` = 1** во всех профилях.

Значения совпадают с семантикой `reviewer/policy/context_limits.py` (дефолт `standard`).

## search_tasks — из размера доски (ортогонально профилю репо)

Размер доски проекта bucket'ится в `floor`/`ceiling`:

| Доска | Условие | floor / ceiling |
|---|---|---|
| малая | < 150 задач | 3 / 8 |
| средняя | 150–800 | 3 / 10 |
| большая | 800+ / 2000+ | 4 / 14 |

**Источник числа задач (best-effort, с фолбэком):**
1. Скилл вызывает `count_tasks(project)` (новый read-only MCP-тул, см. ниже). Успех и `count > 0` →
   bucket по таблице, без вопроса пользователю.
2. reviewer MCP не подключён / тула нет (деплой старше скилла) / `count == 0` (корпус не синкали) →
   **фолбэк:** скилл спрашивает размер доски (малая/средняя/большая) и bucket'ит по ответу.

`search_tasks` берётся отсюда; весь остальной блок — из профиля репо. Чистое разделение сигналов.
Точность не критична — нужен лишь bucket, поэтому стабы-`:Task` от кросс-проектных линков (у них нет
`project`) в счёт не попадают и не важны.

## Серверный тул `count_tasks(project)` (новый, read-only)

Единственное серверное изменение работы. Тонкий тул в `reviewer/mcp/service.py` +
`reviewer/entrypoints/mcp_server.py`, поверх метода графа (рядом с `all_keys`,
`reviewer/tasks/graph.py:153`):

- **Cypher:** `MATCH (t:Task) WHERE ($project = '' OR t.project = $project) RETURN count(t) AS n` —
  считает синкнутые задачи проекта (у стабов `project` не задан → они выпадают). Пустой `project` =
  все задачи (глобально), как в остальных тулах (PRI-170).
- **Возврат:** `{"count": int}` (или просто `int`). Read-only, без побочек, без похода на доску.
- **Fail-soft:** Neo4j недоступен → `{"count": 0}` + лог-warning; скилл трактует как «нет данных» и
  уходит в фолбэк-вопрос.

## Изменения в `plugin/skills/configure-review/SKILL.md`

1. **Frontmatter `description`** (строка 2) — дописать `context_limits (retrieval breadth per repo
   profile)` в список настраиваемых ключей (триггер на «настрой лимиты контекста»).
2. **Scope** (строки 19–31) — добавить `context_limits` в перечень редактируемых ключей (иначе
   правило шага 7 «never clobber outside scope» запретит его писать).
3. **Новый шаг 5c «`context_limits` via repo profile»** (после 5b):
   - классифицировать профиль из скана структуры шага 2 (`N`, `pkgs`);
   - размер доски → `search_tasks`: сперва `count_tasks(project)` (fail-open); при недоступности/0 —
     спросить пользователя (малая/средняя/большая);
   - собрать полный документированный блок профиля (стиль — корневой `.review.yml`);
   - пометить score-shape ручки комментарием «directional, weak signal».
4. **Шаг 6 (present draft + diff)** — обосновать классификацию: назвать `N`, `pkgs`, размер доски,
   почему этот профиль.
5. **Шаг 8 (suggest rebuild)** — явно: `context_limits` **не требует** реиндекса/resummarize;
   читается live server-side; эффект — на следующем прогоне с ветки, куда закоммичен файл.
6. **Merge-запись** (шаг 7) — блок пишется по правилам «preserve every other key + комментарии»,
   идемпотентно (повторный прогон → минимальный diff).

Таблица профилей — **инлайн в SKILL.md** (скилл single-file, референс-папки нет; компактная таблица
не тянет на отдельный файл — YAGNI).

## Границы скоупа

**В скоупе:** эвристики `context_limits` в configure-review (профиль→бандл); best-effort авто-замер
размера доски новым read-only тулом `count_tasks(project)` + фолбэк-вопрос; полный merge-блок; нюанс
«no reindex»; тесты выше; инлайн-таблица профилей.

**Вне скоупа (явно):**
- Движок retrieval/cliff/ANN-префильтр — сделан в PRI-202, не трогаем.
- env-слой конфига `context_limits` — его нет by design (только `.review.yml`).
- Автозамер плотности чанков из БД — скилл её не мерит; профиль из git-структуры.
- Поформульный расчёт каждой ручки — отвергнут в пользу пресетов.
- churn как сигнал профиля — не используется (правит cluster depth, не ширину ретрива).

## Обратная совместимость

- Отсутствие блока `context_limits` в `.review.yml` → дефолт-константы (нынешнее поведение). Скилл
  теперь пишет блок всегда, но для `standard`-профиля значения == дефолты (поведение не меняется).
- **Standalone-baseline сохраняется**: ядро скилла — git + правка файла. `count_tasks` —
  **опциональный** best-effort вызов; его отсутствие (нет reviewer MCP / старый деплой / пустой граф)
  деградирует в фолбэк-вопрос, скилл по-прежнему работает на git-only-сетапе и на свежем репо.
- Новый тул `count_tasks` — аддитивный read-only; старые деплои без него не ломаются (fail-open).
- Изменение `context_limits` не требует rebuild — эффект live server-side.
