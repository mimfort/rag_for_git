# PRI-247 — клиентская половина учёта расхода ревью (usage / total_cost / review_steps)

Собрано из брифа `docs/superpowers/briefs/2026-08-15-PRI-247-client-half-review-cost-accounting.md`.

## Проблема

Серверная половина PRI-209 работает: `publish_review` принимает `model`, `usage`, `total_cost`,
`steps`, `started_at`, кладёт их в `_RunMetadata` и пишет через `ReviewHistory.record_run` в
`review_runs`/`review_steps`. Схема БД полная — `review_steps` уже имеет
`stage`/`unit`/`seq`/`kind`/`name`/`text`/`tool_calls`/`tokens`/`cost`.

Клиент эти поля не отдаёт. Замер на живой базе (прогоны 72–77, `dev`, 2026-08-15):

| run | model | usage | total_cost | review_steps |
|---|---|---|---|---|
| 77 | `claude-opus-5` | NULL | NULL | 0 |
| 76 | `claude-code` | NULL | NULL | 5 (только клиентские имена стадий, `stage`/`kind` пустые) |
| 75 | `claude-code` | NULL | NULL | 3 (серверные `tool_call`) |
| 72–74 | `claude-code` | NULL | NULL | 0 |

`usage` хранится как JSONB-литерал `null` — SQL-предикат `usage IS NULL` даёт false, а значение
пустое; любой аудит поля обязан смотреть на содержимое, а не на `IS NULL`.

Следствие: админка показывает `total_cost = 0` по всем реальным прогонам, стоимость ревью
неизмерима, а `review_steps` описывает только те тул-вызовы, что сделал сам оркестратор —
работа субагентов в счёт не попадает.

## Ограничения, из которых растёт дизайн

- **Хуки исполняются системным `python3`**, где пакет `reviewer` не установлен. Любой код хука —
  stdlib-only и self-contained, как `reviewer_defect.py`. Импорт из `reviewer/` запрещён.
- **Сбой хука не должен ломать ревью.** Публикация обязана проходить и без sidecar; поля расхода
  тогда остаются пустыми.
- **Расход считает клиент, шаги считает сервер.** Токены тратятся в CLI, сервер их не видит;
  наоборот, тул-вызовы видит только сервер. Это два независимых канала с разными режимами отказа,
  и смешивать их в один механизм нельзя.

## Архитектура

### 1. Общий модуль агрегации транскрипта

Новый `plugin/hooks/_transcript.py` — stdlib-only, без импортов из `reviewer/`:

- `read_jsonl(path)` — чтение транскрипта;
- `aggregate_usage(lines, start_idx)` — 4 бакета (`fresh_in`/`output`/`cache_write`/`cache_read`)
  по модели, с разделением main / sidechain;
- `find_window_start(lines, skill_marker)` — индекс последнего user-сообщения с маркерами скилла,
  параметризованный по маркеру (сейчас в `brief_cost.py` он захардкожен на `skills/solve-task`);
- `resolve_transcript(payload)` — путь к транскрипту: `payload["transcript_path"]`, иначе
  реконструкция по `session_id` в `~/.claude/projects/<slug>/<session_id>.jsonl`;
- `weigh(buckets)` — взвешивание бакетов (см. §4).

`brief_cost.py` становится потребителем модуля. Его наблюдаемое поведение для solve-task не
меняется ни на символ: тот же блок, тот же `HEADER`, те же числа. Существующие тесты
`tests/hooks/test_brief_cost.py` остаются зелёными без правок — это и есть критерий выноса.

Второй существующий потребитель формата блока токенов —
`reviewer/metrics/brief_quality/briefs.py::parse_token_block` — живёт на серверной стороне и
читает уже отрендеренный markdown. Он в вынос не входит: общий модуль нужен хукам, а не серверу.

### 2. Хук съёма расхода: `PreToolUse` на `publish_review`

Событие — именно `PreToolUse`. `PostToolUse` опаздывает: к моменту его срабатывания
`publish_review` уже записал историю, и метаданные некуда положить.

Регистрация в `plugin/hooks/hooks.json` — новая секция `PreToolUse` с матчером на оба префикса
имён тула (`mcp__reviewer__publish_review|mcp__plugin_rag-reviewer_reviewer__publish_review`),
по образцу `reviewer_defect.py`.

**Транскрипт.** `resolve_transcript` даёт путь либо из payload, либо по `session_id`. Второй путь
снимает риск того, что `PreToolUse` не получает `transcript_path`: вопрос спайка (шаг 1 задачи)
перестаёт гейтить реализацию, потому что фолбэк покрывает оба исхода. Оба пути покрываются
юнит-тестами; какой из них сработал — пишется в sidecar полем `transcript_source`
(`payload` | `session_id`), чтобы ответ спайка читался из данных первого же живого прогона.

**Окно замера.** От вызова `prepare_review` для этого же `(repo, pr)` — последний assistant-ход с
`tool_use`, чьё имя оканчивается на `prepare_review`, а аргументы совпадают по repo/pr. Это
точнее маркера скилла и переживает два ревью в одной сессии. Фолбэк, если такой ход не найден
(ревью запущено не скиллом, транскрипт обрезан): `find_window_start(lines, "skills/review-pr")`.
Не найдено ничего — sidecar не пишется, публикация идёт как сейчас.

**Раскладка по стадиям.** Sidechain-ходы группируются по цепочке и атрибутируются стадии по
маркеру reference-промпта в первом промпте цепочки:

| маркер в промпте субагента | стадия |
|---|---|
| `references/analyze-prompt.md` | `analyze` |
| `references/risk-changes-prompt.md` | `risk` |
| `references/blast-radius-prompt.md` | `blast_radius` |
| `references/requirements-prompt.md` | `requirements` |
| `references/verify-prompt.md` | `verify` |
| `rag-reviewer:performance-review` | `performance` |
| `rag-reviewer:maintainability-review` | `maintainability` |

Маркеры детерминированы и живут в нашем же `plugin/`: скилл `review-pr` передаёт имена
reference-файлов в промпт субагента дословно. Цепочка без распознанного маркера идёт в стадию
`subagent`; ходы главного агента — в `orchestrator`. Guard-тест сверяет словарь с фактическим
содержимым `plugin/skills/review-pr/references/`: новый reference-промпт без строки в словаре
красит тест — тот же приём, которым `reviewer_defect.py` сверяет продублированный словарь
классов симптомов.

**Sidecar.** JSON в `<tempdir>/reviewer-review-cost/<repo с '/'→'_'>-<pr>.json`. Путь
детерминирован от `repo` и `pr`, которые хук читает из `tool_input`. Содержимое:

```json
{
  "version": 1,
  "repo": "owner/name", "pr": 123,
  "model": "claude-opus-5",
  "transcript_source": "payload",
  "usage": {"by_model": {...}, "sidechain": {...}, "by_stage": {"analyze": {...}, "verify": {...}}},
  "total_cost": 1234.5,
  "written_at": "2026-08-15T05:00:00Z"
}
```

`model` — модель с наибольшим числом main-ходов (реальная модель оркестратора вместо вырожденного
`claude-code`).

**Граница применимости.** Sidecar — файл на диске, поэтому канал работает, когда хук и
`reviewer-mcp` делят файловую систему (stdio-запуск, текущий режим). При удалённом MCP файла не
будет — сервер это увидит как «sidecar отсутствует» и опубликует ревью без метаданных расхода.
Ограничение сознательное и записано в документации, а не обойдено.

### 3. Сервер: чтение sidecar в `publish_review`

`publish_review` перед сборкой `_RunMetadata` пробует прочитать sidecar по тому же
детерминированному пути. Правила слияния:

- **явные аргументы клиента приоритетнее sidecar** — по каждому полю отдельно (`model`, `usage`,
  `total_cost`), а не «всё или ничего»: CLI, умеющий отдать `model`, но не расход, не должен
  терять расход из sidecar;
- отсутствующий, нечитаемый, битый JSON, чужой `version` — как будто sidecar нет (fail-open,
  без исключений наружу);
- после успешного чтения sidecar удаляется — чтобы повторный `publish_review` того же PR не
  переиспользовал устаревший замер.

Чтение живёт отдельной функцией в `reviewer/services/` (не в теле `publish_review`) и тестируется
без MCP-сессии.

### 4. Взвешивание: что такое `total_cost`

`total_cost` = `fresh_in×1 + output×5 + cache_write×1.25 + cache_read×0.1`, по коэффициентам
спайка PRI-246. Единица — input-token equivalent, **условные единицы, не доллары**. Простая сумма
токенов завышала бы величину примерно в 4.1 раза и делала бы разрез по стадиям вводящим в
заблуждение — это прямой критерий приёмки задачи.

Сырые 4 бакета всегда лежат в `usage` JSONB, поэтому пересчёт в валюту по таблице цен возможен
позже без потери данных. Таблицы цен в этой задаче нет: цены устаревают, а хранить их в коде
означает чинить их релизами. Колонка `total_cost` (`NUMERIC(12,6)`) не переименовывается —
миграции не требуется; честность обеспечивается подписью в админке.

### 5. Сервер: учёт `review_steps` независимо от хуков

Механизм уже существует (`MCPReviewService._invoke_tool` пишет шаг на каждый вызов), но неполон:

- `stage` захардкожена в `analyze` для всех тулов;
- вне учёта остаются `submit_findings`, `submit_verdicts`, `get_candidate_findings`,
  `get_pr_diff` — то есть стадии verify и synthesize на сервере не видны вовсе;
- нет размера payload.

Изменения:

- карта «имя тула → стадия»: code-тулы (`search_code`, `read_file`, `get_definition`,
  `find_callers`, `get_related_symbols`, `get_changed_file_diff`, `get_impact`) → `analyze`;
  `get_candidate_findings`, `submit_verdicts` → `verify`; `submit_findings` → `synthesize`;
- `submit_*` и `get_candidate_findings` начинают писать шаг наравне с code-тулами;
- размер payload (`args` и результата, в байтах) кладётся в существующий `tool_calls` JSONB как
  `{"name", "args", "result_bytes", "args_bytes"}` — колонок не добавляется, миграции нет;
- потолок `_MAX_SESSION_STEPS` остаётся прежним, как и усечение клиентского списка.

Канал полностью серверный: он даёт стадийный разрез даже в CLI без хуков — это отдельный
критерий приёмки, и его нельзя закрывать через sidecar.

Замер показал ещё одно: у прогона 76 клиентские шаги пришли с заполненным `name`
(`prepare`, `task_context`, `analyze`, `dimensions`, `verify`), но с пустыми `stage` и `kind` —
клиент передал словари без этих ключей. Такие шаги продолжают приниматься (обратная
совместимость), но пустые поля заполняются дефолтами `kind="client_step"` и `stage="client"`,
чтобы стадийная агрегация не теряла их в безымянном ведре.

### 6. Админка: разрез по стадиям

- `GET /api/runs/{id}/trace` дополняется полем `by_stage`: на стадию — число шагов, суммарные
  `args_bytes`/`result_bytes` и, когда `usage.by_stage` из sidecar есть, 4 бакета и взвешенные
  единицы.
- `TraceView.tsx` получает таблицу разреза; подпись расхода — «усл. ед.», без знака валюты.
- Стадии без данных о токенах показывают счётчики шагов и прочерк вместо расхода — пустая
  ячейка честнее нуля.

### 7. Манифесты и документация

Любая правка содержимого `plugin/` меняет codex payload-digest, поэтому обязателен прогон
`update_codex_plugin_manifest.py` — иначе install-тесты краснеют. Строка
`plugin/skills/review-pr/SKILL.md` о передаче метаданных переписывается: клиент больше не обязан
их добывать, расход снимает хук; явная передача остаётся поддержанной и приоритетной.
`README.md` и `README.ru.md` обновляются синхронно.

## Обработка ошибок

| Отказ | Поведение |
|---|---|
| Хук не установлен / не запустился | Публикация как сейчас; поля расхода пусты |
| Транскрипт не найден обоими путями | Sidecar не пишется; публикация не затронута |
| Окно замера не определено | Sidecar не пишется |
| Sidecar битый / чужой версии | Игнорируется, публикация проходит |
| Хук упал с исключением | `exit 0`, никакого stderr в поток пользователя |
| Sidecar от прошлого ревью | Удаляется после чтения; sidecar старше 24 часов по `written_at` игнорируется и удаляется без применения |

## Тестирование

- **Общий модуль:** перенос тестов агрегации; `tests/hooks/test_brief_cost.py` остаётся зелёным
  без правок — доказательство неизменности поведения solve-task.
- **Хук:** фикстурный `transcript.jsonl` с main- и sidechain-ходами → проверка окна от
  `prepare_review`, атрибуции стадий по маркерам, обоих путей резолва транскрипта, содержимого
  sidecar; отдельно — фолбэк на маркер скилла и «окно не найдено».
- **Guard-тест:** каждый файл `plugin/skills/review-pr/references/*-prompt.md` присутствует в
  словаре маркеров стадий.
- **Сервер, sidecar:** приоритет явных аргументов по каждому полю, fail-open на битом/отсутствующем
  файле, удаление после чтения.
- **Сервер, steps:** стадия по имени тула, запись шага для `submit_*`, байты в `tool_calls`,
  соблюдение `_MAX_SESSION_STEPS`.
- **Веб:** `by_stage` в trace-ответе, включая прогон без данных о токенах.
- Unit-тесты без Postgres/Neo4j; всё, что требует БД, — под `@pytest.mark.integration`.

## Что вне скоупа

- Таблица цен и пересчёт в валюту.
- Атрибуция расхода на отдельные файлы внутри стадии `analyze` (стадия — минимальная единица).
- Работа sidecar при удалённом (не stdio) MCP-сервере.
- Ретроспективный бэкфилл расхода по 17 уже записанным прогонам: транскрипты тех сессий не
  сохранены, восстанавливать нечего.
