# PRI-206 — Ревью-дисциплина: blast-radius общих интерфейсов через reviewer — Design

url: https://ru.yougile.com/team/686c049c8af8/#PRI-206
Бриф: `docs/superpowers/briefs/2026-07-03-PRI-206-blast-radius-shared-interfaces.md`

## Goal

Зашить в авто-ревью `/reviewer_review-pr` обязательную проверку blast-radius **интерфейс-правок**: когда дифф добавляет метод в общий `Protocol`/ABC/абстрактный базовый класс (или меняет сигнатуру абстрактного метода), измерение blast-radius должно **явно перечислить конформеров** и подтвердить их покрытие через reviewer-тулы, а не «на глаз». Fail-open: reviewer недоступен / индекс устарел / граф пуст → откат на то, что доступно, без выдумывания.

## Scope / Non-goals

- **В скоупе:** правка процесса/скилла — один reference-промпт измерения blast-radius, его диспетч, guard-тест и синхронное обновление обоих README.
- **НЕ в скоупе (движок):** никаких правок `reviewer/tools/impact.py` / `get_impact` — точность движкового blast-radius это отдельная задача ID-155. Новых MCP-тулов не добавляем.
- **НЕ в скоупе (другие поверхности):** конвенцию «грунтовка reviewer» в `CLAUDE.md`/`_common` и plan-фазы (solve-task/writing-plans) не трогаем — форсируем только в авто-пайплайне review-pr. (Решение: первичная поверхность = измерение в review-pr.)
- **Новый `_common/`-блок НЕ создаём** (в отличие от PR #90 / PRI-203): правим один промпт, содержимое между скиллами не шарим.

## Архитектура

Расширяем **существующий** blast-radius-субагента, а не заводим новый. Сейчас `blast-radius-prompt.md` делает один проход: `get_impact` → «изменённая сигнатура ломает вызывающих» (callers вне диффа). Добавляем **вторую заботу того же субагента** — «interface expansion»: если дифф правит общий интерфейс, проверить, что все реализации обновлены. Тот же dispatch, та же машинерия anchoring/confidence, ноль лишних no-op субагентов на обычных PR.

Два механизма дополняют друг друга, не дублируют:
- `get_impact` → кто **вызывает** изменённый символ (callers, CALLS-рёбра).
- interface-expansion → кто **реализует** изменённый интерфейс (implementers, IMPLEMENTS / duck-typing).

## Компоненты (файлы к правке)

### 1. `plugin/skills/review-pr/references/blast-radius-prompt.md` — ядро

Новая секция «Interface expansion (mandatory when the diff edits a shared interface)», логически параллельная существующему `get_impact`-проходу. Содержит:

**Триггер** (детект из сырого патча — субагент уже получает диффы всех юнитов):
- изменённый файл определяет `Protocol` / `ABC` / абстрактный базовый класс — сигналы: `class X(Protocol)`, `class X(ABC)` / `abc.ABC`, `@abstractmethod`, тела-заглушки `...` / `raise NotImplementedError`;
- И дифф **добавляет метод** в этот класс **или меняет сигнатуру** его абстрактного метода.
- Триггер узкий (именно интерфейс/абстрактный базовый класс), не «любой базовый класс» — чтобы не плодить шум.

**Enumeration конформеров (слоёный best-effort):**
1. `get_related_symbols(<node_id интерфейса>)` → IMPLEMENTS-рёбра / подклассы (когда SCIP-граф присутствует).
2. `search_code(<имя интерфейса>)` → декларации подклассов **И сайт сборки/диспетчера** (фабрика вроде `make_board_provider`), где перечислены конкретные типы. Это ключ к structural-Protocol: конформер не обязан наследовать интерфейс (duck-typing), поэтому подклассов может не быть — концы сходятся на фабрике/типовых аннотациях.
3. На каждого кандидата: `read_file(path, start, end)` — есть ли новый метод; `get_changed_file_diff(path)` — обновлён ли конформер в этом PR.

**Finding:** конформер, у которого нет метода И который не обновлён в этом PR → находка. Одна находка на метод интерфейса (не дробить по конформерам); в `message` перечислить конформеров и явно указать, кто выглядит непокрытым.

**Anchoring** (переиспользуем существующую секцию `blast-radius-prompt.md:47-54`): пропущенная реализация живёт **вне диффа** (неизменённый файл конформера), где GitHub запрещает inline → якорим на изменённой строке метода интерфейса: `file` = изменённый файл интерфейса, `side: RIGHT`, `code_quote` = новая `def`/`async def`-строка verbatim, `line` из `commentable_right`, `category: "correctness"`.

**Confidence & fail-open** (прямое продолжение секции «Confidence & graph completeness»):
- Список конформеров = **LOWER BOUND**. Структурная типизация Protocol → полного списка гарантировать нельзя; неполные IMPLEMENTS-рёбра (live-ревью синкает граф tree-sitter'ом, CALLS-only) — норма. **Никогда** не заявлять «все конформеры покрыты» как доказанное; не понижать severity из-за короткого/пустого списка.
- `0.8–0.9` — только когда конкретный конформер прочитан (`read_file`), подтверждено отсутствие метода И отсутствие правки в PR (`get_changed_file_diff`), и разрыв однозначен.
- `0.5–0.6` — тип разрыва ясен, но проверены не все кандидаты, либо контекст-зависимо.
- `≤0.4` (или опустить) — enumeration не удалась / спекулятивно.
- Фрейминг неверифицированного — как запрос: «verify that `<conformer>` at `path:line` implements `<method>`», а не категоричное «это ломает X».
- **Fail-open:** reviewer-тулы недоступны / граф пуст / `search_code` ничего не вернул → отметить и не выдумывать; действует существующее «(… не найдено) → пустой список находок».

### 2. `plugin/skills/review-pr/SKILL.md` (диспетч blast-radius, ~строки 98-102)

Мелкая правка описания: указать, что измерение blast-radius теперь покрывает и **interface-conformance** (Protocol/ABC → все реализации обновлены), а не только callers изменённой сигнатуры. Тулы `get_related_symbols` / `search_code` / `read_file` / `get_changed_file_diff` субагенту уже доступны — **новых тулов и новых полей payload не требуется**.

### 3. `README.md` + `README.ru.md` — синхронно (оба)

Одна строка в каждом описывает измерения review-pr:
- `README.md:625` — «…+ **blast-radius** (impact analysis via `get_impact`) → **verify** …»
- `README.ru.md:553` — «…+ **blast-radius** (impact-анализ через `get_impact`) → **verify** …»

Расширить обе: blast-radius покрывает не только callers изменённой сигнатуры, но и **конформность общих интерфейсов** (правка `Protocol`/ABC → перечислить реализации и подтвердить, что все обновлены). Правки EN и RU держать синхронными.

### 4. `tests/skills/test_assembled_prompts.py` — guard-тест (TDD)

Расширить существующий `test_blast_radius_assembled_has_tooling_and_confidence_tail` (строки 47-50) новыми ассертами, что собранный blast-radius-промпт содержит правила interface-expansion. Проверяемые маркеры (точные строки уточняются при реализации промпта):
- присутствие триггера — `Protocol` (и/или `ABC` / `abstractmethod`);
- enumeration-тулы — `get_related_symbols` и `search_code`;
- lower-bound-фрейминг конформеров (напр. «lower bound» / «conformer» / «implementation»).
Старые ассерты (`get_impact`, `0.8`) остаются — измерение по-прежнему делает `get_impact`-проход.

## Testing strategy

TDD-паттерн репозитория (как PR #90): сначала расширить guard-тест `tests/skills/test_assembled_prompts.py` (падает), затем править промпт до зелёного. Прогон: `.venv/bin/pytest tests/skills/ -q`; линт `.venv/bin/ruff check .`.

**Честность про границу теста:** Acceptance поведенческий — «агент при ревью перечисляет конформеров через reviewer-тулы». Автотест может гарантировать только **наличие инструкции** в собранном промпте (текст промпта → guard), но не сам факт enumeration в рантайме LLM-субагента. Это принятое ограничение: измеряем присутствие дисциплины в промпте, не её исполнение. Полная приёмка — ручной прогон review-pr на PR, добавляющем метод в `TaskBoardProvider` (мотивирующий кейс PRI-205/`fetch_one`).

## Инварианты / ограничения

- **Движок нетронут:** `impact.py` / `get_impact` не меняем (граница ID-155).
- **Include-инвариант:** `blast-radius-prompt.md` уже подключает `_common/tool-usage.md`; новый текст добавляем в сам промпт, вложенных include не плодим (нерекурсивный резолвер; guard `assemble()` роняет на неразрешённом маркере).
- **Язык:** тело промпта/SKILL.md/EN-README — английский (как в репо); `README.ru.md` — русский; текст находок субагент пишет на `policy.output_language`.
- **Ветка:** работать off `dev`, не коммитить в `dev` напрямую; Conventional Commits на русском, без self-attribution.
- **Модель субагентов реализации:** Sonnet (стоячее предпочтение «код через superpowers → Sonnet»); Fable не применять.
