# PRI-250 — Офлайн-харнесс метрик solve-task: дизайн

Происхождение: `docs/superpowers/briefs/2026-08-14-PRI-250-offline-solve-task-metrics-harness.md`

## 1. Задача и рамки

Спайк PRI-246 (`eval/pri246_solve_task_cost.py`, PR #197) дал первый baseline цены и качества
этапа solve-task, но он одноразовый: считает срез на сегодня, перезаписывает отчёт целиком и не
хранит историю. Померить эффект оптимизации (PRI-248, правки грунтовки, ретрив под
задачи-развёртки) нечем.

PRI-250 превращает спайк в переиспользуемый офлайн-харнесс: ядро расчёта метрик, история срезов,
режим сравнения, взвешенная цена, полная цена задачи «под ключ», прогноз с разбросом и одна
команда запуска.

**В рамках:** всё, что живёт в `eval/`, плюс одна точечная правка дефекта окна в
`plugin/hooks/brief_cost.py` и юнит-тесты.
**Вне рамок:** онлайн-метрика в БД/админке (PRI-249), клиентский учёт usage для review-pr
(PRI-247), консолидация preflight (PRI-248). Харнесс не попадает в продакшн-путь `reviewer/`.

## 2. Архитектура

Чистый пакет `eval/solve_task_metrics/` — модули с одной ответственностью, без зависимостей на
`reviewer/*` и без обращений к живым внешним сервисам (единственный внешний вызов — локальный
`git`, и он изолирован за одним модулем).

| Модуль | Ответственность | Зависимости |
|---|---|---|
| `briefs.py` | Чтение корпуса брифов: парсер блока «## Токены», экстрактор путей из секций, извлечение ключа задачи из имени файла | stdlib |
| `cost.py` | Взвешивание бакетов, взвешенная и сырая цена | stdlib |
| `classify.py` | Классификатор путей: core / tests / docs / конфиг; таксономия промахов | stdlib |
| `ground_truth.py` | Локальный git: настоящие PR-мержи, изменённые файлы, «существовал ли файл до PR» | `subprocess`/git |
| `recall.py` | core-recall, precision, состояние «нет точки измерения» | `classify`, `ground_truth` |
| `endtoend.py` | Полная цена задачи «под ключ» из транскриптов сессий | stdlib |
| `history.py` | Хранилище срезов (JSONL), загрузка предыдущего среза, дельты | stdlib |
| `forecast.py` | Прогноз цены и core-recall по бакетам размера с разбросом | stdlib |
| `report.py` | Рендер markdown-отчёта из посчитанной модели | stdlib |
| `__main__.py` | CLI: `snapshot` / `compare` / `forecast` | всё выше |

Граница «расчёт vs ввод-вывод» проведена жёстко: `cost`, `classify`, `recall`, `history`
(агрегация и дельты), `forecast` — чистые функции над данными; git, файловая система и
транскрипты живут в `ground_truth`, `briefs`, `endtoend`. Это то, что делает юнит-тесты без живых
сервисов возможными (критерий 8) и то, что PRI-249 сможет переиспользовать.

**Поток данных `snapshot`:** корпус брифов → записи (ключ, токены, предсказанные пути) → ground
truth по каждому ключу → core-recall и таксономия промахов → взвешенная цена → полная цена «под
ключ» (где транскрипт доступен) → срез (модель метрик) → запись в историю + markdown-отчёт.

## 3. Взвешенная цена (критерии 3)

Множители относительно input-токена фиксируются в `cost.py` одной именованной константой:
`fresh_in ×1.0`, `output ×5.0`, `cache_write ×1.25`, `cache_read ×0.1`. Это те же числа, что
спайк применил постфактум; они вынесены в константу с комментарием об источнике, чтобы правка
тарифа была одной строкой, а не поиском по коду.

Основная метрика цены — **взвешенный input-эквивалент**. Сырая сумма токенов показывается, но
всегда с явной пометкой «не пропорциональна стоимости» и с коэффициентом завышения (baseline:
≈4.1×). Ни одно сравнение срезов и ни один прогноз не строятся на сырой сумме.

## 4. Качество ретрива (критерий 4)

Метрика качества — **core-recall**: знаменатель сужен до уже существовавшего продакшн-кода
(`reviewer/**/*.py`, `plugin/**` не-`.md`, корневые `*.py`), из него исключены файлы, которых не
существовало в первом родителе merge-коммита. Сырой recall считается и печатается только как
справочная величина с пометкой «измеряет выбор знаменателя, не качество ретрива»; precision —
справочная, не гейт.

**«Нет точки измерения» — отдельное состояние, а не ноль.** Задача с пустым core-знаменателем
(весь diff — доки/тесты/конфиги/только новые файлы) не даёт значения recall. В модели это
`None`, в агрегате — отдельный счётчик `no_measurement`, в отчёте — отдельная строка. Такие
задачи никогда не попадают в выборку медиан. Тест фиксирует, что задача с пустым core-знаменателем
не понижает агрегатную медиану.

Таксономия промахов сохраняется из спайка (`tests/`, `docs/`, конфиги, `plugin/skills/*.md`,
`reviewer/<модуль>`, `eval/`, прочее) плюс отдельная категория «новый файл».

## 5. Ground truth (критерий 6)

Ground truth — только настоящие PR-мержи: субъект коммита должен соответствовать
`^Merge pull request #\d+ from `. Синхронизационные мержи («Merge remote-tracking branch
'origin/dev' into feature/pri-N», «merge: dev в …») отбрасываются и считаются отдельным счётчиком,
который попадает в отчёт — их молчаливое отбрасывание неотличимо от «мержей не нашлось».

Инвариант покрыт юнит-тестом: функция-фильтр получает список пар (sha, субъект), включающий и
настоящий PR-мерж, и сихронизационные варианты с тем же ключом задачи, и обязана вернуть только
первый. Тест работает на чистых данных, без git-репозитория, потому что git-вызов и фильтрация
разделены: `ground_truth.py` отдельно добывает строки `%H %s` и отдельно их фильтрует.

## 6. Полная цена задачи «под ключ» (критерий 5)

**Решение: ретроспективный разбор транскриптов, без нового хука.**

Обоснование: критерий 8 требует, чтобы харнесс остался офлайн-инструментом; новый рантайм-хук —
это код в горячем пути плагина ради измерения. Ретроспективный разбор не имеет рантайм-риска,
работает и на уже закрытых задачах, и опирается на данные, которые и так пишутся.

Механика: `endtoend.py` обходит транскрипты сессий (`~/.claude/projects/<slug>/*.jsonl`, каталог
задаётся параметром — тесты подают временный каталог).

- **Начало окна** — user-сообщение с маркерами вызова скилла solve-task (`Base directory for this
  skill:` + `skills/solve-task`), в тексте которого присутствует ключ задачи.
- **Конец окна** — конец транскрипта сессии. Окно **не зависит** от записи файла брифа: файл
  брифа в определении окна не участвует вовсе.
- **Связь сессия↔задача** — по ключу задачи в тексте того же сообщения-начала. Сессия без
  распознанного ключа в измерение не входит.
- **Несколько сессий на задачу** — суммируются; их число попадает в отчёт.

Честность покрытия: транскрипты локальны и могут быть неполны (ротация, другая машина). Задача без
доступного транскрипта помечается как «полная цена не измерена», а не считается нулём; отчёт
печатает покрытие (`измерено N из M задач`).

## 7. Дефект повторного срабатывания brief_cost (критерий 5, вторая половина)

Сейчас `plugin/hooks/brief_cost.py::run` срабатывает на **любую** запись файла под
`docs/superpowers/briefs/` и каждый раз пересчитывает окно от вызова скилла до текущего момента.
Повторная правка брифа (служебная строка от оркестратора, правка на брейншторме) раздувает число
всем, что произошло между.

**Решение: печать (seal).** Если бриф уже содержит блок `## Токены (этап solve-task)`, хук —
no-op: измеренное значение — это окно до **первой** записи брифа, то есть ровно этап сборки
контекста, как и задумано. Правка сводится к одной проверке перед агрегацией и не меняет ни
формат блока, ни остальную логику.

Побочный эффект осознан: пересчитать блок в уже размеченном брифе хук больше не может. Это
приемлемо — блок описывает завершённый этап, а не живое состояние.

Поведение фиксируется тестами: (1) первая запись брифа проставляет блок; (2) повторный вызов хука
на том же файле не меняет содержимое, даже если в транскрипт добавились новые ходы.

`upsert_block` остаётся как есть — она по-прежнему нужна для первой записи и остаётся
идемпотентной по форме.

**Обязательный сопутствующий шаг:** любая правка контента под `plugin/` меняет payload-digest
codex-манифеста, поэтому после правки хука прогоняется `update_codex_plugin_manifest.py` —
иначе install-тесты красные.

## 8. История срезов и сравнение (критерии 1, 2)

Хранилище — `eval/solve_task_metrics_history.jsonl`, коммитится в репозиторий (append-only, одна
строка = один срез). Поля среза:

```
{ "taken_at": ISO-8601, "commit": "<sha HEAD>", "corpus": {"briefs": N, "with_tokens": N,
  "with_ground_truth": N, "no_measurement": N},
  "cost": {"weighted_median": ..., "raw_median": ..., "buckets": {...}},
  "quality": {"core_recall_median": ..., "core_recall_mean": ..., "n": ...,
              "raw_recall_median": ..., "denominator_median": ...},
  "endtoend": {"measured": N, "weighted_median": ...},
  "misses": {"<категория>": N} }
```

`snapshot` пересчитывает всё по корпусу, дописывает срез и перегенерирует markdown-отчёт.
`compare` (без аргументов — последний против предыдущего; с аргументами — два указанных индекса
или дат) печатает таблицу «метрика · было · стало · дельта · направление», где направление
проставляется по известной полярности каждой метрики (цена — меньше лучше, recall — больше
лучше). Метрика, которой не было в старом срезе, показывается как новая, а не как рост с нуля.

Схема среза версионируется полем `schema` — чтение старого среза не должно падать при добавлении
метрик.

## 9. Прогноз (критерий 7)

Точечное число не выдаётся. Прогноз строится на бакетах по размеру core-знаменателя (1–3, 4–9,
10+ файлов — граница выбрана по baseline-распределению: медиана 4, максимум 25) и для каждого
бакета даёт **медиану и межквартильный размах (p25–p75)** core-recall и взвешенной цены, плюс
размер выборки бакета.

Бакет с выборкой меньше порога (5 задач) помечается как статистически ненадёжный и печатает
«недостаточно данных», а не интервал. Формулировка вывода всегда интервальная: «ожидаемый
core-recall 45–72% (медиана 61%, N=18)».

`forecast` без аргументов печатает таблицу по всем бакетам; с указанием предполагаемого числа
core-файлов — интервал соответствующего бакета.

## 10. Запуск и документация (критерий 8)

Одна команда, три подкоманды:

```
python -m eval.solve_task_metrics snapshot     # пересчитать всё, сохранить срез, обновить отчёт
python -m eval.solve_task_metrics compare      # дельты последнего среза против предыдущего
python -m eval.solve_task_metrics forecast     # прогноз с разбросом
```

Документируется в `README.md` и `README.ru.md` (оба README поддерживаются синхронно).

Одноразовый `eval/pri246_solve_task_cost.py` удаляется — его логика целиком переезжает в ядро.
`eval/pri246_report.md` остаётся как замороженный исторический артефакт спайка; новый отчёт
пишется в отдельный файл и старый не трогает.

## 11. Отношение к PRI-249 (без дублирования)

Ядро (`cost`, `classify`, `recall`, частично `ground_truth`) написано как чистые функции без
зависимостей на `reviewer/*` — именно для того, чтобы PRI-249 при реализации **перенёс** этот
модуль в продакшн-слой и импортировал его в обе стороны, а не написал расчёт второй раз. Пока
PRI-249 не начата, модуль живёт в `eval/` и в продакшн-путь не попадает (критерий 8). Это
зафиксировано в докстринге пакета, чтобы следующая реализация не выбрала копирование.

## 12. Тестирование

Юнит-тесты в `tests/eval/`, все без внешних сервисов и без сети:

- парсер блока токенов: полный блок, блок с sidechain, отсутствие блока, лоссовое `K`/`M`;
- экстрактор путей секций: backticks, голые пути, пути без расширения, пропуск `(dropped N: …)`;
- ground truth: фильтр PR-мержей отбрасывает синхронизационные (критерий 6);
- классификатор путей и таксономия промахов;
- core-recall: обычный случай, пустой знаменатель → «нет точки измерения», отсутствие в медианах;
- взвешивание: взвешенная цена ≠ сырой сумме, коэффициент завышения считается;
- история: запись/чтение среза, дельты, метрика-новичок, полярность направления;
- прогноз: интервал, малый бакет → «недостаточно данных»;
- `endtoend`: окно от маркера до конца транскрипта, независимость от записей брифа, сессия без
  ключа не учитывается;
- `brief_cost`: печать — повторный вызов не меняет уже размеченный бриф.

Существующие тесты хука (`tests/hooks/test_brief_cost.py`) дополняются, не переписываются.

## 13. Риски

- **Лоссовый формат блока токенов.** `human_tokens` округляет до одного знака в K/M — точность
  цены остаётся диапазоном, а не точным числом. Фиксируется в отчёте как ограничение, не
  «чинится».
- **Покрытие транскриптов.** Полная цена «под ключ» измерима только там, где транскрипт локально
  доступен; покрытие печатается явно.
- **Печать brief_cost меняет смысл исторических замеров.** Часть накопленных блоков измерена
  старым (раздувавшимся) окном, и различить их по содержимому брифа нельзя. Новые замеры
  сопоставимы между собой, но не с историческими. Срез несёт поле `window_mode`
  (`legacy` — снят до правки хука, `sealed` — после), отчёт печатает его отдельной строкой, а
  `compare` предупреждает при сравнении срезов с разными значениями.
