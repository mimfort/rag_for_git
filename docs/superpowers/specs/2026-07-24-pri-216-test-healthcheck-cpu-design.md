# PRI-216 — Healthcheck тестовых сервисов жжёт CPU вхолостую

Задача: https://ru.yougile.com/team/686c049c8af8/#PRI-216
Бриф: `docs/superpowers/briefs/2026-07-24-PRI-216-test-healthcheck-cpu.md`

## Проблема

Сервисы test-профиля в `docker-compose.yml` проверяются healthcheck'ом с `interval: 2s`. Docker
выполняет пробу бесконечно — и после того, как контейнер стал `healthy`. Для `neo4j-test` проба —
`cypher-shell`, а каждый её запуск поднимает JVM.

Замеры на машине разработчика (cgroup `cpu.stat` → `usage_usec`, окно 20 с, стенд в простое):

| Сервис | Нагрузка сейчас | Цена одной пробы |
|---|---|---|
| `neo4j-test` (`cypher-shell`) | 10.17 с CPU / 20 с = **51% ядра** | ≈2.5 с CPU |
| `paradedb-test` (`pg_isready`) | **≈1.4% ядра** | единицы мс |

Это постоянный расход: контейнер жжёт пол-ядра всё время, пока поднят, даже когда тесты не идут.

Замер цены пробы делался через `docker exec` (лишний exec-процесс + конкуренция с фоновым
healthcheck), поэтому 2.5 с — оценка сверху; порядок величины она передаёт верно.

## Решение

Разделить фазу старта и установившийся режим через `start_period` + `start_interval` (Docker
Engine ≥ 25.0 / API ≥ 1.44): в первые 180 с после старта контейнера пробы идут часто (как сейчас),
дальше — редко. `start_period: 180s` (было предложено `60s`) ничего не стоит в установившемся
режиме: каденция проб переключается с `start_interval` на `interval` в момент перехода контейнера
в `healthy`, а не по истечении `start_period` (проверено на живом стенде health-логом) — поэтому
запас на случай «сервис не успел подняться за 60 с на загруженной машине» бесплатен, а без него
следующая проба откладывалась бы до редкого `interval` (5 минут вместо секунд для `up -d --wait`).

### `neo4j-test`

```yaml
    healthcheck:
      test: ["CMD-SHELL", "cypher-shell -u neo4j -p reviewer_test_pass 'RETURN 1'"]
      start_period: 180s
      start_interval: 2s
      interval: 300s
      timeout: 3s
      retries: 3
```

Команда пробы и `timeout` не меняются — проба остаётся честной (bolt + auth + реальный Cypher),
поэтому нет риска ложного `healthy` и флейков в integration-тестах. Остаточная нагрузка:
2.5 с / 300 с ≈ **0.8% ядра** (запас к порогу приёмки 5% — шестикратный).

`interval: 300s` вместо предложенных в задаче `30s`: при цене пробы 2.5 с интервал 30 с даёт
≈7.7% ядра, то есть **не проходит критерий приёмки самой задачи** (< 5%). Интервал 60 с даёт ≈4% —
впритык, без запаса на погрешность замера и разброс машин.

Плата за редкий интервал: упавший сервис отразится в статусе с задержкой до 5 минут. Для
одноразового тестового стенда это неважно — упавшую БД обнаружат сами тесты, а не колонка статуса.

### `paradedb-test`

```yaml
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U reviewer_test -d reviewer_test"]
      start_period: 180s
      start_interval: 2s
      interval: 30s
      timeout: 2s
      retries: 3
```

Та же схема ради единообразия. `pg_isready` — дешёвый бинарник, поэтому `interval: 30s` достаточно:
получается ≈0.1% ядра.

### `retries: 3` вместо `30`

`start_period` покрывает фазу старта (провалы проб внутри неё не переводят контейнер в
`unhealthy`), поэтому 30 попыток в установившемся режиме избыточны. При `interval: 300s` они
означали бы 2.5 часа до `unhealthy`; с `retries: 3` — ~15 минут.

### Комментарий о требовании к версии Docker

Рядом с healthcheck'ами test-профиля — явный комментарий, что `start_interval` требует Docker
Engine ≥ 25.0 / API ≥ 1.44. На старых движках ключ игнорируется, стартовые пробы идут с обычным
`interval`, и `docker compose --profile test up -d --wait` подвиснет на 5 минут вместо секунд.

Локально Docker 29.2.1 / API 1.53, Compose v5.0.2 — совместимо. CI test-профиль не поднимает
(в `.github/workflows/` нет `docker compose --profile test`), так что риск касается только чужих машин.

## Тесты

### `test_compose_defines_isolated_test_profile_services` — гибридный ассерт

Сейчас тест сравнивает словарь `healthcheck` точным `==`, перечисляя `test`/`interval`/`timeout`/
`retries`. Любая правка таймингов ломает его — причём тест не помечен `@pytest.mark.integration`,
поэтому падает в обычном `pytest -q`.

Новая форма (хелпер `_assert_cheap_idle_healthcheck`):

- **точное сравнение** — `test` (команда пробы) и `retries`: то, что меняться не должно;
- **инварианты таймингов, per-service** — `interval >= min_interval`, где `min_interval` —
  обязательный keyword-параметр хелпера (`30` для `paradedb-test`, `300` для `neo4j-test`; единый
  жёсткий порог `30` не поймал бы регресс `neo4j-test` до дешёвого на бумаге, но не проходящего
  критерий приёмки задачи интервала `30s` — мутационно проверено, см. ниже);
  `start_interval <= 5s`; `start_period >= 30s` (не просто «задан больше нуля» — предыдущая версия
  ассерта была вакуумной: `start_period: 1ms` её проходил, хотя стартовое окно фактически исчезает);
  `timeout <= 10s` (раньше это фиксировало точное `==`; без него зависшая проба держала бы
  health-монитор надолго, и переход на гибрид создал бы непокрытое слепое пятно).

Так тест продолжает защищать суть (дешёвый установившийся режим, быстрый и не пропущенный старт,
проба не может зависнуть надолго), но не ломается при последующем тюнинге конкретных чисел внутри
этих границ.

Потребуется маленький хелпер парсинга длительностей compose (`"300s"` → 300 секунд), потому что
формат допускает и `2s`, и `1m30s`. Хелпер — локальный для тест-модуля, в продакшн-код не идёт.

### Новый тест — комментарий о версии Docker

По образцу существующего `test_compose_documents_only_safe_test_profile_teardown`: проверяет, что
в `docker-compose.yml` присутствует комментарий с требованием Docker Engine ≥ 25.0 / API ≥ 1.44.
Комментарий — единственная защита от тихой деградации старта на старом движке, поэтому он
закрепляется тестом.

## Верификация (вручную, при приёмке)

Автотеста на CPU не будет — замер шаткий на загруженной машине и медленный. Проверяется руками:

1. **CPU в простое.** `usage_usec` из `/sys/fs/cgroup/cpu.stat` контейнера до и после окна ≥ 10 с,
   стенд в простое. Baseline снят: `neo4j-test` 51%, `paradedb-test` 1.4%. Измерено после правки:
   `neo4j-test` ≈2.1% ядра суммарно — из них сам healthcheck даёт ≈0.5 п.п., остальное фоновая
   работа JVM, которая была и до правки (входила в те 51%); `paradedb-test` ≈0.25%. Критерий
   приёмки < 5% выполнен для обоих. Ожидание первой версии спеки «< 1% суммарно» было недостижимо
   при любом интервале healthcheck: оно неявно приписывало пробе весь простойный CPU контейнера,
   включая фоновую работу JVM, которую healthcheck не создаёт и не может убрать. Честная
   формулировка: цель по компоненту, за который отвечает это изменение (сама проба), достигнута.
2. **Скорость старта.** `time docker compose --profile test up -d --wait paradedb-test neo4j-test`
   на холодном старте (сервисы предварительно удалены через
   `docker compose --profile test rm -sfv paradedb-test neo4j-test`) — не медленнее прежнего.
3. **Тесты.** `.venv/bin/pytest -q` (включая изменённый тест политики) и
   `.venv/bin/pytest -q -m integration` — зелёные.

Цифры замеров кладутся в описание PR.

## Вне скоупа

- dev-сервисы `paradedb` / `neo4j` — у них healthcheck нет вообще, поведение не меняется;
- CI-воркфлоу — test-профиль там не поднимается;
- автоматизация замера CPU (тест или скрипт в репо) — решено проверять вручную;
- замена команды пробы `neo4j-test` на дешёвую TCP-проверку bolt-порта
  (`bash -c 'exec 3<>/dev/tcp/localhost/7687'`, ≈0.2 с CPU) — рассматривалась и отклонена:
  открытый порт не гарантирует готовность базы, а значит появляется риск ложного `healthy` и
  флейков в integration-тестах.
