# PRI-114 — устарелость установленных скиллов (timeout sync-tasks на kimi)

Дата: 2026-06-18
Задача: PRI-114 / ID-114 «Починить скилл reviewer_sync-tasks: timeout при индексации 19+ задач»
Связь: PRI-96 / ID-96 (batch embeddings + rate-limit-aware indexing, Готово)

## Контекст и первопричина (доказано воспроизведением)

Пользователь наблюдал таймаут `reviewer_sync-tasks` на доске из 19 задач **только на модели
kimi K2.7 Code**; на Opus и DeepSeek v4 pro — нет. Вопрос: минус модели или чинимо.

Проведён контролируемый A/B-прогон через `kimi` CLI (`-p` + `--output-format stream-json`),
**одна и та же модель K2.7 Code**, менялась только версия скилла:

| Условие | Скилл | Индексация | Итог |
|---|---|---|---|
| Вне репозитория (как у обычного юзера) | установленный `~/.kimi-code/skills/sync-tasks` — **старый** (цикл `index_task`) | `mcp__reviewer__index_task` ×20, batch ×0 | баг PRI-114 |
| Внутри репозитория | репозиторный `plugin/skills/...` — свежий (batch) | план на один `index_tasks_batch` | бага нет |

Трейсы: `/tmp/kimi_repro_clean.jsonl` (цикл, 20 вызовов), `/tmp/kimi_synctasks_repro.jsonl` (batch).

**Вывод: это НЕ минус модели.** Определяющая переменная — версия скилла. Модель честно
исполняет данный ей текст: старый скилл предписывает `index_task` на каждую задачу → 20
последовательных эмбеддингов сквозь Voyage free tier (3 RPM) ≈ 7 минут троттлинга → таймаут.
Opus/DeepSeek «не ловили» это, потому что запускались с актуальным скиллом (плагин Claude Code =
HEAD репозитория), а не из-за «лучшей» модели.

### Почему скилл устарел (системный баг)

Исходный фикс PRI-114 (заменить цикл `index_task` на единый `index_tasks_batch`) уже в `main`
(коммиты `158e008`, `7b44212`) с 16 июня. Но:

- MCP-сервер закреплён на `rag-reviewer@latest` (`reviewer/install.py:launch_command`) →
  **авто-обновляется при каждом старте**.
- Скиллы — файловые **копии-снапшоты** в `~/.<client>/skills`, тянутся тарболом с GitHub `main`
  (`install.py:SKILLS_TARBALL`, `install_skills`) **один раз** при установке и больше не
  освежаются. Нет ни авто-рефреша, ни детекта рассинхрона.
- Асимметрия «сервер уезжает вперёд / скиллы заморожены» + молчание = баг. Установка 14 июня
  (до фикса) застыла; повторно не запускалась.
- `extract_skills` только перезаписывает файлы (не удаляет) — повторный запуск безопасно обновит.
- `reviewer install <client>` **уже** ставит скиллы по умолчанию (`cli.py:_ensure_skills`,
  флаг `--no-skills`). Но `.kimi-code/INSTALL.md` это противоречит коду: рекомендует ручной
  одноразовый `curl|tar` (шаг 2) — именно он рождает замороженную копию.

Устарели на машине пользователя 3 скилла: `sync-tasks`, `solve-task`, `review-pr`
(`sync-codebase`, `maintainability-review`, `performance-review` — идентичны репозиторию).

## Цели

1. Немедленно устранить баг на текущей машине (освежить устаревшие скиллы).
2. Убрать молчаливую устарелость: пользователь должен **узнавать**, что установленные скиллы
   отстали от auto-обновляемого сервера.
3. Defense-in-depth: скилл `sync-tasks` не должен скатываться в поштучный цикл даже на буквальной
   или слабой модели.
4. Привести `INSTALL.md` в соответствие с кодом.

## Не-цели (YAGNI)

- Не пакуем скиллы в wheel — тарбол с `main` и так свежий.
- Не трогаем серверный `TaskService.index_batch` — работает корректно.
- Не рефрешим скиллы из процесса MCP-сервера на старте: сервер не знает, какой клиент его запустил,
  и запись в чужой каталог конфигурации инвазивна и неожиданна.

## Компоненты

### Компонент 1 — Освежить скиллы сейчас (операционно, не код)

`reviewer install-skills kimi` (или `reviewer install kimi`) — тянет свежий тарбол с `main`,
перезаписывает устаревшие копии. Выполняется на этапе реализации; верификация — в критериях приёмки.

### Компонент 2 — Стамп установки + детект устарелости в `reviewer check`

**Стамп.** `install_skills` после распаковки пишет `<skills_dir>/.reviewer-skills.json`:

```json
{
  "installed_at": "<ISO-8601 UTC>",
  "source_url": "https://github.com/mimfort/rag_for_git/archive/refs/heads/main.tar.gz",
  "source_etag": "<ETag из HTTP-ответа GitHub, если был>",
  "pkg_version": "<importlib.metadata.version('rag-reviewer')>",
  "skills": { "<skill>": "sha256:<hex>", ... }
}
```

`fetch_skills_bytes` дополнительно возвращает (или отдельная функция извлекает) `ETag`/`Last-Modified`
из ответа. Запись стампа — внутри `install_skills` (а не `extract_skills`, чтобы `extract_skills`
оставался чистой распаковкой; стамп требует знания source_url/etag/pkg_version).

**Детект в `reviewer check`.** Новая функция в `install.py`
(`skills_staleness(client, *, system, timeout) -> StalenessReport`) и её вызов в `cli.py:check`
для каждого клиента из `detect_installed()`, у которого `skills_fn` задан и каталог существует:

1. Нет стампа → «скиллы установлены старым способом / без стампа» → совет `reviewer install-skills <client>`.
2. Пересчитать sha256 установленных файлов, сравнить со `skills` стампа → расхождение = локальный
   дрейф / частичная установка.
3. Сеть (best-effort, короткий таймаут, fail-soft): `HEAD` `source_url`, сравнить `ETag` со стампом →
   расхождение = `main` сдвинулся.
4. Офлайн-фолбэк (если `HEAD` не удался): сравнить `pkg_version` стампа с текущей
   `importlib.metadata.version('rag-reviewer')` → если сервер новее, чем версия на момент установки
   скиллов → мягкий совет переустановить.

Вывод: явная строка `⚠ скиллы <client> устарели → reviewer install-skills <client>` (или ✓, если
свежо). Проверка **не валит** `check` (мягкое предупреждение; офлайн не ошибка). ETag — точный
сигнал «upstream сдвинулся»; pkg_version — дешёвый офлайн-фолбэк; hash — детект локального дрейфа.

### Компонент 3 — Защита в скилле sync-tasks (defense-in-depth)

`plugin/skills/sync-tasks/SKILL.md` (шаг «Normalize + index») и
`plugin/skills/sync-tasks/references/sync-tasks-yougile.md` (шаг «Index») — добавить явный,
выделенный guardrail:

> **НИКОГДА не вызывай `index_task` в цикле по задачам.** Собери все `TaskBrief` в список и сделай
> **один** `index_tasks_batch(...)`. Для очень больших досок — чанками по ≤N задач за вызов (всё
> равно O(число_чанков) вызовов Voyage, а не O(N)). Одиночный `index_task` существует только для
> сценария одной задачи (`solve-task`) — для синка он запрещён.

Текст уже на batch-версии; добавляется именно явный запрет цикла + указание на чанкование, чтобы
буквальная/слабая модель и будущий дрейф доков не возродили поштучный цикл.

### Компонент 4 — Синхронизировать `.kimi-code/INSTALL.md` с кодом

`.kimi-code/INSTALL.md`: убрать утверждение «Быстрая установка пишет только mcp.json» и ручной
одноразовый `curl|tar` (шаг 2) как основной путь; зафиксировать, что `reviewer install kimi`
ставит и MCP, и скиллы, а **обновление = повторный `reviewer install kimi`** (или
`reviewer install-skills kimi`). Ручной `curl|tar` оставить как офлайн-альтернативу с явной
пометкой «снапшот; не обновляется сам».

## Затрагиваемые файлы

- `reviewer/install.py` — извлечение ETag в `fetch_skills_bytes`; запись стампа в `install_skills`;
  новые `read_skills_stamp`, `skills_staleness`/`StalenessReport`, хэш-хелпер.
- `reviewer/entrypoints/cli.py` — `check` вызывает детект и печатает предупреждения.
- `plugin/skills/sync-tasks/SKILL.md`, `plugin/skills/sync-tasks/references/sync-tasks-yougile.md` —
  guardrail против цикла.
- `.kimi-code/INSTALL.md` — синхронизация с кодом.
- Тесты под `tests/` (зеркало `reviewer/install.py`): стамп (write/read), сравнение
  ETag/hash/pkg_version, мягкое предупреждение `check` на фикстурах (свежо / upstream-сдвиг /
  локальный дрейф / нет стампа / офлайн).

## Стратегия тестирования

- unit (на фейках, без сети): запись/чтение стампа; `skills_staleness` на фикстурах для всех веток
  (свежо, ETag-расхождение, hash-дрейф, нет стампа, HEAD недоступен → фолбэк на pkg_version);
  `extract_skills`/`install_skills` пишут корректный стамп.
- guard: `reviewer install --dry-run kimi` показывает скиллы; повторный install идемпотентен
  (стамп обновляется, бэкап чужого не ломается).
- Сеть мокается; реальный HEAD — только в integration (по желанию).
- Ручная верификация (E2E): повторить чистый прогон kimi вне репо после обновления → ожидаем
  **один** `index_tasks_batch`, ноль циклического `index_task`.

## Критерии приёмки

- Чистый прогон `kimi` (K2.7 Code) вне репозитория с `.review.yml` после `reviewer install-skills kimi`
  индексирует доску **одним** `index_tasks_batch`, без цикла `index_task`.
- `reviewer check` на устаревших скиллах печатает понятное предупреждение с точной командой; на
  свежих — не шумит. Офлайн `check` не падает.
- `install_skills` пишет стамп; повторный запуск идемпотентен и обновляет стамп.
- `sync-tasks` SKILL.md и references содержат явный запрет цикла `index_task`.
- `.kimi-code/INSTALL.md` согласован с реальным поведением `reviewer install`.
- `.venv/bin/pytest -q` зелёный; `.venv/bin/ruff check .` без новых замечаний.
- (Исходные критерии PRI-114 сохраняются: первый синк 19 задач < 2 мин; повторный < 30 сек;
  `search_tasks` находит задачи; связи из description попадают в граф — все уже обеспечены
  batch-версией скилла.)

## Риски и открытые вопросы

- GitHub может не отдавать стабильный `ETag` для `heads/main.tar.gz` или менять формат → детект
  обязан быть fail-soft: при отсутствии/недоступности ETag опираемся на hash + pkg_version, и
  отсутствие сигнала не считается ошибкой.
- Сетевой `HEAD` в `check` → короткий таймаут, best-effort; офлайн-режим выдаёт фолбэк-предупреждение,
  но не блокирует `check`.
- Пользователь мог удалить стамп → трактуем как «неизвестно, советуем переустановить», не ошибка.
- `pkg_version`-фолбэк неточен (версия пакета и версия скиллов на `main` не связаны жёстко) — это
  осознанный грубый сигнал, дополняющий ETag/hash, а не замена им.
