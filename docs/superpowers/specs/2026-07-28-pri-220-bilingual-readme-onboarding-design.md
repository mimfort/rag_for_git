# Дизайн — двуязычный README для понятного онбординга (PRI-220)

Задача: https://ru.yougile.com/team/686c049c8af8/#PRI-220

Бриф: `docs/superpowers/briefs/2026-07-28-PRI-220-bilingual-readme-onboarding.md`

## 1. Проблема

`README.md` и `README.ru.md` выросли до 1146 и 1115 строк соответственно. Оба документа
содержат полезные сведения, но смешивают презентацию продукта, установку, архитектуру,
эксплуатацию и справочники. Порядок разделов между языками различается, быстрый путь теряется
среди деталей, а часть публичной поверхности описана неравномерно: в репозитории
зарегистрировано 12 skills, но `reviewer_finish-task` не имеет собственного справочного раздела.

Новый читатель должен одновременно понять ценность продукта, ограничения и первое действие.
Инженеру, разворачивающему reviewer для команды, нужен другой маршрут: топология сервисов,
секреты, хранилища, репозитории, ветки, доска задач, подключение клиентов и эксплуатация.
Попытка вести обе аудитории одним линейным повествованием создаёт нынешнюю перегрузку.

## 2. Цели

1. Дать двум равноправным аудиториям короткие, явно обозначенные маршруты:
   - попробовать reviewer и получить первый результат;
   - развернуть reviewer для команды.
2. Сохранить README самостоятельным для установки, основных сценариев, конфигурации и
   диагностики, но вынести глубокие детали в существующие профильные документы.
3. Сделать `README.md` и `README.ru.md` семантически симметричными: одинаковый порядок,
   команды, возможности, ограничения и ссылки при естественном тексте на каждом языке.
4. Описать все 12 зарегистрированных skills по одному практическому шаблону.
5. Проверять утверждения по коду, CLI, конфигурации и контрактам skills, а не переносить их из
   старых README без верификации.

## 3. Вне скоупа

- Изменение runtime-поведения reviewer, CLI, MCP или skills.
- Создание новой системы документации или перенос всего справочника на отдельный сайт.
- Дословный перевод одного README в другой.
- Документирование внутренних символов и параметров, не относящихся к публичному использованию.
- Сетевые проверки внешних URL в unit-тестах: обычный pytest проекта обязан работать без сети.

## 4. Выбранный подход

Используется **слоистый dual-track README**: общая краткая презентация, два независимых быстрых
маршрута и единые последующие разделы без дублирования справочной информации.

Отклонённые альтернативы:

- **Два полностью самостоятельных маршрута внутри каждого README.** Локально удобно, но команды,
  конфигурация и ограничения дублируются и со временем расходятся.
- **Исчерпывающий линейный справочник текущего объёма.** Сохраняет полноту, но не исправляет
  онбординг: первое действие остаётся после архитектуры и деталей установки.
- **Короткий лендинг со ссылками почти на всё.** Упрощает вход, но делает README недостаточным для
  установки и повседневного использования из GitHub, PyPI или установленного plugin payload.

## 5. Информационная архитектура

Обе языковые версии используют один семантический каркас:

1. **Заголовок и переключатель языка.** Одно предложение о назначении, существенная оговорка о
   внешних сервисах и заметная взаимная ссылка EN ↔ RU.
2. **Start here / Начните здесь.** Небольшая таблица выбора аудитории с двумя якорями:
   «попробовать и выполнить первое ревью» и «развернуть для команды».
3. **Маршрут нового пользователя.** Требования → установка → настройка → проверка → первое
   действие → ожидаемый результат.
4. **Маршрут командного развёртывания.** Топология → секреты и хранилища → repo/branch scope →
   доска задач → подключение клиентов → healthcheck/index → эксплуатация.
5. **Практические workflows.** PR review, solve-task, grounded Q&A, PR walkthrough,
   maintainability/performance review и жизненный цикл задачи до `finish-task`.
6. **Как устроено.** Краткий поток prepare → analyze → publish, base/overlay index, RAG, граф,
   MCP и границы ответственности внешних сервисов.
7. **Установка и конфигурация.** Общий справочник после быстрых маршрутов: платформы, env,
   `.review.yml`, репозитории, ветки, VCS и зарегистрированные board providers.
8. **CLI и skills.** Команды по пользовательским задачам и полный inventory skills.
9. **Эксплуатация, диагностика, безопасность и ограничения.**
10. **Разработка.** Тесты, структура проекта, contributing и license.

Содержание остаётся доступным в начале, но отражает этот каркас и не превращается в второй
справочник.

## 6. Контракт быстрых маршрутов

### 6.1 Новый пользователь

Маршрут отвечает на шесть вопросов без перехода к справочным разделам:

1. Что нужно установить и какие внешние зависимости обязательны?
2. Как установить или временно запустить CLI?
3. Как поднять инфраструктуру и заполнить конфигурацию?
4. Как подключить текущий AI-клиент?
5. Как проверить готовность через `reviewer check` и состояние индекса?
6. Как вызвать первый workflow и какой результат считать успешным?

Команды сверяются с актуальным launcher/install lifecycle. Один основной путь маркируется как
рекомендуемый; ручная установка остаётся краткой альтернативой, а не параллельной инструкцией
того же веса.

### 6.2 Командное развёртывание

Маршрут сначала объясняет границы деплоя: один MCP server, Postgres/ParadeDB, Neo4j, Voyage и
VCS/board providers. После этого читатель последовательно настраивает секреты, `DEFAULT_REPO`,
`REVIEW_BRANCHES`, per-repo `.review.yml`, board provider и глобальные установки клиентов.

Каждый шаг заканчивается наблюдаемой проверкой. Секреты описываются только как имена переменных и
место конфигурации; README не предлагает передавать их клиентам или хранить в репозитории.

## 7. Контракт workflows, CLI и skills

Workflows описываются от намерения пользователя, а не от списка MCP tools. Для каждого сценария
README показывает условие запуска, короткий пример, результат и ссылку на подробный skill или
профильный документ.

CLI группируется по задачам:

- первичная настройка и установка интеграций;
- проверка окружения;
- построение, миграция и диагностика индекса;
- поиск и локальная диагностика;
- эксплуатация web admin.

Каждый из 12 каталогов `plugin/skills/*/SKILL.md` получает отдельный элемент справочника:

- когда применять;
- пример вызова;
- prerequisites;
- что skill читает и какие внешние или локальные изменения может выполнить;
- результат и следующий шаг.

Inventory строится из каталогов `ask`, `configure-review`, `create-task`, `finish-task`,
`maintainability-review`, `performance-review`, `pr-walkthrough`, `review-pr`, `solve-task`,
`summarize-subsystems`, `sync-codebase`, `sync-tasks`. `_common` остаётся support directory и не
показывается как skill.

## 8. Источники истины и factual grounding

Перед написанием каждого раздела факты сверяются по следующему приоритету:

| Поверхность | Источник истины |
|---|---|
| CLI, команды и аргументы | `reviewer/entrypoints/cli.py`, `[project.scripts]` в `pyproject.toml` |
| Skills | `plugin/skills/*/SKILL.md` и их references |
| Env и требования | `.env.example`, `reviewer/config/settings.py`, `pyproject.toml` |
| Per-repo policy | `.review.yml`, `reviewer/policy/` |
| Board providers | registry в коде и `docs/board-providers.md` |
| Архитектура и инварианты | composition/services/index/graph/MCP-код; `CLAUDE.md` как проверочный prior |
| Установка клиентов | installer-код, manifests и install-тесты |

Старые README используются только как список тем и потенциальных фактов. Утверждение сохраняется,
только если подтверждено источником истины. Маркетинговое преимущество всегда соседствует с
существенным ограничением: стоимость/квоты Voyage, внешняя инфраструктура, branch/repo scope,
границы fail-open и доступность точного SCIP-графа.

## 9. Симметрия EN/RU

`README.md` и `README.ru.md` пишутся параллельно по единому content checklist. Для каждой
семантической секции checklist фиксирует:

- наличие и позицию раздела;
- команды и параметры;
- внутренние и внешние ссылки;
- перечисленные возможности и ограничения;
- ожидаемые результаты проверок;
- полный inventory CLI/skills/providers, если он присутствует в секции.

Заголовки и формулировки локализуются естественно; номера, команды, имена файлов, env-переменные и
машиночитаемые идентификаторы остаются идентичными. Переключатели языка ведут на корень
соответствующего файла, чтобы переименование локализованного заголовка не ломало основную ссылку.

## 10. Диагностика и обработка ошибок в документации

Ошибки описываются рядом с шагом, где они возникают:

- отсутствующие credentials или сервисы → `reviewer check` и ссылка на нужную настройку;
- отсутствующий или устаревший base index → `reviewer status` и явная команда индексации;
- лимиты Voyage → предупреждение перед затратной индексацией;
- не настроенная доска → board-less поведение и `docs/board-providers.md`;
- ветка вне `REVIEW_BRANCHES` → объяснение branch routing;
- недоступный Neo4j или вторичный контекст → точное описание fail-soft/fail-open поведения без
  обещания полной функциональности;
- Docker → только безопасная адресная команда очистки тестовой инфраструктуры, без
  `docker compose ... down -v`;
- headless/SSH → отсутствие OAuth loopback там, где это является контрактным ограничением.

Отдельный раздел troubleshooting собирает симптомы в компактную таблицу, но не заменяет локальные
предупреждения в быстрых маршрутах.

## 11. Изменяемые файлы

- `README.md` — новая английская версия.
- `README.ru.md` — новая русская версия с тем же семантическим каркасом.
- `tests/docs/test_readme_onboarding.py` — проверки структуры, относительных ссылок/якорей и
  двуязычного content contract.
- Существующие README-contract тесты в `tests/skills/`, `tests/docs/` и `tests/install/`
  корректируются только там, где новый заголовок или граница секции требует нового селектора.

Runtime-код, manifests, версия пакета и содержимое skills не меняются.

## 12. Проверка

Новый stdlib-only тест:

1. Проверяет взаимные language links и порядок парных высокоуровневых секций.
2. Динамически перечисляет каталоги `plugin/skills/*/SKILL.md` и требует отдельный marker каждого
   skill в обеих README.
3. Проверяет существование относительных файловых ссылок.
4. Для ссылок на локальные Markdown-якоря строит GitHub-совместимые slug из заголовков, включая
   суффиксы дубликатов, и требует существующий target.
5. Проверяет симметричный набор критичных команд и идентификаторов из content checklist.
6. Не обращается к внешней сети; внешние URL проверяются только на допустимую схему и непустой host.

Существующие тесты остаются смысловыми guardrails: grounding section, generic board workflow,
provider terminology, store-first solve-task, Codex plugin inventory и документационная matrix
провайдеров не ослабляются.

Команды проверки:

```bash
.venv/bin/pytest -q tests/docs/test_readme_onboarding.py
.venv/bin/pytest -q tests/skills/test_readme_grounding_block.py \
  tests/docs/test_board_provider_docs.py \
  tests/install/test_codex_plugin_payload.py
.venv/bin/pytest -q
.venv/bin/ruff check .
```

Ручная проверка читает каждый быстрый маршрут с нуля и отвечает: понятны ли prerequisites,
следующая команда, успешный результат, существенные ограничения и путь восстановления после
типового сбоя.

## 13. Критерии приёмки

1. За первые два экрана читатель понимает назначение reviewer, ограничения и выбирает один из двух
   равноправных маршрутов.
2. Оба маршрута доводят читателя до проверяемого результата до архитектуры и полного справочника.
3. EN/RU имеют одинаковый порядок и смысл разделов, команды, ссылки, возможности и ограничения.
4. Все 12 зарегистрированных skills представлены отдельными практическими элементами; inventory
   проверяется динамически.
5. Команды, требования и публичные контракты подтверждены источниками истины из §8.
6. Все относительные ссылки и локальные Markdown-якоря проходят автоматическую проверку.
7. Существенные ограничения стоят рядом с преимуществами и продублированы в компактной
   troubleshooting/limitations секции там, где это помогает поиску.
8. Существующие README-contract тесты и полный unit suite проходят без сети и localhost-сервисов.
