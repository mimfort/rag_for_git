# PRI-145 — blast-radius: отражать неполноту графа в confidence/severity находок

**Задача:** PRI-145 (ID-145) · слой: плагин/агент (blast-radius-промпт) · оценка S
**Надстройка над:** PRI-126 (завершён, PR #31 — создал MCP-тул `get_impact` + blast-radius reference-промпт)
**Дата:** 2026-06-21

## Проблема

MCP-тул `get_impact(repo, pr)` находит символы PR с изменённой сигнатурой и их вызывающих
вне диффа, опираясь на граф кода (Neo4j). Граф строится по **статическим** вызовам:

- tree-sitter-бэкенд пропускает динамические/рефлексивные/алиасные вызовы;
- при **live-ревью** инкрементальная досинхронизация графа в `prepare_review` выполняется
  **всегда** tree-sitter'ом, независимо от `GRAPH_BACKEND` (входящие `CALLS`-рёбра базового
  индекса сохраняются, но полнота для изменённых файлов — на уровне tree-sitter);
- даже точный SCIP не ловит чисто динамическую диспетчеризацию.

Текущий `blast-radius-prompt.md` содержит лишь **мягкое** упоминание неполноты
(стр. 17-20: «Recall depends on graph completeness … Frame findings as concrete but verify
each via `read_file`»). Нет жёсткого правила, как неполнота графа влияет на `confidence`
и формулировку находки → риск категоричных ложных утверждений «это сломает X».

## Объём

**В объёме:** правка только `plugin/skills/review-pr/references/blast-radius-prompt.md`
(markdown reference-промпт). Кода `reviewer/` НЕ касаемся.

**Вне объёма (возможный follow-up):** проброс реального признака бэкенда (`backend_used`)
в вывод `get_impact`, чтобы правило confidence стало условным (tree-sitter → обязательное
понижение; SCIP → можно увереннее). Это потребовало бы честного персиста `backend_used` в
`index_meta` (сейчас `set_index_meta`/`get_index_meta` хранят только `sha`) и проброса через
`ToolContext` → `format_impact`. Дешёвый runtime-хинт через `scip_available()` отвергнут:
он отдаёт *сконфигурированный* бэкенд и при live-ревью (граф фактически tree-sitter)
рискует **завысить** полноту и вернуть категоричность. Поэтому честный сигнал требует
полного персиста — непропорционально для S-задачи; критерий приёмки закрывается одним
промптом, т.к. граф считается потенциально неполным **по умолчанию**.

## Дизайн

Правка точечная: «мягкий» bullet (стр. 17-20) заменяется отдельной **обязательной**
секцией; остальные блоки промпта (различение «что ломает / что нет» — стр. 13-16; секция
Anchoring — стр. 22-29; привязка к схеме `analyze-prompt.md`; правило «пустой `get_impact`
→ пустой список находок») сохраняются и связываются со шкалой confidence.

Тело промпта — на английском (соглашение для reference-промптов); текст находок
(`message`/`suggestion`) агент по-прежнему пишет на языке оркестратора.

### Новая секция: `Confidence & graph completeness (mandatory)`

**1. Список вызывающих от `get_impact` — НИЖНЯЯ ГРАНИЦА.**
Граф строится по статическим вызовам; tree-sitter (всегда используется для
досинхронизированных изменённых файлов при live-ревью) и даже SCIP пропускают
динамические/рефлексивные/алиасные/обёрнутые декоратором вызовы. Следствия:
- НИКОГДА не утверждать, что изменение безопасно, что «затронуты только эти N вызывающих»
  или «остальное не заденет», опираясь на список. Отсутствие вызывающего в отчёте ≠ его
  отсутствие в коде.
- НЕ понижать `severity` до безобидной из-за пустого/короткого списка вызывающих.

**2. Шкала `confidence`** (float 0.0–1.0; кормит gate `publish_review` — быть честным):
- **0.8–0.9** — вызывающий прочитан через `read_file` И подтверждён как НЕ обновлённый
  через `get_changed_file_diff`, И слом контракта однозначен (новый **обязательный**
  параметр без дефолта / удалённый / переименованный параметр / изменённый порядок,
  ломающий позиционные/именованные вызовы).
- **0.5–0.6** — тип слома однозначен, но прочитан НЕ каждый вызывающий из списка, ЛИБО
  прочитан, но эффект зависит от контекста вызова.
- **≤ 0.4 (или опустить находку)** — спекулятивно: тип слома неясен или вызывающего не
  удалось проверить. Лучше отбросить, чем дать низкоуверенную догадку.

**3. Формулировка.** Непроверенные находки оформлять как просьбу — «проверьте, что
<вызывающий> по `path:line` соответствует новому контракту», а не категоричное «это
сломает X». Категоричный язык слома — только для проверенных однозначных случаев (0.8+).

### Сохраняется без изменений
- блок различения «что ломает / что нет» (нынешние стр. 13-16);
- секция Anchoring (привязка находки на строку изменённой сигнатуры, стр. 22-29);
- `category: "correctness"` и привязка к схеме `analyze-prompt.md`;
- правило: `get_impact` вернул «(… не найдено)» → пустой список находок.

## Связь с gate (почему это работает)

`confidence` в схеме находки — float, который `publish_review` сопоставляет с порогом
политики. Понижение `confidence` для непроверенных/неоднозначных blast-radius-находок →
такие находки отсекаются гейтом или уходят в сводку вместо inline-категоричного
комментария. Это и есть механизм исполнения критерия приёмки.

## Критерий приёмки

На tree-sitter-графе blast-radius-находки помечаются меньшей уверенностью; меньше ложных
категоричных утверждений. Критерий **качественный** — юнит-тестом не проверяется.

## Верификация

- Ручная вычитка обновлённого `blast-radius-prompt.md` на внутреннюю согласованность
  (шкала confidence ↔ блок «что ломает / что нет» ↔ Anchoring).
- Смоук: `.venv/bin/ruff check .` и `.venv/bin/pytest -q` остаются зелёными (изменяется
  только markdown; код `reviewer/` не трогаем — регрессий быть не должно).
- Полная проверка «меньше ложных категоричных» — через эвал-прогон ревью PR со сменой
  сигнатуры; вне рамок этой задачи.

## Риски

- Риск регрессии в коде ~0 (правится только промпт).
- Возможный ложный эффект: слишком агрессивное понижение confidence спрячет истинные
  сильные находки. Митигируется верхней ступенью шкалы (0.8–0.9 для проверенных
  однозначных сломов) — сильные истинные находки сохраняют высокий confidence.
