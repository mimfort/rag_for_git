# PRI-267 — единственный источник константы RRF k

Бриф: `docs/superpowers/briefs/2026-08-24-PRI-267-rrf-k-single-source.md`

## Задача

Константа слияния RRF объявлена трижды и независимо: питоновская `RRF_K = 60`
(`reviewer/retrieval/multiquery.py:26`) и числовой литерал `1.0/(60+rank)` в двух SQL —
`reviewer/index/store.py::hybrid_search` (строки 494, 496) и
`reviewer/tasks/store.py::TaskStore.search` (строки 270, 271). Литералов физически четыре: в
каждом SQL значение записано дважды — отдельно для ветки `bm25` и для ветки `ann`.

Ни один тест эти значения не связывает. Докстринг `RRF_K` уже утверждает «та же, что в
`store.hybrid_search` и `TaskStore.search`» — то есть связь задокументирована, но не проверена.
Расхождение `k` между слиянием подзапросов (`rrf_merge`) и RRF внутри одного гибрида прошло бы
молча: ранжирование поехало бы, тесты остались бы зелёными, а обнаружилось бы это в лучшем случае
просадкой метрики брифа, где причину искать уже негде.

## Решение

Расхождение делается **невозможным**, а не обнаруживаемым: числовой литерал уходит из SQL, значение
приезжает туда именованным параметром из единственного объявления.

### Дом константы

Новый модуль `reviewer/rrf.py`:

```python
"""Константа RRF — единственная в системе (PRI-267).

Живёт в корне пакета, а не в retrieval: её читают оба store
(reviewer/index/store.py, reviewer/tasks/store.py), которые лежат НИЖЕ
retrieval. Импорт retrieval→index развернул бы направление зависимости —
reviewer/retrieval/multiquery.py уже импортирует reviewer.index.refs.
"""

RRF_K = 60
```

Корень пакета выбран не по вкусу, а по направлению зависимостей: общий нижний предок
`reviewer/index/store.py` и `reviewer/tasks/store.py` — сам пакет `reviewer/`. Прецедент маленьких
нейтральных корневых модулей в проекте есть: `reviewer/gitutil.py`, `reviewer/versioning.py`.

### Параметризация SQL

В обоих store каждая из двух веток CTE `rrf` берёт значение параметром с **явным кастом**:

```sql
rrf AS (
    SELECT id, 1.0/(%(rrf_k)s::int + rank) AS s FROM bm25
    UNION ALL
    SELECT id, 1.0/(%(rrf_k)s::int + rank) AS s FROM ann
)
```

`params` в обоих методах уже именованные словари, поэтому добавляется ровно один ключ:
`"rrf_k": RRF_K`.

Каст `::int` — не косметика. Без него тип параметра выводится из контекста сложения, и результат
может разойтись между simple- и prepared-протоколом psycopg. С кастом тип детерминирован в обоих
режимах.

### Точка потребления в retrieval

`reviewer/retrieval/multiquery.py` теряет собственное объявление и импортирует
`from reviewer.rrf import RRF_K`. Сигнатура `rrf_merge(runs, k: int = RRF_K)` не меняется.

Реэкспорт `RRF_K` из `multiquery` **не сохраняется**: имя не импортируется больше нигде в
репозитории (проверено grep'ом по всему дереву), а сохранённый реэкспорт создал бы вторую точку
имени вместо совместимости, которую некому потреблять.

## Проверки

### Критерий 1 — «изменение k в одном месте красит тест»

Формулировка критерия написана под альтернативное решение (guard-тест поверх трёх литералов) и
после параметризации вырождается: мест больше не три, а одно, и изменить `k` «только в SQL»
физически нельзя — числа там нет.

Критерий закрывается в перевёрнутом виде — guard ловит **регрессию к литералу**. Unit-тест
`tests/test_rrf_k_single_source.py` (корень `tests/`, а не `tests/index/` или `tests/retrieval/`:
он покрывает оба store сразу и ни одной подсистеме не принадлежит — прецедент таких кросс-модульных
guard'ов в проекте есть, `tests/test_ci_gates.py`, `tests/test_infrastructure_policy.py`) на фейковом
пуле (паттерн `_PoolFactory` из `tests/tasks/test_subtask_store.py`) вызывает
`ChunkStore.hybrid_search` и `TaskStore.search`, перехватывает фактически переданные SQL и `params`
и утверждает:

1. `params["rrf_k"] == RRF_K` — значение реально доезжает до запроса;
2. плейсхолдер `%(rrf_k)s` встречается в SQL ровно дважды на каждый store — обе ветки CTE, не одна;
3. регулярное выражение числового литерала перед `+ rank` в тексте SQL не находит ничего.

Проверяется фактически передаваемое значение, а не форматирование текста. Пункт 3 остаётся
текстовым по необходимости, и его роль узкая: он ловит возврат литерала, а не подменяет пункт 1.
Урок соседнего guard'а (`tests/metrics/test_reexport_guard.py`) учтён — проверка по форме, а не по
случайной подстроке.

### Критерий 2 — «ранжирование не меняется»

Значение остаётся тем же (60), поэтому выдача обязана быть идентичной. Держится существующими
тестами `tests/retrieval/` и `tests/index/`; дополнительно разово сверяется `reviewer search` на
живой базе до и после правки — порядок результатов должен совпасть.

### Критерий 3 — «план запроса не деградировал»

Разовый `EXPLAIN` обеих форм запроса (с литералом и с параметром) на живой базе; вывод обеих форм
фиксируется в этом документе разделом «Замер EXPLAIN» при реализации.

Постоянный integration-тест на план сознательно не заводится: план здесь меняется один раз, а тест,
сверяющий `EXPLAIN`, краснел бы от версии PostgreSQL и накопленной статистики — то есть сообщал бы
о чём угодно, кроме регрессии этой правки.

## Документация

- `CLAUDE.md`, строки 422-426: абзац описывает долг как открытый и утверждает «SQL не импортируется,
  поэтому питоновской копии не избежать». После параметризации это неверно — копии в SQL не
  остаётся. Абзац переписывается: долг закрыт, объявление одно, и названо неочевидное — почему
  константа лежит в корне пакета, а не рядом с `rrf_merge`.
- `plugin/skills/solve-task/references/brief-format.md:35` — формула `SUM(1/(60+rank))` в тексте
  промпта скилла. По значению она остаётся верной, но разъедется так же молча, поэтому
  актуализируется вместе с кодом. Правка под `plugin/` меняет payload-digest, поэтому обязателен
  прогон `scripts/update_codex_plugin_manifest.py` — без него install-тесты краснеют.

## Запасная ветка

Параметризация решает задачу радикальнее, чем просил тикет: там guard-тест — шаг 1, а
параметризация лишь «рассмотреть». Если замер `EXPLAIN` покажет деградацию плана, решение
откатывается на guard-тест поверх трёх литералов (`inspect.getsource` + регулярное выражение,
закрепляющее и значение, и число вхождений). Это заранее предусмотренная ветка того же дизайна, а
не его переделка.

## Границы

- Значение `k` не выносится в `.review.yml` и не становится настройкой политики: SQL её не читает, а
  тюнинг RRF задачей не ставится.
- `reviewer/retrieval/retriever.py`, `search_base` и публичный `search_codebase` не затрагиваются:
  меняется только текст SQL внутри двух методов store и место объявления константы.
- Замер на корпусе не требуется — выдача не меняется по построению.
