# PRI-174 — безопасный контракт ошибок `search_codebase`

## Статус задачи

Исходную PRI-174 следует переписать. Разделение только на ошибки БД и embeddings
недостаточно: оно по-прежнему маскирует неожиданный инфраструктурный сбой под отсутствие
релевантного кода. Новый scope вводит явный трёхсостояний контракт без изменения ранжирования
или дополнительных сетевых вызовов.

## Цель

`search_codebase` должен различать:

1. корректно выполненный поиск без совпадений;
2. недоступность обязательного компонента поиска;
3. неизвестную внутреннюю ошибку.

Потребитель сможет перейти к локальному lexical fallback и не тратить токены и Voyage-вызовы
на бессмысленное переформулирование semantic-запроса.

## Архитектура

### Retriever

`Retriever.search_base` остаётся владельцем пайплайна поиска и вводит типизированную
`SearchUnavailableError` с конечной категорией компонента:

- `embeddings` — отказ `embed_query`;
- `storage` — отказ `hybrid_search`.

Исходное исключение сохраняется через exception chaining для server-side диагностики, но его
текст не становится частью публичного ответа.

Graph expansion и reranker остаются fail-soft. Их отказ не означает недоступность базового
поиска: Retriever логирует деградацию и возвращает результаты hybrid search в прежнем порядке.

### MCP-сервис

`MCPReviewService.search_codebase` переводит доменную ошибку в безопасный текстовый контракт:

- пустой `ContextPack` → `(ничего не найдено)`;
- `SearchUnavailableError("embeddings")` →
  `(поиск недоступен — embeddings)`;
- `SearchUnavailableError("storage")` →
  `(поиск недоступен — storage)`;
- любое другое исключение →
  `(поиск недоступен — внутренняя ошибка)`.

Неизвестная категория `SearchUnavailableError` также отображается как внутренняя ошибка.
MCP-сервис логирует исключение с traceback. Сообщение пользователю не содержит DSN, URL,
текстов ответов провайдеров, токенов или других деталей исключения.

## Поток данных

1. Skill вызывает `search_codebase`.
2. Retriever получает query embedding.
3. Retriever выполняет hybrid search.
4. Корректный пустой результат проходит как пустой `ContextPack`.
5. Отказ обязательного шага превращается в `SearchUnavailableError`.
6. MCP-сервис сериализует результат или безопасную категорию недоступности.
7. Skill распознаёт unavailable-note и не повторяет semantic search.

## Поведение глобального плагина

`plugin/skills/ask/SKILL.md` должен считать любой ответ с префиксом
`(поиск недоступен` сигналом к существующему локальному fallback через `Grep`/`Glob`/`Read`.
Пользователю сообщается, что ответ получен lexical-поиском и может быть менее полным.

`plugin/skills/solve-task/SKILL.md` не требует отдельной ветки по категории: его общий
fail-open контракт уже принимает unavailable-note. Бриф должен записать недоступность в
Constraints и продолжить работу с доступным контекстом, не повторяя `search_codebase`.

## Тестирование

### Retriever

- ошибка `embed_query` становится `SearchUnavailableError("embeddings")`;
- ошибка `hybrid_search` становится `SearchUnavailableError("storage")`;
- exception chaining сохраняет исходную ошибку;
- пустой search result возвращает пустой `ContextPack`;
- ошибки graph expansion и reranker по-прежнему дают fail-soft результат.

### MCP

- пустой `ContextPack` даёт ровно `(ничего не найдено)`;
- категории embeddings и storage отображаются в точные публичные сообщения;
- неизвестная категория и произвольное исключение дают
  `(поиск недоступен — внутренняя ошибка)`;
- текст исходного исключения отсутствует в публичном ответе;
- успешная line-numbered выдача не меняется.

### Плагин

- guard-тест фиксирует новый fallback-триггер в `reviewer_ask`;
- существующий локальный fallback и предупреждение пользователю сохраняются;
- `reviewer_solve-task` продолжает принимать unavailable-note без специального
  перечисления категорий.

## Критерии приёмки

- Инфраструктурная ошибка никогда не возвращается как `(ничего не найдено)`.
- Подлинно пустой результат сохраняет прежнее сообщение.
- Публичный ответ содержит только конечную безопасную категорию.
- `reviewer_ask` автоматически переходит к локальному lexical fallback.
- После unavailable-note skill не повторяет semantic search.
- Graph/reranker degradation не превращает доступный базовый поиск в ошибку.
- Новых сетевых вызовов и изменений алгоритма ранжирования нет.

## Вне scope

- Реализация локального lexical fallback внутри MCP-сервера.
- Изменение relevance scoring, reranking или cliff-отсечки.
- Новая telemetry для подсчёта повторных запросов.
- Унификация контрактов всех session-less инструментов.
- Публичная передача текста или типа исходного исключения.

## Рекомендуемый новый текст PRI-174

**Название:** `search_codebase: безопасно различать пустой результат и недоступность`

**Проблема:** `search_codebase` сейчас превращает любой сбой в `(ничего не найдено)`.
Потребитель не отличает отсутствие релевантного кода от отказа embeddings, storage или
неизвестной внутренней ошибки, поэтому может повторять semantic search и делать неверные
выводы.

**Что сделать:** ввести типизированную ошибку обязательных этапов Retriever, безопасно
отобразить конечные категории на MCP-границе и научить `reviewer_ask` переходить к
существующему lexical fallback по unavailable-note.

**Критерии приёмки:**

- инфраструктурная ошибка никогда не возвращается как `(ничего не найдено)`;
- подлинно пустой результат сохраняет прежнее сообщение;
- embeddings, storage и неизвестная ошибка получают безопасные конечные сообщения;
- исходный текст исключения не попадает в MCP-ответ;
- `reviewer_ask` переходит к локальному lexical fallback и не повторяет semantic search;
- graph/reranker degradation остаётся fail-soft;
- новых сетевых вызовов и изменений алгоритма ранжирования нет.
