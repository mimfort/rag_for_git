# PRI-248 — `prepare_task_context`: свернуть preflight и сбор контекста solve-task

Бриф: `docs/superpowers/briefs/2026-08-15-PRI-248-prepare-task-context.md`

## Проблема

`plugin/skills/solve-task/SKILL.md` — 430 строк, крупнейший файл плагина; он целиком
попадает в контекст оркестратора при каждом вызове скилла. Больше половины объёма —
детальные fail-open ветки, которые описывают **детерминированную** процедуру:
шаги 0.1–0.4 (чтение `reviewer status --json` через `uvx`, разбор `drift`, инкрементальный
`sync_board`, проверка теплоты сводок) и шаг 3 (subsystem prior, `get_task_context`,
`search_tasks`, `search_codebase`, тест-образцы). Это 8–12 тул-раундов, каждый со своим
выхлопом в контексте, и ни один из них не содержит решения, требующего LLM.

В проекте для такого случая уже принят противоположный паттерн: `sync_board` описан как
server-side ETL, а `prepare_review` собирает весь контекст PR одним серверным вызовом.

## Что делаем

Session-less MCP-тул `prepare_task_context`, который отдаёт весь детерминированный контекст
одним payload, и реструктуризация `SKILL.md` по образцу `review-pr` (ядро + `references/`).
За LLM остаётся только то, что требует суждения: relevance-фильтр, сборка брифа, решения по
режимам и стратегии исполнения.

## Решение развилки PRI-246: измерение — фаза 1, но офлайн

Спайк PRI-246 требует step-level разбивку расхода **до** дизайна консолидации, иначе её
эффект недоказуем. Буквальное прочтение («поставить рантайм-хук, накопить прогоны, потом
проектировать») блокирует задачу и добавляет прод-код ради разовой диагностики.

Ключевое наблюдение: атрибуция расхода по под-шагам — чистая функция от транскрипта.
Assistant-ход относится к под-шагу по имени тула, который он вызвал, а транскрипты прошлых
прогонов solve-task уже лежат в `~/.claude/projects/*.jsonl` — тот же корпус, которым
пользовался PRI-246.

Поэтому:

- инструментация реализуется как **офлайн-анализатор** `eval/solve_task_metrics/steps.py`,
  переиспользующий `WEIGHTS` из `eval/solve_task_metrics/cost.py`;
- baseline «до» считается ретроспективно, на существующем корпусе, до единой строки
  реализации тула;
- «после» замеряется тем же анализатором на прогонах с новым тулом — одна линейка на обе
  точки, как того требует критерий приёмки №6;
- новых хуков в `plugin/hooks/` не добавляется; прод-путь не трогается.

Если офлайн-замер покажет, что доля преflight и сбора контекста в взвешенной цене этапа
мала (порог: < 15 % взвешенной цены), это фиксируется в отчёте и служит основанием
пересмотреть объём консолидации до передачи в реализацию.

## Контракт тула

```python
prepare_task_context(
    repo: str,
    key: str,
    branch: str | None = None,
    path: str | None = None,
    warm_board: bool = True,
) -> dict
```

`key` — ключ задачи по `key_pattern` доски либо свободный текст (board-less режим:
формулировка пользователя используется как запрос ретрива).

Payload:

| Секция | Содержимое |
|---|---|
| `preflight` | `{branch, indexed_sha, drift, summaries, chunks, graph_nodes}` |
| `task_board` | разрешённый generic-конфиг (`type`/`project`/`key_pattern`/`create_target`/`done_target`/`options`), без кредов |
| `task` | нормализованный `TaskBrief` из стора либо `null` |
| `related` | `{linked: [...], similar: [...]}` — сырые выдачи `get_task_context` и `search_tasks` |
| `subsystems` | выдача `get_subsystem_summaries` с `query` по задаче |
| `code` | выдача `search_codebase` (нумерованные строки) |
| `test_exemplars` | выдача `search_codebase(include_tests=True)` по тест-запросу |
| `gaps` | список структурных записей о пробелах |
| `warnings` | нефатальные предупреждения (например, результат прогрева доски) |

Три инварианта контракта:

1. **`drift` считает сервер.** Клон резолвится через таблицу `repo_clone`
   (`MCPReviewService._repo_clone_path`, паттерн PRI-235); `path` — необязательный override
   клиента. Это устраняет запуск `uvx --from rag-reviewer reviewer status --json` со стороны
   скилла. При удалённом MCP клона на сервере нет → `drift = null` и запись в `gaps`; это
   штатный случай, а не ошибка.
2. **`warm_board=True` втягивает инкрементальный `sync_board`** внутрь вызова. Это
   чтение доски и запись в стор reviewer, а не запись в доску, поэтому под правило
   «подтверждать запись в доску» операция не попадает. Сбой прогрева → `warnings`, payload
   отдаётся.
3. **Секции ретрива — строки существующих форматтеров**, а не новая структура. `code`,
   `test_exemplars` и `subsystems` возвращают ровно то, что сейчас возвращают
   соответствующие session-less тулы, включая нумерацию строк для цитирования `path:line`
   без повторного `Read`. Второй формат выдачи означал бы второй набор дефектов в нём.

**Дедуп `linked ∪ similar` тул не делает** — он остаётся суждением LLM, как и relevance-фильтр:
эти шаги требуют оценки «напрямую информирует реализацию», а не механической операции.

### Fail-open

Каждая секция собирается в своём `try/except`; сбой не прерывает вызов, а добавляет запись в
`gaps` вида `{"section": ..., "reason": ...}`. Задокументированные сценарии и их поведение:

| Сценарий | Поведение |
|---|---|
| Доска выключена (`task_board:` пуст) | `task_board = null`, `task` из стора, `gaps: board_disabled` |
| Доска недоступна (сеть/креды) | прогрев в `warnings`, остальное собирается |
| Postgres лежит | `code`/`test_exemplars`/`related.similar` пусты, `gaps` заполнены |
| Neo4j лежит | `related.linked` пуст, `preflight.graph_nodes = null`, `gaps` |
| Индекс отсутствует | `drift = null`, `indexed_sha = null`, `gaps: no_index` |
| Сводки не построены | `summaries = 0`, `subsystems` пуст, `gaps: no_summaries` |

Скилл на основании `gaps` печатает те же сообщения пользователю, что и сегодня, и помечает
пробелы в брифе. Наблюдаемое поведение не меняется — меняется число раундов.

### Что тул НЕ делает

Существующие session-less тулы сохраняются без изменений: их используют другие скиллы
(`ask`, `create-task`, `pr-walkthrough`) и сам solve-task для ручного добора — графовые
расширения (`implementations`/`callers`/`related_symbols`), `get_pr_diff` и lazy expansion
остаются отдельными вызовами по суждению LLM. `prepare_task_context` — агрегатор поверх них,
не замена.

## Реструктуризация SKILL.md

Ядро сокращается до ~120 строк: классификация входа, вызов `prepare_task_context`,
relevance-фильтр, скелет брифа, персист, хендофф. Детали уезжают в `references/`, как в
`review-pr`, и подключаются маркером `<!-- include: ... -->`:

- `references/preflight.md` — сбойные ветки, интерпретация `gaps`, ветка ручного реиндекса;
- `references/brief-format.md` — скелет брифа, relevance-фильтр, правила dropped/дедупа;
- `references/modes.md` — стартовый опрос, режимы, стратегии, run-state;
- `references/context-gathering.md` — ручной добор: графовые тулы, `get_pr_diff`,
  lazy expansion, тест-образцы.

## Guard-тесты

Тикет называет три файла. Фактически сырой `plugin/skills/solve-task/SKILL.md` читают
**восемь**: `test_solve_task_brief.py`, `test_preflight_guardrail.py`,
`test_solve_task_modes.py`, `test_ask_uses_summaries.py`, `test_create_task_skill.py`,
`test_finish_task_skill.py`, `test_readme_grounding_block.py`,
`test_review_pr_store_first.py`. Мигрируются все восемь — иначе критерий приёмки №2
выполняется на треть, а остальные ломаются молча ровно так, как тикет и предупреждает.

Резолвер `assemble()` (`tests/skills/test_assembled_prompts.py:12`) сейчас подставляет
**только** пути вида `_common/*.md` и делает это **нерекурсивно**. Как только `SKILL.md`
начнёт включать `references/*.md`, которые сами включают `_common/*.md`, резолвер перестанет
собирать полный текст. Он расширяется: любой путь относительно `plugin/skills/` и
рекурсивный резолв с защитой от цикла.

## Тестирование

- Юнит-тесты `prepare_task_context` на фейковых компонентах, без живых Postgres/Neo4j/сети:
  happy path и каждая строка таблицы fail-open выше — отдельным тестом.
- Тест инвариантов контракта: секции ретрива идентичны выдаче одиночных тулов на тех же
  входах (защита от расползания второго формата).
- Сетевые пути — под маркером `integration`.
- Юнит-тесты офлайн-анализатора `steps.py` на синтетическом транскрипте.
- Восемь мигрированных guard-файлов + тесты самого расширенного `assemble()`.

## Сопутствующее

- Пересборка codex-манифестов (`update_codex_plugin_manifest.py`) — обязательна: меняется
  содержимое `plugin/`, значит меняется payload-digest и install-тесты покраснеют.
- `README.md` и `README.ru.md` — обновить описание потока solve-task синхронно.

## Критерии приёмки

1. Путь до брифа проходит существенно меньше тул-раундов; сокращение подтверждено замером.
2. Все guard-тесты скилла проверяют собранный `assemble()` текст, а не сырой `SKILL.md`;
   мигрированы все восемь файлов.
3. Поведение во всех шести задокументированных сбойных сценариях совпадает с нынешним:
   скилл не падает и помечает пробел в брифе.
4. Новый тул покрыт юнит-тестами без живых внешних сервисов; сетевые пути — под `integration`.
5. codex-манифесты пересобраны, install-тесты зелёные.
6. Эффект подтверждён замером во взвешенных единицах (`fresh_in×1, output×5,
   cache_write×1.25, cache_read×0.1`) до/после, посчитанным одним анализатором.
