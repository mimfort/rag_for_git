# PRI-251 — перечисление семейства однотипных символов

Бриф: `docs/superpowers/briefs/2026-08-14-PRI-251-implementations-family-blind-spot.md`

## Проблема

На задачах с широким blast radius («добавить поле во все провайдеры») core-recall брифа
падает заметно ниже медианы: PRI-223 24% при 25 файлах ядра, PRI-215 36% при 14,
PRI-225 39% при 18, PRI-196 50% при 10 против медианы 61% по выборке спайка PRI-246.

Причина не в потолке выдачи. Корреляция между числом названных в брифе файлов и числом
реально затронутых файлов ядра равна 0.073; ни одна задача выборки не упирается в
`context_limits.search_codebase.ceiling = 15` (максимум predicted — 12). Ретрив приносит мало
и почти всё по делу, но не сообщает, что найденный файл — один представитель семейства из N
однотипных.

Инструмент, который обязан отвечать на вопрос «кто ещё реализует этот контракт», для семейств
провайдеров пуст: `implementations("reviewer/tasks/boards/restbase.py#RestBoardBase")` возвращает
`(implementations не найдены)`, хотя восемь адаптеров наследуют этот класс явно и номинально.
Скилл `solve-task` при этом прямо инструктирует предпочитать `implementations` для
OO/registry/dispatch-задач — то есть отправляет к инструменту, который на этом репозитории для
таких семейств молчит.

## Корневая причина

Она не та, что предполагал тикет. Тикет исходил из того, что scip-python не размечает
наследование на уровне класса и что чинить нужно чтение `si.relationships` в
`reviewer/graph/scip.py:42-51`. Измерение это опровергает.

**Наш парсер корректен.** На контрольном репозитории (класс с переопределением метода и класс
без переопределения, база в соседнем модуле) `parse_scip` эмитит и метод-уровневые, и
класс-уровневые рёбра:

```
('pkg/adapters.py#OverridesClose', 'IMPLEMENTS', 'pkg/base.py#RestBase')
('pkg/adapters.py#OverridesClose.close', 'IMPLEMENTS', 'pkg/base.py#RestBase.close')
('pkg/adapters.py#NoOverride', 'IMPLEMENTS', 'pkg/base.py#RestBase')
```

**scip-python 0.6.6 не эмитит `SymbolInformation` для класса, упомянутого в файле выше своего
определения.** В индексе реального репозитория DEFINITION-occurrence для `AsanaBoard#` есть
(asana.py:172), но `SymbolInformation` для этого символа отсутствует во всех документах и во
внешних символах. Без `SymbolInformation` нет и `si.relationships` — читать нечего.

Корреляция по всему `reviewer/` (199 классов): из 185 классов, получивших `SymbolInformation`,
forward-referenced — **0**; из 14 не получивших — **13**. Единственное исключение
(`_LockedDestination`) — `@dataclass(frozen=True)`. Все 11 адаптеров досок регистрируются в
`provider_spec()`, объявленной выше класса, и потому попадают ровно в этот провал. Размер класса
ни при чём: `MCPReviewService` (2990 строк) `SymbolInformation` получает, `SubtaskRequest`
(11 строк) — нет.

Следствие для дизайна: SCIP как источник класс-уровневого наследования ненадёжен принципиально,
и правка на нашей стороне парсера невозможна — терять данные нечего, их не присылают.

Отдельный, независимый провал: `TaskBoardProvider` (`reviewer/tasks/boards/base.py:110`) и
`VCSProvider` (`reviewer/vcs/base.py:89`) объявлены как `typing.Protocol`. Адаптеры не наследуют
их номинально, поэтому рёбер наследования для них не даст ни один бэкенд — структурная типизация
не выражается рёбрами графа в принципе.

## Решение

Три слоя, каждый закрывает свой класс провала.

### Слой 1 — наследование из синтаксиса

`build_graph_from_files` (`reviewer/graph/builder.py:158`) сейчас эмитит только `CALLS`.
Дополняем его извлечением `class_definition` → список суперклассов и резолвингом имени базы через
уже существующий import-aware механизм (`_resolve_call` умеет имя → узел с приоритетом
локальные определения → импортированные имена → star-импорты → глобальный fallback). Каждая
резолвленная база даёт ребро `(класс, IMPLEMENTS, база)`.

На SCIP-ветке (`reviewer/graph/backend.py:49`, `build_with_scip`) эти рёбра **объединяются** с
рёбрами SCIP с дедупликацией. Разделение ролей:

- SCIP остаётся источником точных `CALLS` и метод-уровневых `IMPLEMENTS` (type-aware, 327 рёбер);
- наследование классов приходит из синтаксиса, который pyright потерять не может.

Слияние, а не замена: tree-sitter резолвит базу по имени и на неоднозначных именах может ошибиться,
поэтому он добавляет только рёбра наследования, не трогая `CALLS`.

Это закрывает критерий приёмки 1.

### Слой 2 — семейство по структурному контракту

Для Protocol рёбер нет и не будет, поэтому принадлежность к семейству считается иначе: класс
принадлежит семейству контракта, если покрывает **весь** набор методов этого контракта, считая
унаследованные.

Учёт унаследованных обязателен и возможен только после слоя 1. Измерение на текущем репозитории:
строгое сопоставление «только собственные методы» находит 6 адаптеров из 11 — остальные не
переопределяют `close()`, он достаётся им от `RestBoardBase`. С учётом наследования по цепочке
`IMPLEMENTS` набор становится точным:

| Сопоставление | Найдено | Ложных срабатываний |
|---|---|---|
| только собственные методы | 6 из 11 | 0 |
| с унаследованными | **11 из 11** (+ сам `TaskBoardProvider`) | **0** |

Проверено по всем классам `reviewer/`. Девять методов `TaskBoardProvider` и восемь методов
`VCSProvider` — фильтр достаточно узкий, чтобы совпадение по полному набору не давало шума.

Это закрывает критерий приёмки 2, включая три легаси-адаптера (`JiraCloudBoard`, `YougileBoard`,
`YouTrackBoard`), у которых нет общей базы и которых слой 1 не находит.

### Слой 3 — явная полнота ответа

Молчаливая пустота там, где семейство существует, хуже ошибки: она неотличима от «семейства нет».

Вводится session-less MCP-тул `family(repo, node_id, branch)`, отвечающий на вопрос «кто ещё
такой же». Он объединяет сигналы в порядке убывания надёжности — наследование (подклассы и
сиблинги по `IMPLEMENTS`) и структурное соответствие контракту — и в каждом ответе сообщает,
какие сигналы сработали и полон ли ответ.

`implementations` сохраняет свой контракт (входящие `IMPLEMENTS`), но перестаёт отвечать голым
`(implementations не найдены)`, когда узел — класс, а другие сигналы семейство находят: ответ
явно указывает, что прямых наследников нет, а семейство есть, и называет `family` как способ его
получить.

Это закрывает критерий приёмки 3.

### Использование в solve-task

Скилл `solve-task` инструктируется вызывать `family` для символов, центральных для задачи, и
выносить в бриф найденное семейство целиком, а не одного представителя.

`Retriever` намеренно не трогаем. Структурный сигнал «член семейства из N» отдаётся тулом по узлу;
детектор внутри `Retriever.search_base` дал бы ту же информацию ценой правки горячего пути ретрива.
Текстовый детектор по формулировке задачи отвергнут отдельно: у PRI-225 сигнал косвенный
(«generic contract», без слов «все»/«каждый»), то есть на реальных задачах он ненадёжен.

## Тестирование

Поведение закрепляется на реальных семействах репозитория (критерий приёмки 5):

- **Юнит, парсер SCIP** — сборка минимального `scip_pb2.Index` вручную, по образцу
  `tests/graph/test_backend.py:21`. Фиксирует, что класс-уровневые рёбра из SCIP по-прежнему
  читаются, когда `SymbolInformation` присутствует.
- **Юнит, tree-sitter** — извлечение наследования из исходника, включая базу из другого модуля,
  многократное наследование и forward-referenced класс (тот самый случай, который теряет SCIP).
- **Юнит, слияние бэкендов** — рёбра наследования присутствуют после `build_with_scip`, даже когда
  SCIP их не прислал; дубликаты схлопнуты.
- **Юнит, структурное семейство** — 11 адаптеров досок находятся полностью, включая три легаси;
  два `VCSProvider`-провайдера находятся; ложных срабатываний по репозиторию нет.
- **Юнит, MCP-тул** — форвардинг аргументов и форма ответа по образцу
  `tests/mcp/test_server_tools.py:148`; отдельный тест на то, что частичный ответ помечен
  частичным, а пустой при существующем семействе не возвращается.
- **Integration** — реальный `scip-python` на временном репозитории, по образцу
  `tests/graph/test_backend_integration.py:53` (`@pytest.mark.skipif(shutil.which(...) is None)`):
  фиксирует упомянутый выше дефект upstream как регрессионный тест. Если будущая версия
  scip-python начнёт эмитить `SymbolInformation` для forward-referenced классов, тест это заметит,
  а слияние из слоя 1 останется корректным (дедупликация).

## Измерение

Критерий приёмки 4 требует подтверждённого числами роста core-recall на bulk-подвыборке.
Харнесс PRI-250 (`eval/solve_task_metrics`) уже в `dev` и даёт срез, историю и сравнение, но
понятия «bulk-подвыборка» в нём нет — его нужно ввести: подвыборка задач со знаменателем ядра
**≥ 10 файлов** и отдельной строкой core-recall по ней в отчёте. Порог взят из анализа PRI-246:
именно на нём там разделялись выборки (при `expected_core ≥ 10` медиана predicted 5.0, при
`expected_core < 10` — 6.0) и в него попадают все четыре задачи-развёртки, давшие провал
(PRI-223 — 25 файлов, PRI-225 — 18, PRI-215 — 14, PRI-196 — 10).

Базовая линия снята на коммите `10ea008`: core-recall медиана 56%, среднее 60%, N=35, медианный
размер знаменателя ядра 4. Порядок замера: срез до правки → правка → срез после → сравнение.

Замер по построению отложенный: core-recall считается по брифам, а брифы появляются только у
задач, решённых после правки. Первый честный замер возможен не раньше, чем накопится
bulk-подвыборка новых брифов; до этого рост подтверждается только на пересобранных брифах
известных bulk-задач.

## Документация

Критерий приёмки 6 требует, чтобы ожидания от тула совпадали с реальностью. В `CLAUDE.md`
(раздел неочевидных фактов) и в обоих README фиксируется: класс-уровневое наследование в графе
приходит из tree-sitter, а не из SCIP, потому что scip-python не эмитит `SymbolInformation` для
forward-referenced классов; SCIP остаётся источником `CALLS` и метод-уровневых `IMPLEMENTS`;
Protocol-контракты рёбер не имеют и обслуживаются структурным сигналом; `family` — способ
перечислить семейство целиком.

Докстринги `implementations` (`reviewer/mcp/service.py:1791`) и `implementations_detailed`
(`reviewer/graph/store.py:108`) сейчас обещают «класс → его подклассы» и «точны после полного
`reviewer index` с SCIP». После правки первое становится правдой, второе — уточняется.

## Границы

- Upstream-дефект scip-python не чиним и не обходим внутри SCIP-ветки: наследование берётся из
  независимого источника.
- Структурное соответствие контракту считается по именам методов, а не по сигнатурам. Для девяти-
  и восьмиметодных контрактов этого достаточно; сравнение сигнатур не добавляется, пока не
  появится семейство, где имена совпадают, а формы расходятся.
- `family` не пытается угадывать семейства по каталогу или форме имени файла: оба сигнала выше
  дают точный ответ на реальных семействах репозитория, а эвристика по путям добавила бы шум,
  который некому проверить.
