# Словарь причин недоступности источника контекста (PRI-274 + PRI-272)

Бриф: `docs/superpowers/briefs/2026-09-05-PRI-274-PRI-272-storage-cause-vocabulary.md`

## Задача

`prepare_task_context` возвращает обеднённый контекст в двух случаях, и ни в одном из них
пользователь не узнаёт настоящую причину.

**PRI-274.** При живых хранилищах исчерпание пула (`pg_pool_max_size = 4`) неотличимо от
остановленных контейнеров: `PoolTimeout` — подкласс `psycopg.OperationalError`, который
`is_storage_unavailable` покрывает целиком. Пользователю советуется `reviewer start` — команда уже
выполнена и делу не поможет; настоящее лекарство — поднять размер пула или снизить параллелизм.

**PRI-272.** При живых хранилищах и недоступном Voyage секции возвращаются пустыми, причина
классифицируется как `unknown`, а формулировка «задачи нет в сторе» указывает на доску вместо
эмбеддера. Формально классификация верна — Voyage не хранилище, — но результат для пользователя
ровно тот, ради устранения которого делался PRI-268.

Задачи решаются одной спекой: обе отвечают на один вопрос — какой класс причины получает сбой, —
и правят один классификатор, одну точку записи, одного клиента и одни тесты.

## Решения

### 1. Пул остаётся внутри класса `storage_unavailable`

`PoolTimeout` **не выводится** из `is_storage_unavailable`. Вывести его — значит лишить
`_StorageState` возможности замкнуть его на первом же сбое, и вернуть 8 таймаутов по 30 с вместо
одного: прямая регрессия PRI-268, PRI-275 и PRI-276.

Отличимость даёт `cause_detail` — механизм PRI-277 без изменений:

```
cause:        "storage_unavailable"
cause_detail: "pool_exhausted"
remedy:       null
reason:       "свободных соединений в пуле не осталось"
```

Критерии приёмки PRI-274 выполняются полностью: случай отличим по наблюдаемым полям ответа,
`reviewer start` не советуется, классификация решается типом исключения, текст с DSN наружу не
идёт.

Решение принимается `isinstance(exc, psycopg_pool.PoolTimeout)` **до** текстовых паттернов
`_DETAIL_PATTERNS`: тип конкретнее текста, и на этом же основании `auth_failed` проверяется раньше
`missing_database`.

### 2. Эмбеддер получает собственный класс причины

`CAUSE_EMBEDDER_UNAVAILABLE = "embedder_unavailable"` — равноправный класс, не `cause_detail`.
Уточнять им `storage_unavailable` было бы ложью: Voyage не хранилище, контейнеры подняты,
`reviewer start` не лечит.

```
cause:        "embedder_unavailable"
cause_detail: null
remedy:       null
reason:       "эмбеддер не отвечает"
```

`remedy` остаётся `null`: локальной команды-лекарства у внешнего API нет.

Класс решается типом: `voyageai.error.VoyageError` и его наследники, **за вычетом**
`RateLimitError` — тот штатно ретраится в `with_voyage_retry` и недоступностью не является.
Импорт `voyageai` — ленивый, внутри функции, как в `index/embeddings.py:45`.

### 3. Классификация живёт в одном модуле

Оба класса и оба уточнения остаются в `reviewer/storage_health.py`. Словарь причин — один
вопрос, и на него должен отвечать один файл; PRI-277 сводила эти решения в одно место, разносить
их обратно по двум модулям значило бы отменять ту работу. Имя модуля становится шире своего
содержания — это лечится докстрингом, а переименование в `source_health` отложено: оно
затрагивает четыре файла импортов и утопило бы суть задачи в шуме.

### 4. Замыкание обобщается с хранилищ на источники

`_StorageState` сегодня замыкает по бэкендам (`postgres`, `graph`). К ним добавляется третий
источник — `embedder`, — а состояние начинает хранить **класс причины** по источнику, а не
подразумевать одну константу. `_storage_gap` берёт `cause` оттуда.

Раздельность обязательна по тому же доводу, что и в PRI-276: мёртвый Voyage не должен отменять
секции, которым нужен только Postgres, и наоборот.

### 5. Причина проводится через два fail-soft барьера, а не через три

На пути контекста задачи барьеров два:

| Секция | Вызов | Барьер |
|---|---|---|
| `related.similar` | `TaskService.search_hits` | `except Exception → None` |
| `code`, `test_exemplars` | `MCPReviewService._search_codebase_multi` | `except Exception → "(ничего не найдено)"` |
| `subsystems` | `get_subsystem_summaries` | барьера нет — уже пробрасывает |

Публичный `search_codebase` в путь контекста не входит и **не меняется вовсе**: его тишина —
сознательный контракт `/ask`, грунтовки и review-pr, тот же принцип, по которому PRI-255 не
тронула `search_base`.

Оба барьера получают keyword-only `strict: bool = False` — форма, введённая PRI-275 для
`_repo_clone_path`. При `strict=True` пробрасывается только распознанный сбой эмбеддера; все
прочие сбои остаются fail-soft, потому что обработать их вызывающему нечем. `strict=True`
передаёт единственный вызывающий — `_TaskContextDeps`.

### 6. Секция `task` лечится структурным признаком синка

`deps.task` не бросает: задачи действительно нет в сторе, потому что её туда не пустил упавший
`warm_board`. Проброс здесь не поможет — причина рождается этажом выше.

`index_batch` теряет объект исключения: `embed_err` — строка `f"embedder: {type(e).__name__}: {e}"`,
а `retry_required=True` ставится одинаково при сбое эмбеддера и при сбое стора. Поэтому:

- рядом с существующим локальным замыканием `storage_down` появляется `embedder_down`;
- результат задачи получает машиночитаемое поле `failure` (`"embedder"` | `"storage"` | отсутствует),
  заполняемое там, где объект исключения ещё жив;
- сводка синка (`sync_board` counts, тот словарь, что уже несёт `enumerated`/`changed`/`failed`)
  получает булев агрегат `embedder_failed` — истинный, когда хотя бы у одной задачи батча
  `failure == "embedder"`. `build_task_context` читает именно его, а не разбирает строки
  `warnings`: текст сообщения драйвера — чужой формат, зависящий от версии клиента Voyage.

`warm_board` уже выполняется раньше секции `task` (`task_context.py:227` против `:239`), поэтому
порядок менять не требуется. Прочитав признак, `build_task_context` взводит источник `embedder`,
и gap секции `task` получает верный класс и формулировку «задача не проиндексирована: эмбеддер не
отвечает» вместо «задачи нет в сторе».

### 7. Клиент ветвится по классу, а не по одному его значению

Шаг 0a в `plugin/skills/solve-task/references/preflight.md` сегодня ищет равенство
`cause == "storage_unavailable"`. Новый класс мимо такой проверки пройдёт молча — ровно тот
дефект, который PRI-277 обошла, намеренно не трогая `cause`.

Шаг переписывается на общий вид: найти gap с названным классом (`cause != "unknown"`), назвать
класс пользователю, предложить `remedy` только когда он есть, уточнить `cause_detail`, когда он
заполнен. Вариант «Поднять сейчас» по-прежнему показывается лишь при наличии `remedy`.

Guard-тест в `tests/skills/` фиксирует, что набор классов, названных в скилле, совпадает с
набором в `storage_health` — иначе следующий класс снова разъедется с клиентом молча.

Правка `plugin/**` меняет codex payload-digest, поэтому в объём входит прогон
`update_codex_plugin_manifest.py`.

## Совместимость

Расширение словаря `cause` — изменение публичного контракта MCP-тула. Задеплоенный скилл прежней
версии ветвится на равенство `storage_unavailable`, поэтому незнакомый класс он пропустит и
промолчит — то есть поведёт себя ровно как сегодня. Деградация безопасная, синхронного обновления
клиента не требует.

Контракт PRI-275 сохраняется: `PoolTimeout` остаётся внутри `is_storage_unavailable`, и тест
`tests/mcp/test_service.py::test_task_context_deps_preflight_raises_and_stops_after_one_store_call`
остаётся зелёным без правок.

## Тестирование

- **Классификатор** (`tests/test_storage_health.py`): `PoolTimeout` → `detail=pool_exhausted`,
  `remedy=None`, при этом `is_storage_unavailable` по-прежнему `True`; ошибки `voyageai` →
  `embedder_unavailable`; `RateLimitError` → **не** `embedder_unavailable`; порядок «тип раньше
  текста» закреплён случаем, несущим оба признака.
- **Payload** (`tests/mcp/test_prepare_task_context.py`): при мёртвом эмбеддере и живых хранилищах
  класс проставлен всем зависящим секциям, включая `task`; при исчерпании пула `remedy` пуст;
  замыкание считается **числом заходов в источник**, а не временем.
- **Синк** (`tests/tasks/test_service_batch.py`): смешанный стор, где сбой эмбеддера и сбой стора
  происходят в одном батче, — поле `failure` различает их.
- **Клиент** (`tests/skills/`): набор классов в тексте скилла совпадает с набором в коде.
- **Мутационная проверка guard-тестов.** Каждый новый guard проверяется снятием проверяемого
  условия на копии модуля вне рабочего дерева: тест обязан покраснеть. Guard, зелёный по
  построению, не проверяет ничего — этот класс дефекта уже ловили в PRI-268.

## Вне скоупа

- Переименование `storage_health` → `source_health`.
- Ретрофит публичного `search_codebase`, `/ask`, грунтовки и review-pr на строгий режим.
- Ретрай или деградация при недоступном эмбеддере — задача сообщает причину, а не чинит её.
- PRI-273 (история прогона) — отдельная дорожка, по коду не пересекается.
