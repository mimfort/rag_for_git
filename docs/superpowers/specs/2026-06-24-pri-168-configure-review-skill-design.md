# PRI-168 — Скилл `reviewer_configure-review`: интерактивная настройка контекст-слоя `.review.yml`

**Дата:** 2026-06-24
**Задача:** PRI-168 (alias; основной ключ `ID-168`) — «Скилл для обновления .review.yml: ignore-правила, depth-оверрайды, разделение по слоям»
**Связанная:** PRI-161 (фундамент контекст-слоя: `paths.ignore`, `summary_cluster_depth_overrides`, `depth_for`)
**Статус:** дизайн согласован, готов к плану

## 1. Контекст и постановка

`.review.yml` несёт «контекст-слой» (PRI-161): что игнорировать при индексации/ревью и как кластеризовать сводки подсистем. Сейчас файл правят руками; на новом проекте это непрозрачно (какой `summary_cluster_depth`? какие поддеревья дробить глубже? что вписать в `paths.ignore`?). Задача — скилл, который сканирует репозиторий, рекомендует осмысленный контекст-слой и редактирует `.review.yml` под проект.

### 1.1 Ключевая находка при разборе (меняет постановку)

Исходная задача просила «дефолтный ignore-список» (`.venv`, `node_modules`, `__pycache__`, `dist`, `build`, `.git`), т.к. они якобы «попадают в индекс и сводки». **В текущей архитектуре это не воспроизводится** — весь конвейер работает только по **трекаемым git-файлам**:

- **Вектора:** `reviewer/entrypoints/cli.py::index` → `gitutil.list_python_files()` = `git ls-tree -r --name-only <ref>` — только трекаемое.
- **Граф:** `reviewer/graph/backend.py` создаёт временный **git worktree** на ref (`add_worktree`) и гоняет `scip-python index .` внутри него (`reviewer/graph/scip.py:72`); worktree содержит только трекаемые файлы. Tree-sitter-фоллбэк работает по тому же списку `files`.
- **Сводки:** `reviewer/mcp/service.py::list_subsystem_clusters` → `store.list_base_members()` — наследует векторный индекс.

Следствие: gitignored-и-незакоммиченный мусор (нормальный случай для `.venv` и пр.) физически невидим всем трём слоям — git отсекает его на входе. Поэтому **дефолтный ignore-список выведен из скоупа** (защищал бы только от *закоммиченного* мусора — редкий случай). Скилл сканирует ровно трекаемый набор и фокусируется на том, что из git **не выводится**: глубине кластеризации и ignore для трекаемых, но шумных путей.

## 2. Скоуп

**В скоупе** (одна спека → один план): новый интерактивный скилл, редактирующий **существующую** схему `.review.yml`:

- `summary_cluster_depth` — глобальная глубина кластеризации сводок;
- `summary_cluster_depth_overrides` — per-prefix переопределения глубины (longest-prefix-match по сегментам директории, как `depth_for`);
- `summary_topk_threshold` — порог масштаба приора сводок;
- `paths.ignore` — для **трекаемых** шумных путей (eval, fixtures, generated, vendored, migrations, data).

**Вне скоупа (явно):**

- (B) Backend «раздельный ignore по слоям» (вектора/граф/сводки) — отдельной задачей; скилл работает против текущей плоской схемы.
- (C) Дефолтный ignore-список в backend — снят (см. §1.1).
- Любой Python/backend-код, миграции схемы `.review.yml`, новые ключи.
- Авто-запуск пересбора индекса/сводок.
- Обход файловой системы / детект нетрекаемого мусора.
- Index-aware рекомендации (запрос `list_subsystem_clusters`) — скилл должен работать **до** первой индексации.

## 3. Архитектура решения

Деливерабл — один файл: `plugin/skills/configure-review/SKILL.md`.

- Тело скилла — по-английски (экономия токенов, как у остальных скиллов), но скилл инструктирует **отвечать пользователю по-русски**.
- Скилл **автономен**: использует только `git` (через Bash) и редактирование файла. Не требует reviewer-MCP, Postgres, Neo4j, доски — поэтому применим на чистом репо до индексации.
- Режим работы — **«черновик → правки»**: скилл сразу генерирует рекомендованный черновик, показывает его + diff, пользователь точечно правит. Не пошаговый опросник.

Имя скилла: `reviewer_configure-review` (согласовано). Описание (`description` во фронтматтере) — триггеры вида «настроить .review.yml», «configure review config», «настрой контекст-слой», «tune cluster depth», «что игнорировать в ревью».

## 4. Pipeline скилла

0. **Preflight.** Резолв пути репо (`git rev-parse --show-toplevel`) и рабочей ветки (`git branch --show-current`; если пусто/detached — взять текущий HEAD-ref). Проверка, что это git-репо (`git rev-parse --git-dir`). Если нет — сообщить по-русски и остановиться. Reviewer-MCP/БД **не нужны**.

1. **Скан структуры.** `git ls-tree -r --name-only <branch>`; отфильтровать `.py`. Построить агрегаты: для каждого префикса-директории на глубинах 1, 2, 3 — число `.py`-файлов под ним. Это вход для выбора depth/overrides и оценки числа кластеров.

2. **Churn.** `git log --since=<окно> --name-only --pretty=format:` (окно по умолчанию ~6 месяцев; если репо моложе/коммитов мало — фоллбэк на последние ~200 коммитов). Агрегировать: сколько коммитов трогали каждое поддерево. Метрика активности — `commits_touching / files_count` поддерева (нормировка на размер). Классификация «активное / стабильное» — относительно медианы по поддеревьям. Fail-soft: если `git log` пуст/ошибка — пропустить churn, рекомендовать только по структуре, отметить это пользователю.

3. **Чтение текущего `.review.yml`** (если есть). Распарсить, **сохранить** все ключи вне контекст-слоя (`task_board`, `categories`, `severity_threshold`, `max_comments`, `min_confidence`, `output_language`, и т.д.) и существующие комментарии. Скилл правит **только** ключи из §2. Файла нет → создать с нуля (с поясняющими комментариями в стиле текущего `.review.yml`).

4. **Генерация черновика (эвристики).**
   - **`summary_cluster_depth`** (глобальный): выбрать `d ∈ {1,2,3}` так, чтобы кластеры были осмысленного размера — ориентир ~3–15 файлов на кластер; избегать «один гигантский кластер» (слишком крупно) и «по файлу на кластер» (слишком мелко). По умолчанию 2; для очень маленьких репо — 1. Алгоритм: оценить распределение размеров кластеров при `d=1/2/3` (из агрегатов шага 1) и выбрать `d`, минимизирующий долю «too-coarse» (> ~20 файлов) и «too-fine» (1 файл) кластеров, с приоритетом 2 при равенстве.
   - **`summary_cluster_depth_overrides`**: для **крупного И активного** поддерева (размер выше порога ~20 файлов и активность выше медианы) — override `depth = d+1` (мельче кластеры → точечная инвалидация, богаче приор). Крупные-но-стабильные — оставить на глобальном `d` (укрупнение допустимо). Ключи — кратчайший различающий префикс директории (longest-prefix-match). Глубину капать на 3.
   - **`summary_topk_threshold`**: оценить число кластеров при выбранных `d` + overrides ≈ число различных `cluster_key`. Если оно велико (> текущего дефолта 20) — оставить 20 (включается ANN top-k); иначе оставить дефолт. Значение в основном информативное; явно показать пользователю оценку числа кластеров.
   - **`paths.ignore`**: предложить **кандидатов** среди трекаемых путей, похожих на не-продакшн-шум: имена/поддеревья вида `eval`/`evals`, `fixtures`/`testdata`, `examples`/`samples`, `vendor`/`third_party`, `generated`/`gen`/`*_pb2.py`, `migrations`, крупные `data`-модули. Это **суждение**, поэтому скилл показывает кандидатов с обоснованием и **спрашивает** подтверждение по каждому — никогда не вписывает молча. Уже присутствующие в `paths.ignore` записи сохраняются.

5. **Презентация черновика + diff.** Показать предлагаемый контекст-слой и unified diff против текущего `.review.yml` (или «новый файл»). Кратко объяснить каждую рекомендацию (почему такой depth, почему override на этом поддереве, почему этот путь в ignore). Принять правки пользователя в свободном диалоге.

6. **Запись `.review.yml`.** Записать итог, **сохранив** чужие ключи и поясняющие комментарии. Идемпотентность: повторный прогон на уже настроенном репо даёт минимальный diff.

7. **Подсказка команд (без авто-запуска).** Если менялся `paths.ignore` → подсказать `/reviewer_sync-codebase` (переиндексация вектор+граф). Если менялись `summary_cluster_depth` / `*_overrides` / `summary_topk_threshold` → подсказать `/reviewer_summarize-subsystems` (смена depth меняет `cluster_key` → полный пересбор сводок; осиротевшие сводки старого depth вычистит `prune_subsystem_summaries` на полном прогоне). Напомнить: изменения вступают в силу **после** пересбора и **с той ветки**, на которую `.review.yml` закоммичен.

## 5. Инварианты дизайна

- **Не клоберить чужие ключи.** `.review.yml` правится merge'ем; `task_board` и прочие ключи вне контекст-слоя остаются нетронутыми.
- **Только трекаемые файлы.** Источник истины — `git ls-tree <branch>`, ровно набор, попадающий в индекс. Никакого обхода ФС.
- **`.review.yml` действует с ветки коммита.** Политика читается из целевой/индексируемой ветки (PR не ослабляет своё ревью). Скилл редактирует рабочее дерево; коммит и выбор ветки — за пользователем; скилл это проговаривает.
- **Fail-open на churn.** Нет git-истории / `git log` упал → деградация до рекомендаций по структуре, с пометкой пользователю.
- **Без побочных эффектов на индекс.** Скилл только редактирует файл и подсказывает команды; пересбор не запускает.

## 6. Тестирование

Скилл — markdown-промпт, не код, поэтому отдельных pytest-тестов backend нет. Проверки корректности:

- **Структурный контракт `.review.yml`.** Сгенерированный файл должен парситься `ReviewPolicy.from_yaml` без потери чужих ключей и проходить существующий guard валидации ключей (`tests/` корневые: `paths.ignore`, `summary_cluster_depth`, `summary_cluster_depth_overrides`, `summary_topk_threshold`). Если потребуется — расширить этот guard примером, который генерирует скилл.
- **Ручная проверка** на этом репозитории: у него уже есть настроенный `.review.yml` — прогнать скилл, убедиться, что diff минимален/осмыслен (идемпотентность), а `task_board` и комментарии сохранены.

## 7. Открытые вопросы / решения

- Точные числовые пороги эвристик (размер «крупного» поддерева, окно churn, целевой размер кластера) — стартовые значения зафиксированы выше (≈20 файлов, ~6 мес, 3–15 файлов/кластер); финальная калибровка — в плане/при ручной проверке, значения вынести в начало тела скилла как настраиваемые ориентиры.
- Имя скилла — `reviewer_configure-review` (согласовано).
- Backend «раздельный ignore по слоям» (B) и дефолтный ignore (C) — отдельные задачи, в этой спеке не реализуются.
