# PRI-260 — слияние слоёв политики по листу и видимость дрейфа рабочего дерева

Бриф: `docs/superpowers/briefs/2026-08-18-PRI-260-policy-layer-leaf-shadowing.md`

## Проблема

Два независимых дефекта резолва политики, оба найдены на приёмке PRI-259.

**1. Затенение по верхнему ключу.** `merge` внутри `resolve_policy_data`
(`reviewer/config/layers.py:355-360`) перезаписывает ключ целиком. Порядок слоёв —
`home:review.yml` → коммиченный `.review.yml` → `home:repos/<repo>.yml`. Домашний per-repo слой,
задавший `context_limits` частично, стирает всю коммиченную `context_limits`, включая подсекции,
о которых сам не высказывался. Измерено на этом репозитории: коммиченный пин
`context_limits.code_section` (`max_files: 12`, `chars_per_file: 1300`) исчез целиком, потому что
домашний слой задавал `context_limits` без этой подсекции, и приёмочный прогон PRI-259 дал числа
нового дефолта. Диагностика этого не показывала: `config show` печатал `shadowed: .review.yml`
на уровне ключа `context_limits`, и по этой строке «подсекция потеряна» неотличимо от «её и не было».

**2. Дрейф рабочего дерева невидим.** `CommittedLayerFetcher.__call__`
(`reviewer/config/committed.py:79-86`) читает `git show <ref>:.review.yml` — коммиченный блоб,
никогда не рабочее дерево. Метка `committed: local` усиливает сюрприз: она означает «через git из
локального клона», а читается как «локальный файл на диске». Пользователь правит `.review.yml` в
корне, запускает `config show` и видит старые значения без единого указания на причину.

Приоритет источников при этом менять нельзя: `.review.yml` берётся из целевой ветки намеренно,
иначе PR ослабляет собственное ревью правкой своего же конфига. Дефект — не в источнике, а в
отсутствии сигнала о расхождении.

## Решение

### 1. Рекурсивное слияние — новый модуль `reviewer/config/deepmerge.py`

Чистая функция вместо замыкания внутри `resolve_policy_data`. Две причины: `layers.py` уже за 1100
строк, и логику обязаны разделить два вызывающих — `resolve_policy_data` и `_simulated_repo_layer`
(`layers.py:1015-1032`), которая сегодня повторяет `merge` вручную. При рекурсии, добавленной
только в одном из них, `config migrate` дал бы другой вердикт о затенении, чем `config show`.

```python
ATOMIC_KEYS = frozenset({"task_board"})

def merge_layer(
    merged: dict[str, object],
    sources: dict[str, str],
    shadowed: dict[str, list[str]],
    data: Mapping[str, object],
    source: str,
) -> None
```

Правило рекурсии: входим в ключ **только когда оба значения — `Mapping`** и верхний ключ не в
`ATOMIC_KEYS`. Во всех остальных случаях — замена целиком: списки (`paths.ignore` слияния по
элементам не предполагает), скаляры, и смена типа (`mapping` ↔ не-`mapping`).

`task_board` — единственное исключение из общего правила, и оно намеренное: это связный контракт
(`type` + `project` + `create_target`/`done_target` + `options`), а не набор независимых настроек.
Частичный домашний `task_board: {type: jira}` поверх коммиченного `yougile` дал бы при рекурсии
конфиг доски, которого не писал ни один слой: тип от одного, проект и целевые колонки — от другого.
Остальные mapping-ключи (`categories`, `summary_cluster_depth_overrides`, `context_limits`) —
наборы независимых флагов/секций, для них рекурсия и есть ожидаемое поведение.

`sources` и `shadowed` ключуются **путём до листа** (`context_limits.code_section.max_files`).
Для скаляра верхнего уровня путь совпадает с сегодняшним плоским ключом, поэтому `max_comments`
в отчёте не меняется вовсе.

При замене mapping'а не-mapping'ом (или наоборот) старые листовые записи `sources`/`shadowed` под
этим префиксом **вычищаются** — иначе в отчёте останется след от значения, которого в эффективной
политике больше нет.

Затенение регистрируется по факту наличия листа в двух слоях, а не по неравенству значений — как и
сегодня: цель диагностики — показать, что слой высказался о ключе, а не что значение изменилось.

### 2. Диагностика той же гранулярности

`ResolutionMeta.sources`/`.shadowed` сохраняют типы (`dict[str, str]`, `dict[str, tuple[str, ...]]`),
меняется семантика ключей — путь до листа вместо верхнего ключа.

`build_config_report` (`layers.py:585-615`) сегодня собирает `sources = {key: meta.sources.get(key,
"env") for key in effective}` по верхним ключам эффективной политики. Теперь для каждого верхнего
ключа собираются все его листья по префиксу.

`_render_config_report` (`cli.py:150-189`):

- все листья ключа пришли из одного слоя → одна строка `source: <layer>`, как сегодня;
- листья пришли из разных слоёв → `source: mixed` и по одной подстроке на каждый расходящийся лист
  (`context_limits.code_section.max_files: .review.yml`);
- `shadowed` печатается тем же способом: по верхнему ключу, если затенён он целиком, иначе — по
  затенённым листьям.

Вывод для скалярных ключей остаётся побайтово прежним; разбухает он только там, где смешение
слоёв реально есть. В JSON (`config show --json`) ключи `sources`/`shadowed` становятся путями —
это изменение формы отчёта, осознанное: плоские ключи и были той самой линзой, скрывшей дефект.

### 3. Дрейф рабочего дерева

Новая чистая функция в `committed.py`, рядом с `validate_clone` (там уже живут `POLICY_FILE`,
`file_at_ref`, `rev_parse`):

```python
@dataclass(frozen=True)
class DriftReport:
    status: str          # "clean" | "drifted" | "absent_in_worktree" | "absent_in_blob"
                         # | "ref_not_head" | "unknown"
    keys: tuple[str, ...]

def worktree_drift(root: str, ref: str, policy_file: str = POLICY_FILE) -> DriftReport
```

Зовёт её **только** `config_show`; MCP (`mcp/service.py`) и ревью PR (`services/review_service.py`)
не затрагиваются — критерий 3 называет только `config show`, а в ревью PR рабочее дерево клона на
сервере к содержимому PR отношения не имеет. Доступ к корню клона — новое публичное свойство
`CommittedLayerFetcher.clone_root` вместо приватного `_clone_root`.

Три решения, принятые здесь явно:

- **Сравнение проводится только если `ref` резолвится в тот же коммит, что HEAD клона.** При
  `config show --branch dev`, запущенном из ветки `feat/...`, дифф был бы огромным и не про дрейф
  вовсе. В этом случае — статус `ref_not_head` и одна строка в выводе: сравнение не проводится и
  почему. Молчания здесь быть не должно — отсутствие сигнала и есть исходный дефект.
- Файл есть в блобе, но отсутствует в рабочем дереве (или наоборот) — отдельный статус, а не
  список всех ключей.
- Любой сбой (чтение, git, парсинг YAML) — fail-soft: статус `unknown`, ничего не печатается,
  код возврата `config show` не меняется.

Расходящиеся ключи — **листовые пути без значений** (обход общий с `deepmerge`). Эффективная
политика по-прежнему целиком из коммиченного слоя: дрейф — предупреждение, не источник данных.

### 4. Метка способа чтения

`SOURCE_LOCAL = "local"` → `"git-blob"` (`committed.py:23`). Метка называет ровно то, что прочитано:
объект git на ref, а не файл в рабочем дереве, — и потому читается в паре с предупреждением о
дрейфе без пояснений. `SOURCE_VCS = "vcs"` не меняется: ось «клон или сеть» сохраняется.
Потребители литерала: `cli.py:167` (рендер), `tests/config/test_committed_layer.py:75`,
`tests/entrypoints/test_config_commands.py:352`.

## Тесты

- `tests/config/test_deepmerge.py` (новый) — чистая функция: частичный mapping не стирает соседние
  подсекции; список и скаляр заменяются целиком; `task_board` заменяется целиком; смена типа
  чистит листовые записи; ключи `sources`/`shadowed` — пути до листа.
- `tests/config/test_layers.py` — 4 существующих ассерта на `meta.shadowed[<верхний ключ>]`
  переписываются под путь-ключи; добавляется **регресс ровно на конфигурацию PRI-259**
  (коммиченный пин `context_limits.code_section` + домашний per-repo слой с `context_limits` без
  этой подсекции → пин виден в эффективной политике); тест «порядок слоёв не изменён».
- `tests/config/test_committed_layer.py` — `worktree_drift`: чистое дерево, дрейф с перечислением
  ключей и без значений, отсутствие файла с каждой стороны, `ref ≠ HEAD`, fail-soft на сбое;
  метка `git-blob`; эффективная политика при дрейфе остаётся коммиченной.
- `tests/entrypoints/test_config_commands.py` — вывод `config show`: свёртка `source:` при одном
  слое, `mixed` с подстроками при смешении, строка предупреждения о дрейфе, `committed: git-blob`
  в тексте и JSON.

## Обратная совместимость

Поведение для не-mapping значений (списки, скаляры) не меняется — критерий 6. Форма
`ResolutionMeta` и типы её полей сохраняются; меняется семантика ключей `sources`/`shadowed` и,
следовательно, форма этих двух ключей в `config show --json`. Строковая метка `local` меняется на
`git-blob`. Три потребителя `resolve_policy_data` (CLI, MCP `_resolve_policy`,
`services/review_service.py`) сигнатур не меняют.

## Документация

Абзац «Сбой чтения коммиченного `.review.yml` не обнуляет домашние слои» в `CLAUDE.md` дополняется
гранулярностью слияния (рекурсия по mapping, `task_board` — исключение) и новой меткой; там же
называется предупреждение о дрейфе рабочего дерева как диагностика, не меняющая приоритет источников.
