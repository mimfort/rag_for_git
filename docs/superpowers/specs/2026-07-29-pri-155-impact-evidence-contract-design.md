# PRI-155 — достоверный контракт `get_impact`

## Статус исходной задачи

Исходную PRI-155 нужно переписать, а не удалить. Два дефекта всё ещё существуют и
снижают качество глобального `rag-reviewer` plugin:

- `compute_impact` отбрасывает caller по признаку «его путь присутствует в PR». Это
  скрывает не обновлённый call-site, если тот находится в изменённом файле, но вне
  затронутого хунка или изменён по другой причине.
- caller, найденный графом, но отсутствующий в chunk store, превращается в
  `path:0 | `. Такая строка выглядит как доказательство, хотя прочитать символ не
  удалось.

Пункт про неподдерживаемые декораторы устарел: после PRI-158
`reviewer/index/struct_diff.py::extract_signature` уже пропускает декораторы и
покрыт регрессионным тестом.

## Цель

Сделать `get_impact` recall-safe и честным источником кандидатов для
blast-radius сабагента: не терять callers только из-за присутствия файла в PR,
отличать прочитанные символы от пробелов покрытия и не выдавать технические
заглушки за факты.

## Решение

### Модель данных

`CallerRef` остаётся представлением только реально прочитанного caller-символа
и получает булево поле `changed_file`: путь caller входит в `changed_paths`.

`ImpactItem` получает `unresolved_caller_ids: list[str]`. В этот список входят
идентификаторы, возвращённые графом, для которых `store.fetch_nodes` не вернул
chunk. Для таких идентификаторов `CallerRef` не создаётся.

Списки детерминированы: исходные graph IDs сортируются, `callers` сохраняют этот
порядок, `unresolved_caller_ids` также упорядочен.

### Вычисление impact

Гейт target-символа не меняется:

1. target должен существовать и в base, и в overlay;
2. обе сигнатуры должны извлечься;
3. старая и новая сигнатуры должны различаться.

После гейта `compute_impact` берёт всех callers из `graph.callers`, не исключая
пути из `changed_paths`. Существующий overlay/base-aware
`store.fetch_nodes(..., overlay_ref, changed_paths, base_ref=...)` читает
актуальную версию caller: overlay для изменённого файла и base для остальных.

Движок намеренно не пытается решить, обновлён ли конкретный call-site. Изменение
любого текста caller-символа не доказывает обновление вызова, а статический граф
не хранит достаточно данных для надёжного сопоставления аргументов динамического
Python-вызова. Проверка остаётся ответственностью blast-radius сабагента.

`ImpactItem` сохраняется, если граф вернул хотя бы одного caller — разрешённого
или unresolved. Поэтому рассинхрон графа и store не превращается в ложное
«ничего не найдено».

### Публичный текстовый контракт

`format_impact` называет строки «кандидатами для проверки», а не
«устаревшими вызывающими».

Каждый прочитанный caller получает явный scope-маркер:

- `[в PR] path:line | signature` — файл присутствует в изменениях;
- `[вне PR] path:line | signature` — файл не менялся.

Если есть `unresolved_caller_ids`, после прочитанных строк выводится отдельное
предупреждение покрытия с количеством и идентификаторами. В нём прямо сказано,
что метаданные caller не удалось прочитать из индекса. Формы `path:0 |` в
выводе больше нет.

Пустой результат сохраняет текущий совместимый sentinel
`(изменений сигнатур с вызывающими не найдено)`.

### Контракт глобального plugin

`plugin/skills/review-pr/references/blast-radius-prompt.md` больше не утверждает,
что `get_impact` возвращает только callers вне PR. Сабагент обязан:

1. прочитать каждый caller через `read_file`;
2. для `[в PR]` изучить `get_changed_file_diff` и проверить именно call-site,
   не считая присутствие файла в PR доказательством исправления;
3. для `[вне PR]` подтвердить, что файл действительно не входит в diff;
4. не создавать finding из unresolved ID: это только сигнал неполноты;
5. по-прежнему якорить finding на изменённой сигнатуре в diff.

Краткое описание `get_impact` в общем tool-usage блоке и MCP/docstrings должно
говорить о callers изменённой сигнатуры, а не только о callers вне diff.

## Ошибки и деградация

- Недоступный graph/store по-прежнему обрабатывается внешним `get_impact` guard.
- Исключение самого `fetch_nodes` не подменяется coverage-gap: вызов сохраняет
  действующий error-контракт инструмента. Coverage-gap означает только успешный
  запрос, который не вернул отдельные graph IDs.
- Missing chunk — нормальный coverage-gap, а не исключение и не finding.
- Добавленные и удалённые target-символы остаются вне scope: текущий
  `changed_node_ids` и base/overlay pair gate не задают достоверной политики для
  удалений. Их поддержка требует отдельной задачи.
- API `extract_signature(str) -> str | None` не меняется: причины `None` нет
  потребителя в публичном контракте.

## Тестирование

В `tests/tools/test_impact.py` нужны отдельные проверки:

- caller из того же изменённого файла возвращается и помечается `changed_file=True`;
- caller вне PR остаётся и помечается `changed_file=False`;
- для обоих путей store получает существующий overlay/base-aware вызов;
- отсутствующий chunk попадает в `unresolved_caller_ids`, но не в `callers`;
- formatter выводит `[в PR]`, `[вне PR]` и coverage-gap без `:0 |`;
- item с одними unresolved callers не теряется;
- body-only target change и added/removed target по-прежнему не создают impact;
- действующий тест decorated async signature остаётся регрессией PRI-158;
- StructuredTool `get_impact` отдаёт новый текстовый контракт end-to-end.

В тестах собранных skill prompts нужно закрепить три правила: callers могут быть
в PR, изменённый файл не доказывает обновление call-site, unresolved ID не
является основанием для finding.

## Критерии приёмки

- Неизменённый или не полностью обновлённый caller в файле PR виден
  blast-radius сабагенту.
- Ни один непрочитанный graph node не отображается как `path:0 |`.
- Пользовательский вывод различает grounded callers и coverage gaps.
- Глобальный plugin проверяет caller по исходнику и diff независимо от scope.
- Существующие сигнатурный гейт, fail-soft поведение и поддержка декораторов не
  регрессируют.
- Точечные unit/skill-тесты и полный unit suite проходят без внешней сети.

## Вне scope

- Полная поддержка удалённых target-символов.
- AST/type-aware доказательство совместимости аргументов вызова.
- Изменение схемы публичного MCP tool с текста на JSON.
- Новые LLM-вызовы или зависимости.
