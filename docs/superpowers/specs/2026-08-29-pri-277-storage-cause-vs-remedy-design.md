# PRI-277 — различить причину недоступности хранилища и уместность лекарства

Происхождение: `docs/superpowers/briefs/2026-08-29-PRI-277-storage-cause-vs-remedy.md`

## Задача

Пользователю с поднятыми контейнерами и опечаткой в пароле система советует `reviewer start` —
команду, которая уже выполнена. Замер приёмки PRI-269 (дефект Д-6, `eval/pri269_acceptance_report.md`)
показал: неверный пароль, несуществующая БД и остановленные контейнеры дают побайтово одинаковый
ответ — `cause: storage_unavailable`, `remedy: "reviewer start"`, ~60 с. Ни одно наблюдаемое поле
их не различает.

Дефект не в классификации причины, а в лекарстве: `storage_remedy()`
(`reviewer/storage_health.py:60-64`) решает, предлагать ли `reviewer start`, **только** по признаку
loopback-эндпоинта. Исключение в этом решении не участвует, хотя драйвер знает причину дословно.

Два факта из того же замера определяют форму решения. Первый: ветвиться по коду ошибки нельзя —
при сбое на этапе установления соединения libpq не возвращает результат, поэтому `e.sqlstate` и
`e.diag.sqlstate` равны `None` во всех трёх случаях. Второй: пароль в `str(exc)` не попадает,
а хост, порт, имя пользователя и имя базы — попадают.

## Критерии приёмки (из задачи)

1. Неверный пароль и несуществующая БД отличимы от остановленных контейнеров по наблюдаемым полям.
2. Пользователю не советуется `reviewer start` при живых контейнерах.
3. Ни пароль, ни полный DSN в диагностику не попадают.
4. Поведение закреплено тестом.

## Принятые решения

| Развилка | Решение | Отвергнутая альтернатива и почему |
|---|---|---|
| Как сделать случаи машиночитаемо различимыми | Пятый ключ `cause_detail` в записи `gap()` | Уточнение самого `cause` тихо ломает шаг 0a скилла `solve-task`: он ищет равенство `storage_unavailable`, и auth-сбой перестал бы показываться пользователю вовсе. Различение только через прозу `reason` нарушает доктрину «потребитель ветвится по `cause`, а не по прозе». |
| Выходит ли текст исключения наружу | Только для нераспознанного `OperationalError` | Закрытый enum без текста оставляет нераспознанный сбой ровно таким же немым, как сегодня. Всегда показывать текст — самая широкая поверхность утечки без выигрыша: у распознанных случаев класс уже несёт всю информацию. |
| Скоуп `reviewer check` | Входит | Критерий 2 не называет канал, а `reviewer check` выдаёт тот же ложный совет по независимой логике. Оставить его — значит формально не выполнить критерий и получить два разных ответа на один диагноз. |
| Глубина Neo4j | Только по типу исключения | Текстовых паттернов Neo4j никто не замерял, а угадывать формулировки чужого драйвера — тот же класс ошибки, что в исходном дефекте. |
| Где живёт решение | Класс и лекарство — в `storage_health`; формулировки — у каждого канала | Отдавать готовую русскую фразу из классификатора означало бы, что модуль владеет текстом для двух разных адресатов: `reason` в payload читает LLM и вставляет в бриф, а CLI печатает строку в терминал. Отдавать только класс — вернуть решение «советовать ли `reviewer start`» в два места, то самое расхождение, которое устраняется. |

## Архитектура

### `reviewer/storage_health.py` — единственный источник решения

Новый публичный контракт:

```python
DETAIL_AUTH_FAILED = "auth_failed"
DETAIL_MISSING_DATABASE = "missing_database"

@dataclass(frozen=True)
class StorageDiagnosis:
    detail: str | None      # закрытая метка класса причины либо None
    remedy: str | None      # "reviewer start" либо None
    redacted: str | None    # вымаранный отрывок текста либо None

def classify_storage_failure(exc: BaseException, *endpoints: str) -> StorageDiagnosis: ...
```

Правила, в порядке проверки:

1. `is_storage_unavailable(exc)` ложно → `StorageDiagnosis(None, None, None)`. Этим одним условием
   чинится Neo4j-половина в CLI: `AuthError` из предиката исключён с PRI-268, поэтому неверный
   пароль Neo4j перестаёт получать совет без единой строки текстовой логики.
2. Текст совпал с паттерном → `detail` заполнен, `remedy` равен `None` (контейнеры живы, лекарство
   неприменимо), `redacted` пуст (класс уже несёт информацию).
3. Иначе → `detail` пуст, `remedy = storage_remedy(*endpoints)` как сегодня, `redacted` несёт
   вымаранный отрывок.

Паттерны сопоставляются регистронезависимо по `str(exc)`, ровно в замеренных формах:
`password authentication failed` → `auth_failed`; `database ... does not exist` → `missing_database`.

`is_storage_unavailable` и семантика `cause` не меняются: соединения нет, и по типу исключения это
действительно недоступность хранилища (критерий 4).

### Вымарывание

Локальная функция в том же модуле: из каждого эндпоинта извлекаются хост, порт, имя пользователя,
пароль и имя базы (`urlsplit` плюс тот же regex-фолбэк для keyword-DSN, что уже использует
`is_loopback_endpoint`), затем literal-вхождения заменяются на `[REDACTED]`, длинные значения
первыми, чтобы префикс не оставлял хвост более длинного значения. Результат обрезается до 200
символов, чтобы отрывок не раздувал payload; обрезка идёт **после** вымарывания, иначе значение,
попавшее на границу, уцелело бы наполовину.

Пароль вымарывается, хотя замер показал его отсутствие в тексте: замер снят на одной версии libpq
и одном классе ошибок, и полагаться на это как на инвариант нельзя.

**Осознанное дублирование.** `sanitize_provider_text` (`reviewer/tasks/boards/errors.py:19-28`)
делает ровно это, но импортировать его нельзя: импорт исполнит
`reviewer/tasks/boards/__init__.py`, который строит реестр провайдеров досок — тяжёлая и
неправильная по направлению зависимость для модуля в корне пакета. Единого источника здесь не
будет, как и у весов токенов между хуком и сервером (PRI-247).

### `reviewer/mcp/task_context.py` — поток данных

Сегодня `_StorageState(_remedy(deps))` (строка 138) фиксирует лекарство до первого обращения к
хранилищу; исключение ловится позже в `_safe` и туда не передаётся. Поэтому текстовая
классификация в нынешней форме недостижима.

`_StorageState` начинает хранить эндпоинты вместо готового лекарства и получает поле
`diagnosis: StorageDiagnosis | None`. Вердикт вычисляется один раз — в `except`-ветке `_safe`, где
исключение наконец доступно. Секции, пропущенные по замыканию (`SKIPPED_REASON`), переиспользуют
тот же вердикт, поэтому все записи одного прогона согласованы между собой.

`_remedy(deps)` превращается в `_endpoints(deps)` с теми же `getattr` и fail-soft: провайдер без
метода `storage_endpoints` обязан продолжать работать.

Запись `gap()` получает пятый ключ:

```python
{"section": ..., "reason": ..., "cause": ..., "cause_detail": ..., "remedy": ...}
```

`cause_detail` равен `None` везде, кроме распознанных случаев. Вымаранный отрывок дописывается в
`reason` — он проза по природе и отдельного ключа не заслуживает. Формулировки живут здесь, а не
в классификаторе: «хранилище отвергло учётные данные», «базы данных не существует».

### `reviewer/entrypoints/cli.py` — команда `check`

Решение `local_storage_down |= _is_loopback_endpoint(...)` в обеих ветках (`:887`, `:903`)
заменяется на вердикт `classify_storage_failure(e, <эндпоинт>)`: подсказка `reviewer start`
печатается, только если хотя бы один вердикт несёт непустой `remedy`. При непустом `detail`
печатается класс причины.

Существующий вывод `✗ Postgres: {err}` не трогается: это терминал самого оператора, поведение
дореализационное, и задача его не касается.

## Обратная совместимость

Два существующих теста жёстко требуют `remedy == "reviewer start"` для generic
`OperationalError("connection refused")` (`tests/mcp/test_prepare_task_context.py:314`) и
`remedy is None` для удалённого деплоя (`:353`). Оба остаются зелёными **по построению**: текст
`connection refused` не совпадает ни с одним паттерном, поэтому случай идёт прежней третьей веткой.

Пятый ключ аддитивен: скилл `solve-task` копирует записи `gaps` в бриф целиком и ветвится на
`cause`, который не меняется.

## Известное ограничение

Сообщения libpq локализуются по `lc_messages` сервера. На сервере с не-английской локалью паттерны
не совпадут, и случай уедет в нераспознанную ветку — вымаранный отрывок плюс сегодняшнее поведение.
Деградация безопасная, но различение не гарантировано на любом деплое. Это записано как
ограничение, а не как незамеченный дефект.

## Тестирование

- **Классификатор** (`tests/test_storage_health.py`): auth-текст → `auth_failed` и `remedy is None`;
  текст отсутствующей БД → `missing_database` и `remedy is None`; generic + loopback → `detail is
  None` и `remedy == "reviewer start"`; generic + удалённый эндпоинт → оба `None`; не-storage
  исключение (`neo4j AuthError`) → все три поля `None`.
- **Отсутствие секретов** по образцу `tests/config/test_fetch_errors.py:64-72`: DSN с паролем,
  хостом и именем пользователя кладётся в текст исключения, проверяется, что ни одно из этих
  значений не встречается в `repr` вердикта.
- **Payload** (`tests/mcp/test_prepare_task_context.py`): auth-сбой даёт `cause ==
  "storage_unavailable"`, `cause_detail == "auth_failed"`, `remedy is None`; оба регрессионных
  якоря остаются нетронутыми; guard формы записи обновляется с четырёх ключей на пять осознанно.
- **CLI** (`tests/entrypoints/test_cli.py`): неверный пароль Postgres не печатает подсказку
  `reviewer start`; `AuthError` от Neo4j не печатает её же; остановленные контейнеры печатают.

- Текстовая классификация ошибок Neo4j — нет замера.
- Гранулярность `PoolTimeout` внутри `is_storage_unavailable` — отдельная задача ID-330; дизайн
  не должен закрывать к ней путь.
- Ретрофит `sanitize_provider_text` в нейтральный модуль.
