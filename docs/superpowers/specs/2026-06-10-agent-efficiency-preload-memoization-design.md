# Эффективность агента: предзагрузка PR-контекста + мемоизация тулов

**Дата:** 2026-06-10
**Статус:** дизайн согласован, ожидает реализации
**Область:** `reviewer/agent`, `reviewer/tools`

## Проблема (по данным трейсов)

Анализ реальных прогонов в Postgres (`review_runs` / `review_steps`, 7 прогонов на `mimfort/rag-demo` PR 10–14) выявил, что главный источник неэффективности — **повторная и лишняя работа**, раздувающая и латентность, и стоимость.

Прогон 12 (PR 14): 5 файлов, **521 секунда**, 117 шагов трейса, 48 tool-call'ов и 30 LLM-вызовов в `analyze` — на выходе **1 находка**. Прогон 10 (тот же PR) — 360 секунд, 1 находка.

Конкретные потери, видимые в трейсе:

1. **Повторные вызовы тулов.** Шаги 6–24 прогона 12 — это `get_changed_file_diff` по одним и тем же файлам 5+ раз подряд (повторяются одинаковые размеры результатов: 8203 / 1741 / 1198 / 533 / 408). Модель переспрашивает то, что уже получала. То же с `read_file`.
2. **Нет кэша в тул-слое.** `read_file` / `search_code` / `get_changed_file_diff` ходят к источнику (GitHub / Voyage / Neo4j) каждый раз заново.
3. **Эмбеддинги запросов без дедупа.** `retriever.retrieve` зовёт `embedder.embed_query(query)` на каждый `search_code` — отсюда упор в троттлинг Voyage free-tier (3 RPM).
4. **Пофайловый fan-out перезапрашивает общий контекст.** Каждый из 5 файлов (`Send`) независимо тянет диффы чужих файлов и общие модули — кэша между юнитами нет.
5. **Чужие диффы не предзагружены.** `_pr_context` кладёт в промпт только манифест (список файлов + статус), но не их диффы — поэтому модель вынуждена дёргать `get_changed_file_diff` по каждому чужому файлу (это тул №1: 23 вызова за все прогоны, в основном повторные).

Распределение тулов за все прогоны: `get_changed_file_diff` (23), `read_file` (21), `search_code` (17), `find_callers` (9), `get_related_symbols` (4), `get_definition` (0).

## Цель и не-цели

**Цель.** Убрать лишнюю/повторную работу так, чтобы при **тех же находках** заметно упали число tool-call'ов, число обращений к Voyage и `duration_ms`.

**Не-цели (вне этого спека).**
- Менять качество/полноту находок, добавлять новые тулы анализа (статанализ, тесты, git-история) — отдельное направление.
- Менять модель (`OPENROUTER_MODEL`) — оптимизация модель-агностична и помогает на любой.
- Переход на архитектурный retrieval-препасс (Подход 3) — возможная эскалация по итогам замеров.

## Дизайн

Три изменения, без новых внешних зависимостей. Все — чистые оптимизации с fail-soft на текущее поведение.

### (A) Предзагрузка PR-bundle в промпт

Новая функция `_pr_bundle(...)` в `reviewer/agent/analyzer.py` рядом с `_pr_context` / `_signature_changes`. Один раз на прогон собирает компактный обзор PR:

- диффы **всех** изменённых файлов (из `deps.patches`), каждый под капом по строкам;
- изменённые сигнатуры — переиспользуем готовый `_signature_changes`;
- карта сигнатур модулей — переиспользуем `_module_signatures` по `deps.sources`.

Блок вставляется как **кэшируемый** (`_cacheable`, `cache_control`) в human-промпт `analyze` и `synthesize`. Он стабилен и одинаков для всех файлов PR → prompt-caching переиспользует его между итерациями tool-loop (а при удачном тайминге — и между юнитами).

Эффект: `get_changed_file_diff` и львиная доля кросс-файловых `read_file` становятся не нужны — материал уже в контексте.

### (B) Run-level кэш результатов тулов

- Новое поле `Deps.tool_cache: dict | None = None` — один словарь на прогон.
- Инициализируется там, где собирается `Deps` (`reviewer/entrypoints/cli.py`), значением `{}`.
- Пробрасывается в `ToolContext` (новое поле `cache`).
- `make_tools` оборачивает каждую из 6 функций: ключ `(tool_name, нормализованные_args)` → результат.
  - **Промах:** считаем, кладём в кэш, возвращаем.
  - **Попадание:** отдаём из кэша **без обращения к источнику** (Voyage / GitHub / Neo4j / `read_file_fn`).
- Кэш **общий для всех юнитов** PR → файл B бесплатно переиспользует посчитанное файлом A.

Этот же кэш автоматически даёт **дедуп эмбеддингов запросов**: одинаковый `search_code(query)` не доходит до `embed_query`.

### (C) Дедуп-заглушка внутри одного юнита

Поверх кэша (B): если в рамках одного tool-loop модель повторно зовёт тот же `(tool, args)`, второй раз возвращаем короткое `(повтор: результат уже показан выше)` вместо повторной вставки полного результата. Бьёт по наблюдаемому в трейсе паттерну (один и тот же дифф 5 раз подряд) — экономит input-токены и обрывает холостой рост контекста.

Реализация: множество «уже отданных в этом юните» ключей живёт per-`ToolContext` (создаётся в `analyze`/`verify`/`synthesize` на юнит), компонует run-level кэш (B).

## Точки врезки

| Файл | Изменение |
|---|---|
| `reviewer/agent/state.py` | `Deps`: поле `tool_cache: dict \| None = None` |
| `reviewer/tools/code_tools.py` | `ToolContext`: поле `cache`; `make_tools` — обёртка «кэш + дедуп-заглушка» вокруг 6 тулов |
| `reviewer/agent/analyzer.py` | новый `_pr_bundle(...)`; врезка в human-промпт `analyze` и `synthesize` как cacheable-блок |
| `reviewer/entrypoints/cli.py` | инициализация `tool_cache={}` при сборке `Deps` на прогон |

## Edge-cases и инварианты

- **Большой PR.** Bundle под суммарным капом по строкам (по образцу `_WINDOWS_LINE_CAP = 1500`); при переполнении обрезаем хвост и оставляем `get_changed_file_diff` / `read_file` как fallback для опущенных файлов. Тулы **не удаляем** — только разгружаем.
- **Корректность кэша.** В пределах прогона `head_sha` фиксирован, граф и индекс не меняются → результаты тулов детерминированы, кэшировать безопасно. Кэш живёт только на прогон, не персистится.
- **Fail-soft.** При любой ошибке сборки bundle или обёртки — падаем на текущее поведение (тул считает заново). Качество находок не деградирует ни при каких сбоях оптимизации.
- **Нормализация ключа.** `args` сериализуем стабильно (например, `json.dumps(args, sort_keys=True, ensure_ascii=False)`). Ключ — полный набор args (просто и без риска коллизий между разными окнами `read_file`).

## Проверяемость

**Unit-тесты (на фейках, без внешних API):**
1. Повтор `(tool, args)` → источник (фейковый retriever / read_fn) дёрнут **один раз**, второй вызов из кэша.
2. Дедуп-заглушка: повтор того же `(tool, args)` в пределах юнита возвращает маркер-заглушку.
3. Два одинаковых `search_code(query)` → `embed_query` вызван **один раз**.
4. Bundle отрендерен в промпт `analyze` (содержит диффы чужих файлов) и обрезан по капу при переполнении.

**Измерение эффекта (критерий успеха):**
Прогнать `reviewer review owner/repo 14 --dry-run` на том же PR и сравнить с прогоном 12 по:
- числу шагов трейса (`review_steps`, особенно `kind='tool_call'`);
- числу обращений к Voyage (вызовы `search_code` / `embed_query`);
- `duration_ms` в `review_runs`.

Успех = меньше tool-call'ов и меньше времени при **сохранении набора находок**.
