# PRI-255 — Multi-query по сущностям и структуре задачи с RRF-слиянием

Бриф: `docs/superpowers/briefs/2026-08-17-PRI-255-multi-query-rrf.md`

## Проблема

Секция `code` контекста задачи (`prepare_task_context`) строится по одному запросу —
`_query(task, key)` даёт «заголовок + первые 8 строк описания» (`reviewer/mcp/task_context.py:39-50`).
У этого одного вектора три независимых следствия, и все три измерены на корпусе 55 задач
(`eval/replay_report.md`):

1. Текст с пятью темами усредняется в вектор, не близкий ни к одной из них.
2. Технические идентификаторы тонут в длинной формулировке и не поднимаются BM25-веткой гибрида.
3. Хвостовые пункты «Что сделать» не участвуют в поиске вовсе.

Замер: медиана core-recall 0.225, **bulk core-recall 0.127**, медиана числа предсказанных
файлов — **2**. Подъём потолков (`ceiling` 15→25, `candidate_pool` 30→50, вариант `limits`)
делу не помог: bulk 0.127→0.091. Узкое место — запрос, а не бюджет.

Второй, независимый механизм потери выяснился при разборе: `ContextPack.as_context`
режет рендер тупым `text[:8000]` (`max_tool_result_chars`). Один чанк-класс на 400 строк
выжигает весь символьный бюджет, и остальные файлы до сборщика брифа не доезжают —
это наблюдалось на выдаче по самой PRI-255, где первым блоком пришёл
`reviewer/tasks/service.py#TaskService` строки 35-469 с обрывом `[...truncated]`.
Починка одного запроса без защиты рендера даёт RRF право поставить правильный чанк
первым — и ровно ничего больше, если этот чанк большой.

## Решение

Мультизапрос с RRF-слиянием на отдельном пути, параллельном существующему.

### Инварианты

- **`Retriever.search_base` не меняется.** Он общий для `/ask`, грунтовки и ревью PR.
  Новый путь зовёт то, что лежит ниже него (`store.hybrid_search`), и переиспользует
  его хвост импортом, а не копией.
- **Публичный MCP-тул `search_codebase` не меняется.** Мультизапрос включается только
  внутри `prepare_task_context` (секции `code` и `test_exemplars`). Контракт публичного
  тула сохранён.
- **Вырожденный вход тождественен сегодняшнему поведению.** Продакшн-запрос `q0` всегда
  входит в набор подзапросов первым; если извлечь больше нечего (board-less, задача без
  списков), набор равен `[q0]`, RRF тождественен, поведение прежнее.
- **Ноль LLM-вызовов.** Извлечение подзапросов детерминированное.
- **Один вызов Voyage на сборку секции.** N подзапросов эмбеддятся одним батчем;
  реранка в этом пути нет.

### Компоненты

| Модуль | Роль | Зависимости |
|---|---|---|
| `reviewer/mcp/subqueries.py` (новый) | `build_subqueries(task, key) -> list[str]` | нет: ни сети, ни БД |
| `reviewer/retrieval/multiquery.py` (новый) | `rrf_merge(runs, k=60)` — чистая; `search_multi(...) -> ContextPack` — оркестрация | store, graph, embedder |
| `reviewer/index/embeddings.py` | `+ embed_queries(texts)` — батч поверх того же LRU-кэша | аддитивно |
| `reviewer/mcp/task_context.py` | `deps.code` / `deps.test_exemplars` принимают **список** запросов | нет |
| `reviewer/mcp/service.py` | `_search_codebase_multi` + два метода `_TaskContextDeps` | — |
| `eval/solve_task_metrics/live.py` | `+ code_multi(repo, branch, queries, limits)` — тот же продакшн-путь, без своей копии | живые компоненты |
| `eval/solve_task_metrics/variants.py` | вариант `multiquery` одной строкой `_REGISTRY` | — |
| `eval/solve_task_metrics/subquery_stats.py` (новый) | распределение числа подзапросов по корпусу + подкоманда `subqueries` | — |

### Извлечение подзапросов (`build_subqueries`)

Два источника, как требует задача:

1. **Структура.** Пункты списков под заголовками, совпадающими с
   `(?i)(что сделать|критери|приёмк|acceptance)`: нумерованные и маркированные строки.
   Каждый пункт — свой подзапрос (идентификаторы, стоящие внутри пункта, остаются в нём).
2. **Идентификаторы.** `snake_case`, `CamelCase`, пути с `/`, `*.py`, имена таблиц —
   собранные из прозаической части текста (вне списков) в один подзапрос-пул.

Число подзапросов производно от размера задачи: `1 + число пунктов + пул идентификаторов`.
На мелкой задаче это 2-3, на задаче-развёртке 10-15. Предохранитель `MAX_SUBQUERIES = 20`
против вырожденного текста. Дедуп по нормализованной строке.

### Слияние (`rrf_merge`)

`score(node) = Σ 1/(60 + rank_в_прогоне)`, где `rank` — позиция элемента в выдаче
`hybrid_search` этого подзапроса (выдача упорядочена по `score DESC`). Константа 60 и
форма формулы — те же, что в `store.hybrid_search` и `TaskStore.search`; третьей формулы
RRF в проекте не появляется. Тай-брейки детерминированы по `node_id`. Файл, найденный
несколькими подзапросами, поднимается наверх; найденный одним — всё равно попадает в выдачу.

### Поток данных

```
task ──build_subqueries──> [q0, q1..qN пункты, qN+1 пул идентификаторов]   cap 20
                              ▼
        embed_queries([...])        ← ОДИН вызов Voyage (батч, LRU-кэш)
                              ▼
        N × store.hybrid_search     ← только Postgres
                              ▼      + ANN-префильтр тем же предикатом, что в search_base
        rrf_merge(runs, k=60)
                              ▼
        один graph-expand от топа слитого списка → graph-only элементы в хвост
                              ▼
        _dedupe_overlapping + фильтр тестов + top-ceiling (CodebaseLimits.ceiling, 15)
                              ▼
        обрезка текста блока по границе строк (предохранитель рендера)
                              ▼
        ContextPack.as_context(line_numbers=True)
```

Реранкера и cliff-отсечки в этом пути нет: финальный ранкер — RRF. Причина не в экономии,
а в измеренном механизме потери. `cliff` считается по скорам реранкера **против того же
многотемного запроса**; на размытом запросе все скоры низкие, отсечка падает до `floor=4`
чанков — отсюда медиана «2 файла». Сохранить реранк и cliff на исходном запросе значило бы
сохранить сам механизм, который режет выдачу.

Порядок «сначала hybrid-элементы, потом graph-only» сохранён из `search_base`: hybrid
приоритетен, граф добавляет разнообразие.

### Предохранитель рендера

`as_context` общий с ревью PR и не меняется. Обрезка живёт в `multiquery.py`: перед сборкой
пачки текст каждого элемента режется до `MAX_BLOCK_CHARS = 2000` **по границе строк**, и через
`dataclasses.replace` правится `end_line`, чтобы заголовок `(path:start-end)` не лгал.
Значение 2000 — четверть символьного бюджета `max_tool_result_chars`: даже при четырёх
максимальных блоках в выдаче помещается не один файл, а четыре.
Это же чинит побочный дефект: `text[:8000]` в `as_context` калечит заголовки блоков, а
`extract_context_paths` требует в заголовке диапазон `:\d+-\d+` и такой блок отбрасывает —
обрезая заранее и честно, путь перестаёт теряться на границе усечения.

Файловая диверсификация и файловые квоты в эту задачу **не входят** — это ID-310.
Здесь только защита рендера от выжигания одним блоком, без которой рычаг неизмерим.

### Обработка ошибок (fail-open)

| Отказ | Поведение |
|---|---|
| `embed_queries` | откат на `embed_query(q0)`, один прогон |
| один `hybrid_search` | прогон пропускается с `log.warning`, остальные сливаются |
| graph недоступен | только hybrid-элементы, как в `search_base` |
| пустой результат | `"(ничего не найдено)"` |

## Приёмка

| Критерий | Как закрывается |
|---|---|
| 1. Распределение числа подзапросов по размеру задачи, не константа | подкоманда `python -m eval.solve_task_metrics subqueries` печатает распределение по корпусу |
| 2. Положительная дельта bulk core-recall в replay | `replay --variant multiquery` против `baseline` на одном `indexed_sha`; величина в `eval/replay_report.md` |
| 3. Хвостовой пункт находит свои файлы | юнит на фейках: файл, найденный только последним подзапросом, доезжает до рендера; плюс разбор задачи-развёртки в отчёте |
| 4. LLM-токены не растут | извлечение детерминированное, ноль LLM-вызовов; юнит на фейках проверяет ровно один вызов эмбеддера на сборку |

Baseline для критерия 2 — **линия `replay`, bulk 0.127**, а не цифра 0.373 из тикета:
`replay.py` мерит весь сырой ретрив, а snapshot — пути, отобранные LLM из выдачи; линии
несравнимы напрямую, сравнивать можно только replay с replay.

Критерий 1 закрывается отдельной подкомандой, а не полем в снимке replay: контракт
варианта возвращает множество путей, и протаскивание метаданных сломало бы его для всех
вариантов.

## Границы скоупа

Соседние рычаги той же программы повышения core-recall остаются за пределами задачи:
ID-310 (файловая диверсификация и файловый бюджет секции `code`), ID-311 (подмешивание
diff-путей похожих задач и git-со-изменяемости), ID-312 (разворот кластеров `subsystems`
в файлы-кандидаты). Секция `subsystems` продолжает получать единый запрос `q0`.

Известное ограничение: `test_exemplars` мультизапрос получает, но replay эту секцию не
мерит — улучшение там остаётся недоказанным. Мерить его отдельно в этой задаче не входит.
