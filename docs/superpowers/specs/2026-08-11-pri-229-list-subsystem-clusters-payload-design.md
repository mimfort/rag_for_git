# PRI-229 — ограничение объёма ответа `list_subsystem_clusters`

Бриф: `docs/superpowers/briefs/2026-08-11-PRI-229-list-subsystem-clusters-payload-limit.md`

## Проблема

`MCPReviewService.list_subsystem_clusters` (`reviewer/mcp/service.py:1717`) отдаёт по каждому
кластеру полный список `files`, `top_symbols` и те же пути повторно в
`added_files`/`changed_files`/`moved_files` вместе с fingerprint'ами (`_fragment_ref`,
`reviewer/mcp/service.py:1684`). Размер ответа растёт линейно по числу файлов репозитория и
ничем не ограничен: параметр `cap` отбрасывает наименее приоритетные stale-кластеры к
пересборке, но на размер полезной нагрузки не влияет.

Замер на этом репозитории (`mimfort/rag_for_git`, ветка `dev`, `cap=0`): **106 878 байт**,
40 кластеров, **407 путей** в `files`, 248 элементов delta-списков. Штатный вызов из скилла
(`plugin/skills/summarize-subsystems/SKILL.md:29`) идёт без ограничителей, поэтому ответ не
помещается в контекст LLM-клиента и требует парсинга вспомогательным субагентом.

## Что меняем

Четыре независимо приёмлемых изменения, покрывающие подзадачи PRI-230…PRI-233.

### 1. Сжатый режим ответа (PRI-230)

Сигнатура сервиса:

```python
def list_subsystem_clusters(
    self,
    repo: str,
    branch: str | None = None,
    depth: int | None = None,
    min_size: int | None = None,
    cap: int | None = None,
    *,
    compact: bool = False,
    offset: int = 0,
    limit: int | None = None,
) -> dict
```

Тул `reviewer/entrypoints/mcp_server.py:309` повторяет параметры как обычные, без `*` — так
объявлены все остальные тулы файла, и такая форма гарантированно ложится в схему FastMCP.

Выбран `compact: bool = False`, а не `fields: str`: единственные два осмысленных режима,
дефолт сохраняет текущее поведение, булев флаг однозначен для LLM-клиента.

Запись кластера в `compact=True`:

| поле | тип | источник |
|---|---|---|
| `cluster_key` | str | `cluster.key` |
| `num_members` | int | `cluster.num_members` |
| `source_hash` | str | `cluster.source_hash` |
| `stale` | bool | `stale[cluster.key]` |
| `bootstrap` | bool | `generation_flags[...][0]` |
| `full_rebuild` | bool | `generation_flags[...][1]` |
| `reused_files` | int | `len(delta.reused)` |
| `added` | int | `len(delta.added)` |
| `changed` | int | `len(delta.changed)` |
| `removed` | int | `len(delta.removed)` |
| `moved` | int | `len(delta.moved)` |

Счётчики названы `added`/`changed`/`removed`/`moved` — **без суффикса `_files`**. Это
обязательное требование, а не стиль: если бы ключ `added_files` был то списком объектов, то
числом, клиент, не проверивший режим, ломался бы молча. Разные имена делают режим
самоопределяемым по форме ответа.

Ни `files`, ни `top_symbols`, ни fingerprint'ы в сжатом режиме не отдаются. `source_hash`
остаётся — он нужен скиллу для `get_subsystem_summary_work` и `prune_subsystem_summaries`, и
это хеш кластера, а не файла.

Верхнеуровневые поля (`branch`, `depth`, `layout_token`, `depth_source`, `deferred`,
`deferred_files`, `orphans`) идентичны в обоих режимах.

### 2. Детерминированная пагинация (PRI-231)

`build_clusters` (`reviewer/graph/summaries.py:153`) уже строит кластеры через
`sorted(groups.items())`, то есть порядок по `cluster_key` детерминирован сегодня. Изменение
состоит в том, чтобы **зафиксировать** этот инвариант явно (сортировка списка кластеров на
сериализации) и покрыть тестом, а не полагаться на порядок обхода вышележащего слоя.

Правила:

- `offset` по умолчанию `0`, `limit` по умолчанию `None` → весь набор (полная обратная
  совместимость).
- `offset < 0` приводится к `0`. `limit is None` или `limit <= 0` трактуется как «без
  лимита». Оба правила описаны в докстринге тула; исключений не бросаем — тул вызывает LLM,
  и мягкая нормализация надёжнее падения.
- `offset` за границей набора → `clusters: []`, `has_more: false`, без ошибки.

Новые верхнеуровневые поля (в обоих режимах):

| поле | смысл |
|---|---|
| `total_clusters` | число не-deferred кластеров во **всём** наборе, независимо от страницы |
| `offset` | применённый (нормализованный) offset |
| `limit` | применённый limit (`null` = без лимита) |
| `has_more` | есть ли кластеры за концом текущей страницы |

Инвариант: `deferred`, `deferred_files`, `orphans`, `layout_token`, `depth`, `depth_source`
вычисляются по полному множеству кластеров **до** среза страницы и одинаковы на каждой
странице. Сегодня это уже так по построению; после введения среза это становится
инвариантом, который обязан охраняться тестом.

`cap` и `limit` — ортогональны и не смешиваются: `cap` определяет, какие stale-кластеры
откладываются (`deferred`), `limit` режет только выдачу оставшихся. Порядок вычислений:
резолв → кластеризация → дельты → `cap`/`deferred` → сортировка → срез страницы →
сериализация.

Ранние возвраты с `note` (нерезолвленная ветка `service.py:1728`, пустой индекс
`service.py:1744`) дополняются `total_clusters: 0` и `has_more: false`, чтобы клиент,
обходящий страницы, не ловил `KeyError`. Остальные их поля не трогаем.

### 3. Дедупликация путей в полном формате (PRI-232)

`files` в полном формате содержит только пути кластера, **не встречающиеся** в
`added_files`/`changed_files`/`moved_files` — то есть неизменённые файлы.

- Полный состав кластера восстановим как `files ∪ added_files ∪ changed_files ∪ moved_files`.
- `removed_files` в состав не входят: это пути, которых в кластере уже нет.
- При `bootstrap`/`full_rebuild` дельта покрывает все файлы, поэтому `files` становится
  пустым — максимальная экономия ровно в самом тяжёлом случае.
- Контракт фиксируется в докстринге тула и докстринге сервисного метода.
- В `compact=True` поля `files` нет вовсе, поэтому изменение касается только полного формата.

**Разрешение противоречия критериев.** Критерий PRI-230 «полный формат не меняется
байт-в-байт для того же состояния индекса» относится к правкам PRI-230 и PRI-231: сжатый
режим и пагинация обязаны быть чисто аддитивными. PRI-232 — намеренное изменение контракта
полного формата, задокументированное в докстринге и зафиксированное тестом. Отсюда
обязательный порядок работ: **PRI-230 + PRI-231 → PRI-232 → PRI-233**.

Потребители поля `files`, установленные по коду: `plugin/skills/summarize-subsystems/SKILL.md`
поле **не читает** (композитору его передавать прямо запрещено, `SKILL.md:80`); реальные
потребители — только тесты `tests/mcp/test_subsystem_summaries.py`. Их и обновляем.

### 4. Скилл и документация (PRI-233)

`plugin/skills/summarize-subsystems/SKILL.md`:

- Шаг 2 «List clusters» — вызов `list_subsystem_clusters(repo, branch, compact=True,
  limit=100)` в цикле по `offset`, пока `has_more == true`. Накапливаются
  `expected_source_hashes = {cluster_key: source_hash}` по всем страницам и статистика для
  preflight (`stale`, `bootstrap`, `full_rebuild`, счётчики). Compact-запись ≈150 байт → 40
  кластеров ≈ 6 КБ вместо 107 КБ, поэтому полный обход страниц дешёв и `expected_source_hashes`
  собирается целиком, не разрывая verified prune.
- Шаг 3 «Preflight» — статистика считается по накопленным счётчикам сжатого перечисления.
- Шаг 5 не меняется: детализация по кластеру уже идёт через `get_subsystem_summary_work`
  (`service.py:1834-1868`), который отдаёт полную file-level дельту и тексты переиспользуемых
  фрагментов. Разрыва по данным нет — расширять перечисление обратно не требуется.
- Шаг 6 «Prune» — определение полного прохода дополняется: все страницы обойдены
  (`has_more == false` на последней) **и** `deferred == 0` **и** `raced == 0` **и** не
  передавался явный `depth`/`cap`. Пагинация override'ом не считается.

Документация: CLAUDE.md (раздел про инкрементальные fragments сводок), README.md и
README.ru.md (раздел `summarize-subsystems`) получают описание актуального контракта ответа.

Замер для критерия приёмки: «до» — 106 878 байт / 40 кластеров (зафиксирован выше); «после»
снимается тем же способом и записывается в задачу PRI-233.

## Тестирование

`tests/mcp/test_subsystem_summaries.py` — новые unit-тесты:

1. Сжатый ответ не содержит ни одного пути и ни одного fingerprint'а: рекурсивный обход
   значений записи кластера, ни одна строка не содержит `/` и не является 64-символьным hex,
   кроме разрешённых `cluster_key` и `source_hash`.
2. Счётчики `added`/`changed`/`removed`/`moved`/`reused_files` сжатого формата равны длинам
   одноимённых списков полного формата для того же состояния.
3. Полный формат остаётся дефолтом; верхнеуровневые поля совпадают в обоих режимах.
4. `files` не пересекается с путями `added_files`/`changed_files`/`moved_files`, а их
   объединение равно полному составу кластера.
5. Полный обход страницами возвращает ровно то же множество кластеров, что и вызов без
   пагинации, без пропусков и дублей; порядок воспроизводим между вызовами.
6. `deferred`, `deferred_files`, `orphans`, `layout_token`, `total_clusters` идентичны на
   каждой странице и совпадают с непагинированным вызовом.
7. Границы: `offset` за пределами набора → пустой список без ошибки; `limit` больше числа
   кластеров → одна страница с `has_more: false`; `offset < 0` и `limit <= 0` нормализуются.
8. Ранние возвраты с `note` содержат `total_clusters` и `has_more`.

`tests/skills/test_summarize_subsystems.py` — guard-тесты скилла обновляются под новый шаг
перечисления (сжатый режим, цикл пагинации, определение полного прохода).

Существующие тесты, затрагиваемые изменением: `tests/mcp/test_subsystem_summaries.py`
(вызовы `list_subsystem_clusters`, проверки `files`), `tests/mcp/test_summary_depth_overrides.py`,
`tests/mcp/test_server.py:131` (реестр имён тулов — имя не меняется).

Инфраструктура не нужна: все тесты юнитовые на фейках, как и существующие в этом файле.

## Границы

- Не трогаем `get_subsystem_summary_work`, `index_subsystem_summary`,
  `prune_subsystem_summaries`, `backfill_summary_embeddings` — их контракты неизменны.
- Не трогаем `_serialize_summary_delta` для пути `include_reused_content=True`
  (детальный тул) — только добавляем ветку для перечисления.
- Не меняем семантику `cap`, `deferred`, `layout_token`, `source_hash`, кластеризации и
  freshness.
- Резолв repo id из git remote на стороне MCP-клиентов в скоуп не входит (отдельный пробел,
  зафиксированный в PRI-229).
