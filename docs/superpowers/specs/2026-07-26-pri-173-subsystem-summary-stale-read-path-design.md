# PRI-173 — свежесть сводок подсистем на read path

## Цель

`get_subsystem_summaries` должен сообщать потребителям, соответствует ли каждая сохранённая
сводка текущей структуре base-индекса. Глобальные навыки Codex и Claude Code используют это поле
как сигнал доверия к архитектурному приору, не превращая сводку в источник фактов о коде.

## Решение

Каждая возвращённая сводка получает поле `stale`:

- `false` — сохранённый `source_hash` совпадает с текущим хешем кластера;
- `true` — хеши различаются либо соответствующего текущего кластера больше нет;
- `null` — свежесть сознательно не вычислялась или не могла быть вычислена.

`source_hash` остаётся в ответе как диагностическая метаинформация. Публичные параметры MCP-тула
и форма верхнего уровня (`summary` для одного ключа, `summaries` для списка) не меняются.

## Store layer

`SummaryStore.get_summaries()` и `SummaryStore.search_summaries()` добавляют `source_hash` в
`SELECT` и возвращаемый словарь. `get_summary()` уже возвращает это поле и сохраняет текущий
контракт.

Изменение схемы БД и миграция не нужны: колонка `source_hash` уже существует.

## Service layer

В `MCPReviewService` появляется внутренний fail-soft helper, который:

1. резолвит ту же глубину и те же path-overrides, что builder path;
2. читает base members через `list_base_members(repo, branch)`;
3. строит кластеры штатным `build_clusters(..., in_degree_fn=None, min_size=1)`;
4. возвращает отображение `cluster_key → current source_hash`.

GraphStore не вызывается: центральность не нужна для проверки свежести. Дополнительный
`get_source_hashes()` также не нужен — сохранённый хеш уже пришёл вместе со сводкой. Это оставляет
малый read path с одним дополнительным сканированием base members.

`get_subsystem_summaries` применяет helper по следующим правилам:

- `cluster_key`: получить одну сводку; если она существует, вычислить её `stale`;
- без `query`: получить все сводки и вычислить `stale` для каждой;
- `query` и число сводок не превышает `SUMMARY_TOPK_THRESHOLD`: сохранить текущий fetch-all
  контракт и вычислить `stale`;
- `query` и число сводок выше порога: выполнить текущий ANN top-k, не читать base members и
  установить `stale: null` для каждого результата.

Для пустого списка helper не запускается. Если base-индекс пуст, резолв глубины, чтение members
или кластеризация завершаются ошибкой, сводки всё равно возвращаются со `stale: null`; исключение
не покидает consumer read path.

## Поведение навыков

No-guidance pressure controls перед реализацией показали, что `reviewer_ask` в 5/5 прогонов
отверг неподтверждённые stale-утверждения, а `reviewer_pr-walkthrough` в 5/5 прогонов безопасно
пропустил спорную подсистему. Их существующие grounding-контракты уже дают нужное поведение,
поэтому дополнительные инструкции туда не добавляются.

`reviewer_solve-task` в 4/5 прогонов перенёс stale-структуру в `## Subsystems`, даже когда
`search_codebase` показывал другой механизм. Только этот навык получает явное правило:
stale-сводка помечается `[stale]`, не используется для структурных утверждений и остаётся
слабым приором.

`stale: null` не получает пользовательского маркера: это отсутствие сигнала, а не доказанная
устарелость. Как и раньше, ни одна сводка не является источником `path:line`.

Описание MCP-тула документирует три состояния, чтобы сторонние клиенты могли корректно
интерпретировать поле.

## Производительность

Полный пересчёт ограничен путями, которые уже возвращают все сводки малого репозитория.
Масштабный query/ANN path сохраняет текущую стоимость и явно возвращает неизвестную свежесть.

Таблица `cluster_hash_snapshots`, автоматический rebuild и кэширование current hashes не входят в
работу. Их стоит рассматривать только после измеренного замедления: сейчас они добавили бы
состояние, миграцию и инвалидацию без подтверждённой пользы.

## Тестирование

### Store

- `get_summaries()` возвращает `source_hash`;
- `search_summaries()` возвращает `source_hash`.

### Service

- совпадающий хеш даёт `stale: false`;
- изменившийся или исчезнувший кластер даёт `stale: true`;
- single-`cluster_key` path аннотируется;
- query ниже либо на пороге использует fetch-all и аннотируется;
- query выше порога использует ANN, возвращает `stale: null` и не вызывает
  `list_base_members`;
- пустой результат не запускает вычисление;
- сбой вычисления возвращает исходные сводки со `stale: null`.

### Skills

Для `solve-task` используются writing-skills pressure scenarios: no-guidance control должен
демонстрировать перенос stale-структуры, а после правки пять свежих прогонов должны либо отбросить
сводку, либо пометить её `[stale]` без неподтверждённых структурных утверждений. Существующий
`tests/skills` остаётся regression-гейтом сборки промптов; новые grep-тесты текста не добавляются.

## Вне скоупа

- автоматическое обновление или перестроение сводок;
- отдельная таблица snapshot-хешей;
- изменение `SUMMARY_TOPK_THRESHOLD`;
- закрытие или переписывание PRI-184;
- дополнительные инструкции в `reviewer_ask` и `reviewer_pr-walkthrough`, чьи no-guidance
  controls уже безопасны;
- изменение builder cap/deferred semantics в `list_subsystem_clusters`.
