# PRI-322. Проверка полноты GitHub compare перед обновлением base-индекса

Измерения выполнены 25 ноября 2026 года на коммитах `mimfort/rag_for_git`.
В обоих случаях использован тот же запрос GitHub compare без параметров пагинации,
который отправляет автоматическая синхронизация перед ревью.

| Сравнение SHA | Ответ GitHub | Файлы в ответе, всего / Python | Различия между деревьями Git, всего / Python |
| --- | --- | ---: | ---: |
| `09c0a4c…d95ea26` | `behind`, 12 коммитов позади | 0 / 0 | 25 / 19 |
| `627bed4…09c0a4c` | `ahead`, 1960 коммитов впереди | 300 / 0 | 1174 / 622 |

В первом случае ревью успевает прочитать прежний SHA целевой ветки до того,
как параллельная индексация публикует новый. GitHub возвращает пустой список
для обратного сравнения. До исправления `ReviewService.prepare` передавал его
в `update_base`, который публиковал прежний SHA поверх более свежих чанков.
Проверка ожидаемой версии записи при этом срабатывала штатно, поскольку
сервис считывал уже новую версию метаданных.

Во втором случае GitHub исчерпал лимит списка файлов.
[Документация GitHub Compare REST API](https://docs.github.com/en/rest/commits/commits#compare-two-commits)
указывает предел в 300 файлов на всё сравнение и выдачу списка файлов
на первой странице при пагинации. По ответу с ровно 300 записями нельзя
отличить полный список от усечённого, поэтому обновление пропускается уже
на этой границе.

При подтверждённом продвижении ветки и списке короче 300 файлов база
обновляется. Пустой список допустим, если итоговое дерево осталось прежним.
Состояние `identical` требует нулевых счётчиков и пустого списка.
При обратном, разошедшемся, неполном или некорректном сравнении сохраняется
ранее опубликованный base-индекс, а подготовка ревью продолжается.
Предупреждение указывает причину, репозиторий, ветку и команду полного обновления.

## Воспроизведение

Для воспроизведения нужен локальный клон с указанными коммитами.

```sh
indexed=09c0a4ce9c36b12a8986b76968bd84b83b0b9a18
earlier=d95ea26a868ac3775bb0c4f719df2d6eff13b66b
initial=627bed406f9406273c6b50e5a400a5ad52e3fa10
gh api "repos/mimfort/rag_for_git/compare/${indexed}...${earlier}" --jq \
  '{status, ahead_by, behind_by, files: (.files | length)}'
gh api "repos/mimfort/rag_for_git/compare/${initial}...${indexed}" --jq \
  '{status, ahead_by, behind_by, files: (.files | length),
    python_files: ([.files[] | select(.filename | endswith(".py"))] | length)}'
git diff --name-only "$indexed" "$earlier" | wc -l
git diff --name-only "$indexed" "$earlier" -- '*.py' | wc -l
git diff --name-only "$initial" "$indexed" | wc -l
git diff --name-only "$initial" "$indexed" -- '*.py' | wc -l
python -m pytest -q tests/services/test_review_service.py -k github_compare
```

Регрессионные тесты используют `ReviewService.prepare` и `GitHubProvider.compare_files`
с ответами HTTP-фикстуры. Девять исходных сценариев падали на `8e93b21`.
После исправления они проверяют, что база пропускает запись и ревью строит
контекст PR. Положительный сценарий проверяет передачу новых чанков, нового SHA
и ожидаемой версии метаданных в атомарную запись.
