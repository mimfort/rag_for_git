# PRI-299. Парный пилот формата ссылок брифа

21 ноября 2026 года проверили Markdown и структурированные записи на шести задачах. Сервер вернул читаемый раздел `## Relevant code` во всех 11 полученных структурированных брифах. Все 11 полученных контрольных брифов использовали строку `Relevant code` без Markdown-заголовка, поэтому перед подсчётом ссылок её нормализовали. По одному ответу для PRI-221 отсутствовало в каждом условии. Изменение покрытия при переходе к структурированным записям имело разные знаки в двух повторах.

## Условия

- Использовали шесть задач прежнего пилота в том же порядке. Крупные — PRI-170, PRI-202, PRI-221. Остальные — PRI-179, PRI-205, PRI-207.
- Передали сохранённую гибридную выдачу `all-30` с лимитом 20 файлов. Архив [входа](input.json.gz) содержит только ключи, постановки и отрисованные фрагменты. SHA-256 распакованных байтов — `4a9773cef65ef00d0bda3b1404337f5d035b7e1687a76d2c3dd32bcf087b8157`. Источники — `eval/pri278/independent-corpus.json` и `eval/pri278/independent/evidence.jsonl.gz`. [Разметку путей](labels.json) читали при оценивании.
- Отправили четыре запроса через Codex CLI 0.170.0 с `gpt-6-luna` на уровне `low`. Оба условия в паре запускались параллельно. В первой паре запросы поставили в очередь в порядке Markdown, затем записи. Во второй паре порядок подачи развернули. Сохранили все четыре ответа первичного прогона.
- Контроль получил исходный промпт и JSON-схему из `eval/pri278/briefs.py`. Структурированный вариант получил те же правила отбора и порядка с полями `section`, `path`, `line`, `reason` для ссылок. Краткая постановка и пояснение об отброшенных фрагментах имели отдельные поля. Роли в обоих условиях не запрашивали. MCP отключили. Журнал CLI подтвердил отсутствие вызовов инструментов. [Хеши промптов, схемы и ответы](responses.json)

## Подсчёт

Покрытие — число уникальных путей с подтверждённой ссылкой, делённое на число путей соответствующей группы в разметке. Ядро состоит из ранее существовавших файлов, нужных для реализации, зависимости — из неизменённых файлов для чтения. В знаменатель вошли все размеченные файлы для шести задач, включая отсутствующие в выдаче. Для медианы сначала посчитали долю по каждой задаче. Ссылка засчитывается только на полностью видимой строке. Для Markdown извлекали первую ссылку из пункта нужной секции и сверяли строку с выдачей. Для записей передавали их в `BriefEvidence.verify_references` и брали ссылки из возвращённого Markdown через `parse_rendered_citations`.

Ошибка формата означает пропущенный или продублированный ответ на задачу, неразбираемую ссылку или секцию, нарушение схемы ответа либо ошибку рендера или обратного чтения. В Markdown принимали отдельную строку `Relevant code`, в том числе в оформлении заголовка или жирным. Читаемые ссылки из частично повреждённой секции сохраняют вклад в покрытие. Пустая читаемая секция даёт нулевое покрытие и считается валидной. Знаменатель — шесть ожидаемых брифов на условие и повтор, 12 на условие в двух повторах. Для отсутствующего брифа покрытие равно нулю.

Отдельно посчитали брифы с точным заголовком `## Relevant code`, который ищет продуктовый потребитель. Долю отказов посчитали по вхождениям разобранных ссылок, включая повторные. Отказы включают ссылки на отсутствующий в секции путь или на строку вне показанного фрагмента. Отказ сам по себе не образует ошибку формата.

Обе ошибки формата — пропуск PRI-221. В первом повторе пропуск был в Markdown, во втором — в записях. Сама секция ссылок читалась во всех полученных брифах после нормализации заголовка для Markdown. В сумме Markdown дал 17 отказов на 88 разобранных ссылок, из них восемь по пути и девять по строке. Записи дали 18 отказов на 76 ссылок, из них десять по пути и восемь по строке.

На пяти задачах, получивших ответ во всех четырёх запусках, покрытие ядра в первом повторе составило 18/44 в обоих условиях, а во втором составило 21/44 для Markdown и 16/44 для записей. Покрытие зависимостей в обоих условиях составило 3/13 в первом повторе и 2/13 во втором.

На этом корпусе сервер стабилизировал заголовок и чтение подтверждённых ссылок из структурированных ответов. Повторы не подтвердили устойчивого роста покрытия ядра или зависимостей. [Разбивка по задачам и посчитанные ссылки](metrics.json)

## Проверка клиентов

Codex CLI 0.170.0 и Claude Code 2.1.309 выполнили `prepare_task_context` и `verify_task_brief` через MCP. Тест использовал один синтетический набор фрагментов. Обе записи файла совпали побайтно с ответом сервера. Парсер прочитал одну подтверждённую ссылку из кода и одну из тестов. Обрезанная строка и путь, упомянутый только в пояснении, остались вне подсчёта. [Результат проверки](client-smoke.json)

Codex использовал живую модель. Claude Code выполнил реальные MCP-вызовы и записал файл своим инструментом `Write`. Ответы модели для Claude Code поступали из локальной фикстуры Messages API, поскольку текущий аккаунт Anthropic приостановлен. Формат потоковых ответов фикстуры следует документации API. [Claude Messages API](https://platform.claude.com/docs/en/build-with-claude/streaming)

Для повторения проверки с локальной фикстурой Claude Code используйте установленный Codex и Claude Code.

```bash
client_run_dir="$(mktemp -d)"
python -m eval.pri299.client_smoke --work "$client_run_dir" --claude-fixture
```

## Воспроизведение

Из корня репозитория с установленными зависимостями проекта. Новый прогон и подсчёт его результатов выполняются в отдельном каталоге.

```bash
pilot_run_dir="$(mktemp -d)"
python -m eval.pri299.pilot run --work "$pilot_run_dir"
python -m eval.pri299.pilot score --work "$pilot_run_dir"
```

Для пересчёта сохранённых ответов без вызова модели используйте следующую команду.

```bash
python -m eval.pri299.pilot score --work eval/pri299
```

Добавьте `--pri278 /путь/к/eval/pri278`, чтобы сверить вложенный вход и Markdown-контроль с исходными материалами. С `score` эта проверка также сверяет разметку.
