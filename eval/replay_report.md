## Оговорка

### Три оговорки, без которых числа читаются неверно

1. **Baseline — «4 файла» из раздела «Приёмка PRI-255», а не «5-6» из описания тикета.**
   Цифра «5-6» ни одним отчётом этого репозитория не подтверждается и, судя по всему,
   предшествует замеру PRI-255. Сверять приёмку с ней значило бы мерить две стороны
   разными линейками.
2. **Сторона «до» эмулирована оверрайдом `code_section` 4×1×2000, а не старым кодом.**
   Это воспроизводит прежнюю арифметическую стену `max_tool_result_chars 8000 ÷
   MAX_BLOCK_CHARS 2000 = 4 блока`. Эмуляция великодушна к baseline: старый путь мог
   потратить слоты на несколько чанков ОДНОГО файла и дать меньше четырёх различных
   файлов. Измеренная дельта, таким образом, — нижняя оценка.
3. **`indexed_sha` не тот, что у PRI-255.** Тот замер снят на `a1b28c1`, индекс с тех пор
   перестроен на `7d66a08`, а корпус вырос с 56 задач до 57. Поэтому числа PRI-256 не
   сравниваются с числами PRI-255 напрямую: сравниваются только две стороны ЭТОГО прогона
   (у обеих `indexed_sha`, коммит и корпус совпадают — предупреждений о несопоставимости
   в отчёте нет).

### Процедура воспроизведения

**Прежде чем запускать: `replay` перезаписывает `eval/replay_report.md` целиком** — автоген
(шапка, идентичность прогона, агрегат, дельта по задачам) затирает и разделы приёмки, включая
этот. Сохрани файл (`git show HEAD:eval/replay_report.md > /tmp/report.md`) и верни разделы
приёмки на место после прогона.

Сторона «до» и сторона «после», два прогона подряд (второй берёт первый как baseline):

```bash
.venv/bin/python -m eval.solve_task_metrics replay --variant multiquery \
  --repo mimfort/rag_for_git --branch dev --baseline multiquery \
  --set code_section.max_files=4 --set code_section.max_chunks_per_file=1 \
  --set code_section.chars_per_file=2000
.venv/bin/python -m eval.solve_task_metrics replay --variant multiquery \
  --repo mimfort/rag_for_git --branch dev --baseline last
```

Объём секции в символах в снимок replay не входит (снимок хранит пути, не тексты), поэтому
он считается отдельно — обе стороны в одном процессе, чтобы LRU эмбеддера не удваивал
расход Voyage:

```python
import pathlib
import statistics

from eval.solve_task_metrics import live, replay as replay_mod
from eval.solve_task_metrics.context_paths import extract_context_paths
from reviewer.mcp.subqueries import build_subqueries

BEFORE = {"code_section": {"max_files": 4, "max_chunks_per_file": 1,
                           "chars_per_file": 2000}}
rows = []
provider, repo, branch = live.open_live("mimfort/rag_for_git", "dev")
with provider:
    for key in replay_mod.corpus_keys(pathlib.Path("docs/superpowers/briefs")):
        task = provider.task(key)
        queries = build_subqueries(task, provider.query(task, key))
        before = provider.code_multi(repo, branch, queries, BEFORE)
        after = provider.code_multi(repo, branch, queries, None)
        rows.append((len(before), len(after),
                     len(extract_context_paths(before)),
                     len(extract_context_paths(after))))
        print(key, rows[-1], flush=True)
for i, name in enumerate(("символов до", "символов после", "файлов до", "файлов после")):
    print(name, statistics.median([r[i] for r in rows]))
```

Оверрайд `code_section` через `--set` появился вместе с этим замером (PRI-256): без него
раздел не сериализовался в `limits_to_yaml` и молча терялся в `LiveRetrieval.code_multi`,
то есть сторону «до» нечем было бы выразить.

Единственная задача с ростом recall прибавила +0.25 медианы (пренебрежимо на фоне семи падений).

**Вердикт: рычаг снимается** — 2 % точность подмешанных путей, вытеснение core-хитов (9 из 92)
и просадка recall у 7 задач против 1 выросшей перевешивают потенциальный выигрыш; механика
бюджета проверена и не виновата (см. ниже).

### Механика бюджета проверена — сигнал доезжает до секции

Перед интерпретацией числа проверено ровно то, о чём предупреждает PRI-257 (три ложных нуля,
вызванных механикой бюджета, а не свойством сигнала): нота видимости `— подмешано N файлов:
subsystems N (квота Q)` в сырой выдаче секции `code` подтверждает, что файлы разворота реально
доезжают до неё. Ручная проверка на первых шести задачах корпуса (вариант `subsystem_paths`,
изолированно): 5 из 6 задач показали `— подмешано 2 файлов: subsystems 2 (квота 2)` — квота
`max_subsystem_files=2` выбирается целиком; одна задача (`PRI-162`) не дала ноты вовсе (пустое
пересечение сводок с известными путями — штатный случай отсутствия сигнала, а не сбой механики).
Таким образом низкий core-recall варианта — свойство самого сигнала (файлы релевантного кластера
сводок часто не совпадают с ядром правки конкретной задачи), а не артефакт квоты/известности/
файлового бюджета, как было у трёх первых замеров co-change в PRI-257.

### Что показывают числа

**Разворот кластеров вытесняет core-файлы, которые `similar_paths` находил сам.** У совместного
варианта 9 из 81 вытесненных путей были core-хитами `similar_paths` — то есть каждый девятый файл,
занятый разворотом кластеров, отобрал слот у файла, который гибрид+similar-diffs уже держали в
ядре выдачи. У изолированного `subsystem_paths` эта доля ещё выше — 30 core-хитов из 86
вытесненных.

**Точность добавленных путей крайне низкая.** Из 92 путей, добавленных разворотом кластеров
поверх `similar_paths`, в ядро попали только 2 (2 %) — против 80 % у similar-diffs при приёмке
PRI-257. Кластер сводки подсистемы описывает состав подсистемы в целом, а не файлы, которые нужно
менять под конкретную задачу; релевантность по ANN-близости запроса к сводке не эквивалентна
релевантности конкретных файлов состава.

**Дельта отрицательна и по медиане, и по bulk одновременно** — не единичный выброс распределения:
7 задач потеряли recall против 1 выигравшей, падения сосредоточены на задачах, где similar-diffs
и без того давал полное покрытие (`PRI-249`, `PRI-255`: 1.0 → 0.6667) — разворот кластеров вытеснил
уже найденные core-файлы файлами состава подсистемы.

### 5. Чего метрика не видит

Знаменатель core-recall — только файлы, изменённые настоящими PR-мержами задачи. Файл, который
надо прочитать, но не менять (контракт, соседний адаптер, образец для нового кода), в знаменатель
не входит: recall он не штрафует, а precision — штрафует (`predicted`, не входя в `expected`,
считается шумом). Отсюда два вывода этого раздела.

Во-первых, **измеренная precision систематически занижена, и её рост не является целью**: медиана
precision по ходу лестницы/яруса B падает (0.3333 → 0.225 на выбранной точке). Это не регресс —
оптимизация под precision выбрасывала бы ровно тот контекст, ради которого секция существует. В
приёмке PRI-257 рост precision вдвое читался как хороший знак — с точки зрения этого раздела это
индикатор со смещением, а не самостоятельная цель.

Во-вторых, **справочная точка `20×780` (ниже пола глубины) дала числа, тождественные `20×975`**
(0.7500/0.5833) при операционном бюджете на 20 % меньше (15 600 против 19 500). Это прямое
эмпирическое подтверждение слепоты метрики к глубине фрагмента: метрика считает пути, а не
содержимое блока, поэтому сокращение `chars_per_file` ниже 975 бесплатно по замеру — и оплачено
ровно тем, чего замер не видит: способностью брифа объяснить, ЗАЧЕМ файл нужен. Точка `20×780`
отклонена не по числам (по числам она выигрывает у выбранной точки, а не проигрывает), а потому
что её выигрыш куплен вслепую. Пол `chars_per_file ≥ 975` взят из требования «в блоке читаются
сигнатура символа и несколько строк тела», а не из метрики — метрика к этому требованию
чувствительности не имеет.

## PRI-261 — отрицательный результат

**Гейт ручной сверки не пройден: 41.8 % путей контекстного ядра признаны осмысленными против
предзарегистрированного порога ≥ 50 %.** Раздел документирует, почему `context-recall` в его
текущем виде не готов к принятию решений, а не описывает принятую метрику.

### 1. Что мерилось и зачем

`core-recall` считает знаменателем только файлы, изменённые настоящими PR-мержами задачи. Файл,
который надо ПРОЧИТАТЬ, но не менять (контракт, соседний адаптер, образец для нового кода), в этот
знаменатель не входит: recall его не штрафует, а precision — штрафует (`predicted`, не входя в
`expected`, считается шумом). `context-recall` был задуман как второй знаменатель рядом с первым —
контекстное ядро из графа (соседи затронутых диффом символов по исходящим `CALLS`/`IMPLEMENTS`),
не заменяющий core-recall, а измеряющий отдельно ту часть ретрива, которую core-recall структурно
не может оценить.

### 2. Спайк: решает сидирование, а не глубина обхода

Замер на 8 задачах (`dev`, `indexed_sha 308b86b`, всего core-файлов в репозитории — 152), медиана
числа НОВЫХ core-файлов (сверх изменённых задачей):

| сиды | обход | медиана |
|---|---|---|
| все символы изменённых файлов | ненаправленный, 1 хоп | 60 |
| все символы изменённых файлов | направленный `CALLS`, 1 хоп | 57 (37 % репозитория) |

   и корректно исключена вычитанием изменённого ядра — но это вычитание защищает только файлы,
   которые сами были изменены, а не файлы, достигнутые через нетронутую ветку той же функции.
2. **God-модули тащат всё, что импортирует функция, а не то, что трогает логика правки.**

### 5. Вопрос глубины закрыт доказательством, а не замером

Код-уровневое доказательство: в `reviewer/retrieval/multiquery.py:274-292` `diversify_by_file`
фиксирует НАБОР ФАЙЛОВ только по `max_files`/`max_chunks_per_file`; `chars_per_file` применяется
ПОСЛЕ, в `cap_block` (строка 292), к уже отобранным блокам — а заголовок блока — первая строка
блока, и обрезка `cap_block` её не убирает никогда (`kept`, пустой на первой итерации, всегда
получает первую строку независимо от длины). Значит набор путей физически не может зависеть от
`chars_per_file`.

Подтверждение: три прогона на `chars_per_file` 780/975/1300 (тот же `indexed_sha`, тот же
`--baseline last`) дали побайтово идентичные `context_core_paths` во всех трёх и тождественные
ВСЕ МЕДИАНЫ агрегата (`core_recall_median`, `bulk_core_recall_median`, `context_recall_median`,
`union_precision_median`, `precision_median`, `predicted_median`). Одно исключение, и оно не
случайно: `core_recall_mean` различается — 0.71347 (975) / 0.71037 (780) / 0.70674 (1300).
Это НЕ эффект глубины, а прямое следствие пола шума из раздела 6: у нескольких задач сырые
`predicted_paths` расходятся на один файл, среднее к такому сдвигу чувствительно, медиана — нет.
Формулировка «тождественные агрегаты» была бы здесь неверна, и разделы 5 и 6 согласуются только
в точной формулировке: набор путей от глубины не зависит (это и доказано), а среднее гуляет от
шума харнесса. Вывод: ни одна метрика, считающая пути, не может отличить глубину фрагмента; пол
`chars_per_file ≥ 975` (PRI-259) остаётся инженерным решением, но теперь задокументирован как
принципиально неизмеримый метриками этого класса. Дефолты `CodeSectionLimits` не изменены.

### 6. Измеренный пол шума харнесса

Отдельная находка, не связанная с гейтом раздела 3, но полезная сама по себе: сырые
`predicted_paths` (не контекстное ядро) отличались на ±1 файл у 4 из 62 задач В КАЖДОМ ПОПАРНОМ
сравнении прогонов на ОДИНАКОВЫХ параметрах — причём прогоны 780 и 1300 разошлись друг с другом
ровно настолько же, насколько каждый разошёлся с прогоном 975, немонотонно по `chars_per_file`.
Важно не спутать попарную величину с общим охватом: затронутые задачи в трёх сравнениях РАЗНЫЕ
(975↔780 — PRI-254/251/243/238; 975↔1300 — PRI-251/225/202/238; 780↔1300 — PRI-254/225/243/202),
поэтому объединение — 6 задач из 62 (≈ 9.7 %), а не 4 (≈ 6 %). Попарная величина отвечает на
вопрос «насколько разойдутся два прогона», объединение — «сколько задач вообще нестабильны». Такой рисунок
исключает причинность от глубины (будь дело в ней, расхождение было бы систематическим) — это
шум тай-брейка живого гибридного поиска на границе `max_files`, не эффект `chars_per_file`.
Практическое следствие: построчные дельты путей в таблицах приёмок PRI-255…259 в пределах
примерно ±1 файла — шум, а не сигнал; медианы там не затронуты.

### 7. Четыре оговорки

- **`typing.Protocol` не даёт рёбер наследования** — структурная типизация рёбрами не выражается
  ни при каком графовом бэкенде (тот же класс дефицита, что закрывает `family` вне графа).
- **Импорт — не ребро.** Граф знает только вызовы (`CALLS`) и наследование (`IMPLEMENTS`); файл,
  достижимый только через `import`, без вызова символа из него, обходом не находится.
- **Обход идёт по СЕГОДНЯШНЕМУ графу**, а не по состоянию репозитория на момент каждой
  исторической задачи; на момент измерения `dev` нёс `drift=25` (индекс не пересобирался —
  пересборка обнулила бы сравнимость этого раздела с историей PRI-254…259, измеренной на том же
  `308b86b`).
- **Слепое пятно сидирования на non-Python `plugin/*` (новое, PRI-261).**
  `classify.is_core_production_path` считает `plugin/*` не-`.md` файлы ядром, включая JSON/конфиг;
  `context_seeds._symbols_at` строит сиды через `chunk_python`, который понимает только Python.
  Задача, чьё core-изменение целиком лежит в non-Python `plugin/*` (3 из 62: PRI-177, PRI-237,
  PRI-243), не может дать ни одного сида по построению — её знаменатель контекста не пустой, а
  НЕОПРЕДЕЛЁННЫЙ, и это не одно и то же с «у задачи честно нет контекста».

### 8. `no_context_measurement = 5` разобран по задачам

Ни одного проглоченного исключения — подтверждено прямым безоборачиваемым вызовом той же цепочки
(`collect_seeds` → `derive_context_core`) против живого графа `dev`, без `except`, ни разу не
упавшим:

- **PRI-211** — сиды нашлись, сосед нашёлся (`reviewer/index/store.py`), но этот путь и так внутри
  изменённого ядра задачи — корректно вычтен по определению `derive_context_core`.
- **PRI-259** — сид нашёлся (`CodeSectionLimits`, простой dataclass), но у него ноль исходящих
  `CALLS`/`IMPLEMENTS` рёбер в графе — честно безлистный узел.
- **PRI-177, PRI-237, PRI-243** — слепое пятно non-Python `plugin/*` из раздела 7 выше: core-путь
  задачи целиком JSON, ноль сидов по построению.

### 9. Выбор по критерию 6 — офлайн-only

Схема `brief_quality` не менялась. Основания: `bulk_n_measured = 4` у существующей онлайн-метрики

### 10. Гипотеза для follow-up (post-hoc, НЕ поправка к вердикту)

Правдоподобная причина неудачи (раздел 3) наводит на гипотезу: отфильтровать хунки, не меняющие
исполняемый код, и сузить сиды до символов, чьи ИЗМЕНЁННЫЕ строки содержательны. Проверка этой
гипотезы честности ради: если вручную исключить из выборки два чисто-комментарийных случая

как направление для будущей задачи, а не как пересчёт вердикта: применить её только после того,
как данные уже увидены, — ровно то, для предотвращения чего существует предрегистрация порога.
